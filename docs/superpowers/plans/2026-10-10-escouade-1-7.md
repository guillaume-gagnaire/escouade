# Escouade 1.7 — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Livrer la 1.7 décrite dans `docs/TODO-1.7.md` : l'interface en anglais et en français (langue du système par défaut), le site dans les deux langues, plusieurs comptes Claude avec bascule automatique, un serveur MCP pour piloter Escouade depuis Claude, et la gestion des branches.

**Architecture:** Même architecture qu'en 1.6 : backend Rust (`src-tauri/src`, commandes Tauri dans `commands.rs`, logique dans `core.rs`, `tickets.rs` et les modules métier), frontend Svelte 5 (runes) dans `src/`, IPC typé dans `src/lib/ipc.ts`, types dans `src/lib/types.ts`, état global dans `src/lib/state.svelte.ts`. Nouveaux modules : `src/lib/i18n/` (catalogues), `src-tauri/src/i18n.rs`, `src-tauri/src/accounts.rs`, `src-tauri/src/mcp/`. Le travail est réparti en chantiers (L langues, S site et vidéo, K comptes, M serveur MCP, G branches, D docs) exécutés dans des worktrees séparés, par vagues (voir « Ordre d'exécution »).

**Tech Stack:** Rust (Tauri 2, tokio, git CLI, rusqlite, keyring), `rmcp` 3.5 (SDK MCP officiel) servi par `hyper` 1 / `hyper-util`, `sys-locale`, `sha2` ; Svelte 5 + TypeScript, CodeMirror 6, xterm.js ; Vitest + Testing Library, Playwright (app réelle) ; site Nuxt 4 (`website/`), vidéo Remotion (`video/`).

**Spec:** `docs/TODO-1.7.md` (rédigée avec l'utilisateur, commits du 2026-10-10) fait office de spec ; les essais du point 0 et les décisions sur les points laissés ouverts sont consignés ci-dessous. `docs/SPEC.md`, `docs/PROTOCOL.md` et `PRODUCT.md` décrivent le produit existant.

**Forme du plan :** comme en 1.6, les tâches donnent les exigences, les libellés, les interfaces et les cas de test, sans le code complet. L'implémenteur explore le code cité, écrit d'abord les tests (rouge vérifié), puis le code.

## Résultats des essais (point 0 de la todo)

Faits le 2026-10-10 sur Claude Code 2.1.289 (Windows), dans des dossiers jetables :

1. **Trousseau macOS et `CLAUDE_CONFIG_DIR`** (lu dans le binaire de Claude Code) : le nom du service est `Claude Code-credentials` quand `CLAUDE_CONFIG_DIR` n'est pas défini, et `Claude Code-credentials-<h>` sinon, `<h>` étant les 8 premiers caractères hexadécimaux du SHA-256 de la valeur de `CLAUDE_CONFIG_DIR` normalisée en NFC (`CLAUDE_SECURESTORAGE_CONFIG_DIR` prend le pas s'il est défini). Chaque dossier de config a donc son entrée : les comptes multiples marchent sous macOS. **Conséquence :** le compte Principal se lance **sans toucher** à `CLAUDE_CONFIG_DIR` (le définir, même à `~/.claude`, changerait le nom de l'entrée et déconnecterait l'utilisateur) ; un autre compte reçoit exactement la chaîne dont Escouade calcule le hachage. Sous Windows, Claude Code écrit `<dossier>/.credentials.json` (un drapeau distant, `tengu_windows_credman`, pourrait le faire passer au Gestionnaire d'identification avec les mêmes noms : hors périmètre, à noter dans la SPEC).
2. **Reprise d'une session dans un autre dossier** : `projects/<cwd encodé>/<id>.jsonl` copié dans un autre `CLAUDE_CONFIG_DIR`, `claude -p --resume <id>` lancé depuis le même dossier de travail trouve la session (le refus porte sur la connexion, « Not logged in », alors qu'un id inconnu donne « No conversation found with session ID »). La reprise sur un autre compte est donc possible ; non vérifié faute de second compte réel : que l'API accepte une conversation d'un autre compte (blocs de réflexion signés). Le dire dans la SPEC, et rendre l'échec lisible (K7).
3. **`rmcp`** : version 3.5.1 (MSRV 1.88, toolchain du dépôt 1.98) ; features `server`, `macros`, `transport-streamable-http-server` ; le service HTTP est un service tower à servir avec `hyper` 1 + `hyper-util`, déjà dans `Cargo.lock` (1.11 / 0.1.21) ; tokio 1.53 compatible (ajouter la feature `net` de tokio). Côté tests, `client` + `transport-streamable-http-client-reqwest` en dev-dependencies.
4. **`claude mcp add` sous Windows** : `claude mcp add --scope user --transport http escouade http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <jeton>"` passe tel quel (en-tête avec espace compris) ; avec `CLAUDE_CONFIG_DIR`, l'entrée va dans `<dossier>/.claude.json` → `mcpServers.escouade = {type:"http", url, headers:{Authorization}}`. Un second `add` du même nom échoue (code 1, « already exists in user config ») ; `remove` d'une entrée absente : code 1 ; `mcp get` tente une connexion (lent) : Escouade compare en lisant `.claude.json` directement et n'utilise la CLI que pour écrire (`add` / `remove`).
5. **Priorité entre la config utilisateur et `--mcp-config`** (essai en plus) : un serveur `escouade` passé par `--mcp-config` (source « dynamic ») remplace celui du même nom de la portée `user` ; seul le serveur de `--mcp-config` est contacté, avec son en-tête. Claude Code 2.1.289 envoie d'abord une sonde `server/discover` (protocole `2026-07-28`) puis `initialize` (`2025-11-25`).

## Décisions sur les points ouverts de la todo

- **Langues, mécanique de la fenêtre :** module maison (pas de Paraglide) : catalogues TypeScript par langue et par zone, gabarits `{param}`, pluriels `{ one, other }` résolus par `Intl.PluralRules`. Les clés et les paramètres sont vérifiés à la compilation (types) et par un test.
- **Langues, Rust :** macro `tr!("texte fr {x}", "english {x}", x = …)` : les deux langues sont écrites ensemble à l'endroit du texte, et le compilateur refuse un argument nommé que l'une des deux n'utilise pas (« named argument never used ») : clés et paramètres identiques par construction. Pas de fichiers de catalogue séparés côté Rust.
- **« 7j »** (et non « W ») pour la fenêtre hebdomadaire en français, « W » en anglais, comme proposé.
- **`headersHelper` :** écarté pour la 1.7 (un script par système qui lit le trousseau à chaque connexion : fragile). Le jeton est écrit en clair dans `.claude.json`, ce que l'onglet dit, et désactiver change le jeton. À reprendre plus tard si besoin.
- **Pont stdio (`escouade-mcp.exe`) et outils destructeurs :** hors 1.7, comme la todo le dit.
- **Identité d'un agent auprès du serveur MCP :** un jeton par agent (et non un en-tête que n'importe quel client pourrait imiter), passé par `--mcp-config` ; l'essai 5 garantit qu'il remplace l'entrée de l'utilisateur.
- **Agents d'un projet où « Les agents peuvent utiliser Escouade » est désactivé :** lancés avec `--disallowedTools mcp__escouade`, sinon ils hériteraient de l'entrée déclarée dans la config de l'utilisateur.
- **Le serveur tourne** quand « Claude peut piloter Escouade » est activé ou qu'au moins un projet laisse ses agents l'utiliser.
- **`move_ticket` :** réordonne un ticket « À faire » (en tête, en bas, avant un autre) ; démarrer, c'est `start_ticket` ; valider (merge) reste exclu.
- **Compte « en cours » de la barre d'état :** celui sur lequel partiraient les nouveaux agents (le premier compte actif sous le seuil, sinon le premier actif).
- **Fichiers partagés entre comptes :** dossiers (`skills`, `agents`, `commands`, `plugins`, `hooks`, `output-styles`) liés par jonction (Windows) ou lien symbolique (macOS) ; fichiers (`settings.json`, `CLAUDE.md`) liés par lien symbolique sous macOS, copiés sous Windows (un lien de fichier y demande des droits d'administrateur), ce que la fenêtre dit.
- **README anglais, voix anglaise de la vidéo :** pas dans la 1.7. Le site anglais a des sous-titres anglais ; une voix anglaise (crédits ElevenLabs) et un `README.en.md` attendent l'accord de l'utilisateur.
- **Version :** CHANGELOG « ## [1.7.0] — à venir » ; la montée de version, le push et la release restent soumis à l'accord de l'utilisateur.

## Global Constraints

- **Textes de l'interface dans les deux langues, jamais en dur :** tout texte visible passe par `t()` (fenêtre) ou `tr!` (Rust) dès la tâche L1/L2 ; le garde-fou de L1 fait échouer les tests sur un texte en dur dans un fichier qui n'est pas encore dans une liste « à extraire ». Les nouveaux textes (chantiers K, M, G, S) s'écrivent directement dans les deux catalogues.
- **Français :** au tutoiement, simple et concret, sans emphase ; apostrophes et guillemets typographiques (’ « ») comme dans le code existant. Les libellés entre « » de ce plan sont à reprendre tels quels.
- **Anglais :** même ton (« you », phrases simples et concrètes, impératif pour les actions, majuscule au premier mot seulement : « Add an account », pas « Add An Account ») ; apostrophe typographique ’ et guillemets “ ” ; termes du glossaire `src/lib/i18n/GLOSSARY.md` (créé en L1, complété par chaque tâche).
- **Clés :** `zone.composant.sens` en camelCase (`editor.tabs.closeOthers`), une phrase entière par clé (jamais de fragments recollés : l'ordre des mots change d'une langue à l'autre), pluriels par feuille `{ one, other }` avec le paramètre `count`, paramètres `{nom}`. Une zone (`editor`, `settings`…) appartient à une seule tâche à la fois ; `common` (Annuler, Enregistrer, Fermer…) est rempli par L1 et n'est plus modifié par les tâches d'extraction (elles ajoutent ce qui leur manque dans leur zone).
- **Changement de langue à chaud :** aucun texte calculé une fois pour toutes au chargement d'un module (`const LABELS = { … 'Texte' }`) : une constante de libellés devient une fonction, un getter ou un `$derived`, lu au rendu.
- **Code, noms et commentaires en anglais**, avec la densité de commentaires du code voisin (commentaires qui disent le *pourquoi*).
- **Windows 10/11 et macOS 11+ :** raccourcis par `primaryKey` / `keyLabel` de `src/lib/platform.ts` ; Ctrl+Alt est AltGr sur les claviers français : jamais un raccourci. Code `cfg(target_os = "macos")` : compilé seulement par le job macOS de la CI, l'écrire avec soin et le dire dans le rapport.
- **Chemins :** tout chemin reçu du frontend passe par `paths::contained` / les validations de `fsedit.rs`.
- **Persistance :** nouveaux champs de réglages et d'état : `#[serde(default)]` ; un ancien `settings.json` / `state.json` / `stats.db` se charge toujours : un test de chargement d'un ancien fichier pour chaque nouveau champ ou colonne.

Les tests existants restent en français et leurs attentes ne changent pas.

**Interfaces (Produces, utilisées par toutes les tâches suivantes):**
- `export type Lang = 'fr' | 'en'` ; `locale` (`$state`, `{ ui: Lang }`) ; `setLang(l: Lang)` (met aussi `document.documentElement.lang`).
- `t(key, params?)` : `key` est une union typée de tous les chemins de feuilles du catalogue français ; `params` est exigé et typé (`string | number`) quand la feuille a des `{x}`, `count: number` pour une feuille plurielle ; lit `locale.ui`, donc réactif dans un gabarit ou un `$derived`.

- `Rich.svelte` : `<Rich text={t('…')} {...snippets} />` découpe le texte sur les `{nom}` et rend le snippet du même nom (`<kbd>`, lien, gras) ou le paramètre texte ; pour les phrases avec du balisage au milieu.
- `fList(items: string[])` (`Intl.ListFormat`, conjonction : « a, b et c » / « a, b, and c »).

**Files:** Modify `src-tauri/src/git.rs` (+ `repo_tests`), `src-tauri/src/core.rs` (opérations sur le dossier du projet, rafraîchissement), `src-tauri/src/commands.rs` + `lib.rs`, `src/lib/ipc.ts`, `src/lib/types.ts`

**Interfaces (Produces):**
- `git::branch_list(repo) -> Vec<BranchInfo { name, remote: bool, current, upstream: Option<String>, ahead, behind, worktree: Option<String> (chemin), last_commit_at }>` (locales puis distantes, `refs/remotes/*/HEAD` exclu ; une distante déjà suivie en local reste listée, marquée).
- `git::check_ref_format(name) -> Result<()>` (`git check-ref-format --branch`, nom commençant par `-` refusé).
- `git::branch_create(repo, name, start: &str) -> Result<()>` ; `git::switch_to(repo, name) -> Result<()>` (locale ; distante `origin/x` → `switch --track`, ou la locale qui la suit déjà) ; `git::stash_push(repo, message) -> Result<String>` ; `git::branch_delete(repo, name, force) ` ; `git::branch_delete_remote(repo, remote, name)` ; `git::merged_into(repo, base) -> Vec<String>` ; `git::unique_commits(repo, branch) -> u32` (commits que n'a aucune autre branche locale ou distante) ; `git::diff_refs(repo, a, b) -> String` (`git diff a b`).
- `Core` : `branches(project)`, `branch_switch(project, name, stash: bool)`, `branch_create(project, name, start, switch)`, `branch_delete(project, name, remote: bool, force: bool)`, `branches_merged(project)`, `diff_refs(project, a, b)`, avec les erreurs typées `DIRTY` (changements non commités), `IN_WORKTREE:<agent>` (branche prise par le worktree d'un agent), `AGENT_WORKING:<agent>` (un agent sans worktree travaille dans le dossier du projet), `UNMERGED:<n>` (commits uniques), lues par la fenêtre comme `NOT_ON_BASE`.

**Exigences:**
- Changer de branche : refusé tant qu'il reste des changements non commités (`DIRTY`), sauf avec `stash` (stash « escouade: avant de passer sur <branche> » puis changement) ; refusé si un agent sans worktree du projet a un tour en cours (`AGENT_WORKING`) ; une branche prise par un worktree d'agent : `IN_WORKTREE` (au lieu de l'erreur de git).
- Supprimer : jamais la branche courante ni celle d'un worktree ; une branche mergée dans la base du projet se supprime directement ; sinon `UNMERGED:<n>` tant que `force` n'est pas donné ; la distante en option.
- Après chaque opération : `core.git.refresh(project)`.
- Toutes les erreurs affichées par `tr!`.

**Tests attendus (dépôts git réels):** liste (locale, distante, courante, upstream, avance/retard, worktree) ; nom invalide refusé (`a..b`, `-x`, `x.lock`, vide) ; création depuis un commit, depuis une autre branche ; changer sans changements, avec changements (refus), avec stash (changements dans le stash, branche changée) ; branche d'un worktree refusée ; agent qui travaille refusé (cœur) ; suivre une branche distante ; supprimer mergée, non mergée refusée puis forcée, courante refusée, de worktree refusée, distante ; `merged_into` ; `diff_refs`.

- [ ] Tests rouges, `git.rs`, verts
- [ ] Cœur, commandes, tests verts
- [ ] Vérifications globales, commits `feat(git): …`
