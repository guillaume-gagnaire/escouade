# Escouade 1.6 — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Livrer le lot validé le 2026-10-10 : navigation de code par Ctrl+clic (liens de fichiers et définitions approchées), corrections (pilote auto et quotas, diff de tout le projet, merge vers la base), mises à jour silencieuses, confirmation des recettes, gains rapides, gros chantiers et petits points de la revue du 2026-10-09.

**Architecture:** Chaque tâche est autonome et suit l'architecture existante : backend Rust (`src-tauri/src`, commandes Tauri dans `commands.rs`, logique dans `core.rs` et les modules métier), frontend Svelte 5 (runes) dans `src/`, IPC typé dans `src/lib/ipc.ts`, types dans `src/lib/types.ts`, état global dans `src/lib/state.svelte.ts`. Les tâches sont réparties en quatre chantiers (E éditeur, G git et Kanban, C conversations et agents, O exploitation) exécutés en parallèle dans des worktrees séparés ; dans un chantier, les tâches se suivent dans l'ordre.

**Tech Stack:** Rust (Tauri 2, tokio, git CLI, rusqlite), Svelte 5 + TypeScript, CodeMirror 6 (`@codemirror/*`, Lezer), xterm.js, Vitest + Testing Library, Playwright (app réelle).

**Spec:** ce document fait office de spec : décisions validées par l'utilisateur dans la conversation du 2026-10-09/10 (réponses « ok / corrige / yes go » sur la liste de suggestions), plus `docs/SPEC.md` et `PRODUCT.md` pour le produit existant.

**Forme du plan (écart assumé) :** contrairement aux plans précédents, les tâches donnent les exigences, les libellés exacts, les interfaces et les cas de test attendus, sans le code complet. L'implémenteur explore le code cité, écrit d'abord les tests (rouge vérifié), puis le code.

## Global Constraints

- UI en français, au tutoiement, simple et concrète, sans emphase ; apostrophes et guillemets typographiques comme dans le code existant (« », ’ dans les textes Svelte). Les libellés entre « » de ce plan sont à reprendre tels quels.
- Code, noms et commentaires en anglais, avec la densité de commentaires du code voisin (commentaires qui disent le *pourquoi*, phrases complètes).
- Windows 10/11 et macOS 11+ : raccourcis par `primaryKey` / `keyLabel` de `src/lib/platform.ts` (Ctrl sous Windows, Cmd sous macOS) ; Ctrl+Alt est AltGr sur les claviers français : jamais un raccourci.
- Tout chemin reçu du frontend passe par `paths::contained` / les validations de `fsedit.rs` ; rien ne s'écrit hors du dossier du projet ou du worktree de l'agent.
- Nouveaux champs de réglages et d'état persistés : `#[serde(default)]` (un ancien `settings.json` / `state.json` doit toujours se charger) ; test de chargement d'un ancien fichier pour chaque nouveau champ.
- Accessibilité : tout se fait au clavier, focus visible, `prefers-reduced-motion` respecté, rôles ARIA justes ; couleurs via les variables CSS existantes (`--line`, `--elev2`, `--muted`, `--dim`, `--text`, `--wait`, `--add`…).
- TDD : test rouge vérifié avant le code, pour chaque comportement ; tests Vitest à côté du fichier (`x.test.ts`), tests Rust dans le module de test existant du fichier (ou `*_tests.rs`) ; noms de `test_dir(...)` uniques dans tout le binaire de test.
- Vérifications avant de déclarer une tâche finie, depuis le worktree du chantier : `npm run format:check`, `npm run check`, `npm test`, puis dans `src-tauri` : `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`. Un test e2e Playwright n'est écrit que si la tâche le demande ; dans ce cas, `npx tauri build --debug --no-bundle` puis `npx playwright test -g "<nom du test>"` (pas la suite complète : elle est lancée par le contrôleur sur `main`).
- Commits atomiques sur la branche du chantier, au style du dépôt : `type(portée): phrase en français qui décrit le comportement` (`feat`, `fix`, `test`, `refactor`, `docs`, `chore`), terminés par la ligne `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Pas de push. Ne pas toucher `CHANGELOG.md` ni la version : chaque rapport d'implémentation se termine par une section « Changelog » (puces au style de `CHANGELOG.md`) que le contrôleur compile à la fin.
- Environnement Windows : pas de Python ; contenus avec antislashs ou backticks écrits avec Write/Edit (pas de heredoc bash, pas de `node -e` avec backticks) ; `String.replace` dans un script interprète `$&` : utiliser `split/join`.
- Aucune nouvelle dépendance sans nécessité ; celles autorisées par ce plan : `keyring` (tâche 15), `trash` (tâche 6). `@codemirror/merge` est déjà là.

**Interfaces:**
- Produces (utilisé par la tâche 2) :
  - `export interface NavTarget { path: string; line?: number; col?: number }` (chemin relatif à la racine de la source, `/`)
  - `export interface NavSpot { from: number; to: number; resolve: () => Promise<NavTarget[]> }`
  - `export type NavResolver = (ctx: { state: EditorState; pos: number; path: string; files: readonly string[] }) => NavSpot | null`
  - `export function gotoExtension(o: { resolvers: NavResolver[]; onTargets: (t: NavTarget[], from: { line: number; col: number }) => void; ... }): Extension` — les résolveurs sont essayés dans l'ordre, le premier qui rend une zone gagne.
  - `openEditor({ ..., line?, col? })` : `col` (1-based) place le curseur exactement ; `app.editor[pid].reveal` devient `{ path, line, col?, seq }`.
  - `navHistory` (dans `history.ts`) : `push(entry)`, `back()`, `forward()`, entrées `{ projectId, source, path, line, col }`.

**Exigences:**
- Aujourd'hui Ctrl+clic (Cmd+clic sous macOS) ajoute un curseur (défaut de CodeMirror). Désormais : Alt+clic (Option+clic) ajoute un curseur, via `EditorView.clickAddsSelectionRange.of((e) => e.altKey)`. Ctrl+clic (Cmd+clic) navigue.
- Modificateur enfoncé et souris sur une zone navigable : la zone est soulignée et le curseur souris devient une main ; relâcher la touche, quitter la zone ou perdre le focus de la fenêtre retire le soulignement.
- F12 navigue depuis la position du curseur texte.
- Zones navigables du niveau A :
  - spécificateurs d'import relatifs ou aliasés en JS/TS/JSX/TSX/Svelte/Vue : `import … from '…'`, `export … from '…'`, `import('…')`, `require('…')` ; résolution : relatif au dossier du fichier, extensions essayées `.ts .tsx .d.ts .js .jsx .mjs .cjs .svelte .vue .json`, puis `index.*` du dossier ; alias `compilerOptions.paths` + `baseUrl` de `tsconfig.json` / `jsconfig.json` à la racine (JSON avec commentaires) et `$lib` → `src/lib` pour SvelteKit ;
  - CSS/SCSS : `@import '…'`, `url(…)` relatifs ;
  - Rust : `mod nom;` → `nom.rs` ou `nom/mod.rs` à côté (ou dans le dossier du module parent pour un fichier non `mod.rs`/`lib.rs`/`main.rs`) ;
  - Python : `from .x import y`, `from ..x.y import z`, `import a.b` (relatif à la racine de la source) → `x.py` ou `x/__init__.py` ;
  - Markdown et HTML : liens relatifs `[t](./x.md)`, `src="…"`, `href="…"` (sans schéma) ;
  - partout (tout langage, texte brut compris) : un chemin qui existe dans l'arborescence, éventuellement suivi de `:ligne` ou `:ligne:colonne` (`src/lib/x.ts:42:7`).
  - Un spécificateur de paquet (`react`, `@scope/x`) n'est pas navigable au niveau A (pas de soulignement).
- Seuls les fichiers de l'arborescence de la source (`tree.files`) sont des cibles ; une cible absente : toast « Fichier introuvable : <chemin> ».
- Une cible ouvre le fichier dans la même source, à la ligne et colonne données, curseur placé, ligne centrée.
- Historique de navigation par projet et source : avant chaque saut (Ctrl+clic, F12, ouverture depuis un résultat de recherche des tâches 2-3), la position courante est empilée. Alt+← / Alt+→ (macOS : Ctrl+- / Ctrl+Maj+-) reculent / avancent, et les boutons « précédent / suivant » de la souris aussi, quand le focus est dans l'éditeur. Pile limitée à 50 entrées ; une entrée dont le fichier n'existe plus est sautée.
- Les raccourcis Alt+← / Alt+→ ne sont pris que dans l'éditeur (jamais dans un terminal ni dans le composer).

- Ordre de recherche :
  1. dans le fichier, par l'arbre Lezer : définitions portant ce nom (JS/TS : `VariableDefinition`, `TypeDefinition`, `PropertyDefinition` de classe, fonctions et classes ; Rust : `FunctionItem`, `StructItem`, enum, trait, type, const, static, `let`, paramètres ; Python : `FunctionDefinition`, `ClassDefinition`, affectations de premier niveau ; Go : `DefName`) — la plus proche qui précède dans la portée englobante, sinon la première ;
  2. si le nom vient d'un import (JS/TS `import { X } from`, `import X from`, Rust `use …::X`, Python `from … import X`) : le fichier résolu par `links.ts`, puis sa définition de `X` (lu par `api.fsRead`, recherche des mêmes motifs) ;
  3. sinon `code_search` avec les motifs de définition du langage (JS/TS : `\b(function\*?|class|interface|type|enum|const|let|var)\s+NAME\b` ; Rust : `\b(fn|struct|enum|trait|type|mod|const|static|macro_rules!)\s+NAME\b` ; Python : `\b(def|class)\s+NAME\b` ; Go : `\bfunc\s+(\([^)]*\)\s*)?NAME\b|\btype\s+NAME\b` ; autres : `\bNAME\b\s*[:=(]`), limité aux fichiers de la même famille de langage, la ligne cliquée exclue ; classement : même fichier, même dossier, puis le reste.

- Chaque saut passe par l'historique de la tâche 1.
