# Escouade — Spécification v1

Anciennement « Claude Code Manager » (jusqu'à la 0.1.3 pour les noms internes). Au premier lancement de la 0.1.4, ce qui existait sous les anciens noms est déplacé : dossier `~/.claude-code-manager/` → `~/.escouade/`, dossiers de l'identifiant `dev.gagnaire.claude-code-manager` → `dev.gagnaire.escouade` (WebView, taille de fenêtre), préférences `ccm.*` → `escouade.*`. La variable `CCM_DATA_DIR` reste acceptée à côté d'`ESCOUADE_DATA_DIR`. Les nouveaux agents travaillent sur des branches `escouade/` ; ceux d'avant gardent leurs branches `ccm/`. La mise à jour réapplique le nouvel identifiant aux raccourcis, dont Windows se sert pour les notifications.

Application desktop pour piloter plusieurs instances de Claude Code en local, organisées par projet.
Référence visuelle : `design/Claude Code Manager.dc.html` (source de vérité pour le look & feel).

## Stack

| Couche | Choix |
|---|---|
| Shell applicatif | Tauri 2 (Windows uniquement en v1) |
| Backend | Rust (tokio) : process `claude`, PTY (portable-pty), git (gix/CLI), watchers (notify), SQLite (rusqlite) |
| Frontend | Svelte 5 + TypeScript + Vite |
| Terminaux | xterm.js (addon WebGL) |
| Markdown | rendu incrémental en streaming + coloration syntaxique (shiki) |
| Stockage | `~/.escouade/` (config JSON + SQLite) |

## Pilotage de Claude Code

- Chat natif uniquement (pas de TUI embarqué).
- Chaque agent = un process `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages` dans le dossier du projet (ou du worktree de l'agent).
- Les demandes de permission et `AskUserQuestion` remontent via le protocole de contrôle (permission prompts « host ») et s'affichent comme cartes « Claude attend ta réponse ».
- Modèle, effort et mode de permission changeables en cours de conversation.
- **1 agent = 1 conversation.** Reprise après redémarrage via `--resume <session_id>`.

## Fenêtre

- Fenêtre sans cadre : la barre d'onglets du design sert de barre de titre (zone de drag), boutons Windows ─ ☐ ✕ à droite (à la place des pastilles macOS).
- Thème sombre du design, teinté par la couleur du projet actif (`color-mix` sur les tokens).
- Polices Hanken Grotesk + JetBrains Mono embarquées (hors-ligne).
- Fermer la fenêtre → réduction dans le tray, les agents continuent. « Quitter » (menu tray) → arrêt propre ; au relancement, chaque agent reprend sa session.

## Barre d'onglets

- Un onglet par projet : pastille couleur, nom, point vert si un agent tourne, compteur `Δ n` (fichiers non commités, worktrees des agents inclus), pastille pulsante = nombre d'agents en attente.
- `+` ouvre la modale « Nouveau projet ». Onglet « Stats » à droite.
- Défauts : onglets réordonnables par glisser ; clic droit → renommer, couleur, worktree par agent, « Réglages du projet… » (onglet « Projets » des réglages), ouvrir le dossier, fermer le projet (retire de l'app, ne touche pas au disque).

## Modale « Nouveau projet »

Dossier (+ Parcourir…), détection git (sinon `git init`), nom, aperçu d'onglet, 14 couleurs, bascule « Créer un premier agent » (+ modèle), bascule « Un worktree git par agent ».

## Barre latérale projet

- **Agents** : compteur, « + Nouvel agent ». Carte : statut (Prêt / En cours / Question / Terminé), nom, modèle · durée active, tokens · coût · nb fichiers ; pour l'agent d'un ticket, « ▸ ATL-42 · boucle 2/5 » (« · à tester » une fois le ticket à tester : voir *Kanban*).
- Nom créé en `agent-N`, puis renommé automatiquement en slug par Haiku après le premier message. Renommable (double-clic).
- Clic droit : Renommer, Archiver (historique du projet, réouvrable), Préparer le lancement (agent à worktree, pas tant que son ticket est « En cours » : voir *Kanban*), Ouvrir dans l'éditeur, Supprimer (arrête le process, supprime le worktree après confirmation si non mergé).
- **Remote control** (clic droit, par agent, désactivé par défaut) : la session de l'agent devient accessible depuis claude.ai et l'app Claude mobile, sous le nom « projet · agent » (requête de contrôle `remote_control`). Son process reste lancé (démarré avec l'app, jamais arrêté pour inactivité) et retrouve la même session distante après un redémarrage (`reattach_session_id`, `keep_session_on_exit`), donc le lien reste valable. Les messages envoyés depuis claude.ai s'affichent dans l'app (« depuis claude.ai ») grâce à `--replay-user-messages` ; l'écho des messages envoyés depuis l'app est écarté par son uuid. Icône sur la carte (connecté / en attente) ; clic droit : Ouvrir sur claude.ai, Copier le lien. Archiver ou supprimer l'agent met fin à sa session distante.
- **Lancement** (entre Agents et Terminaux) : les commandes qui lancent le projet, configurées dans l'onglet « Projets » des réglages, qu'ouvrent le ⚙ de la section et « Réglages du projet… » au clic droit sur l'onglet (nom, ligne de commande, shell parmi ceux détectés, sous-dossier optionnel ; enregistrées avec le projet). Chacune tourne dans son propre terminal ConPTY (`pwsh -Command …`, `bash --login -c …`, `wsl -- bash -lc …`), sans saisie : un clic sur la commande affiche son log dans la zone principale (xterm.js en lecture seule, gardé d'un lancement à l'autre avec un séparateur « relancé à HH:MM »). Statut en direct : prêt, en cours, arrêté (stoppé depuis l'app), terminé (code 0), planté (code N, avec une notification). Lancer ▶, relancer ⟳, stopper ■ (arrête aussi les programmes lancés par la commande), « Tout lancer » / « Tout arrêter ». Fermer le projet arrête ses commandes ; elles ne survivent pas à un redémarrage.
- **Terminaux** : menu `+` → PowerShell 7 (cherché dans le PATH, Program Files et l'alias du Microsoft Store ; à défaut, Windows PowerShell 5.1), Git Bash, WSL (Ubuntu). Vrai terminal (ConPTY via portable-pty + xterm.js WebGL) : autocomplétion native du shell (Tab / PSReadLine / bash-completion), historique, Ctrl+R, couleurs ANSI, programmes plein écran (vim, less, htop), redimensionnement, copier/coller, liens cliquables, recherche. Les terminaux ne survivent pas à un redémarrage.
- **Pied** : chemin, branche (et « Parcourir » : l'éditeur sur la branche du projet), `~ modifiés / + ajoutés / − supprimés`, sélecteur de couleur.

## Conversation

- En-tête : nom, statut, projet / branche ; « ▶ Tester » (agent à worktree qui a une recette de lancement) ou « Préparer le lancement » (agent à worktree sans recette, pas tant que son ticket est « En cours ») : voir *Kanban* ; modèle, tokens, coût, « Fichiers ▸ » (ouvre le panneau), durée ; sélecteur de disposition. Quand la colonne est étroite, tokens et durée (puis coût et fichiers) s'effacent : la carte de l'agent les affiche aussi.
- **Disposition** (globale, mémorisée dans `state.json`, `Ctrl+Maj+L`) : classique (panneau des fichiers à ouvrir) ou **moitié / moitié** : conversation à gauche, à droite le panneau « Non commités » toujours visible avec, sous la liste, le diff du fichier sélectionné (premier fichier par défaut, rafraîchi pendant que l'agent édite).
- Messages : utilisateur (bulle à droite), assistant (markdown), lignes d'outils compactes **dépliables** (diff pour Edit/Write, unifié ou côte à côte selon le style choisi dans les vues de diff ; sortie pour Bash…), réflexion repliée dépliable.
- Carte question (AskUserQuestion / permission) : options en boutons, réponse libre possible dans le composer ; carte répondue grisée « → réponse ».
- Carte « Tâche terminée » : durée, tokens, coût, fichiers ; « Revoir les fichiers », « Commit… ».
- Indicateur « Claude travaille… » + bouton Stop (interrompre).
- Composer : menus déroulants ouverts vers le haut — Modèle (Fable · Opus · Sonnet · Haiku, alias CLI), Effort (Bas · Moyen · Élevé · Très élevé · Max), Mode (Auto · Demander · Plan · Édits auto · Bypass ; **Auto par défaut**) — puis Envoyer (↵), toujours sur une seule ligne : dans une colonne étroite, les libellés des menus s'effacent et Stop se réduit à ■. Bordure jaune si une question attend.
- Composer v1 : fichiers joints — images (PNG, JPEG, GIF, WebP ; 5 Mo), PDF (20 Mo), fichiers texte UTF-8 (1 Mo) — par le trombone, le collage ou le glisser-déposer (tout autre fichier est refusé avec un message), autocomplétion `@fichier`, slash commands (intégrées + `.claude/commands` + skills), messages envoyés pendant que Claude travaille : transmis tout de suite, le CLI les intègre à l'étape suivante du tour (mention « transmis pendant le tour » jusqu'à la fin du tour).

## Git & fichiers

- Panneau « Non commités » : portée « Cet agent » / « Tout le projet », attribution par worktree (ou par outils Edit/Write de l'agent hors mode worktree). Clic → diff ; bouton `</>` ou clic droit → éditeur.
- Onglet « Historique » du même panneau : git graph des 300 derniers commits de tout le dépôt (branches locales et distantes, tags, branches `ccm/…` des agents étiquetées de leur nom). La branche de l'agent (son worktree, sinon la branche courante) est mise en avant, le reste atténué. Clic sur un commit → son diff (contre le premier parent pour un merge) dans la vue diff. Rafraîchi à chaque commit, merge ou branche.
- « Voir le diff » : vue diff plein écran (unifiée / côte à côte ; choix partagé avec le volet de la disposition moitié / moitié et les diffs de la conversation, et mémorisé).
- « Commit… » / « Commit tout… », selon le réglage « Commit » du projet (groupe « Git » de l'onglet « Projets ») : « Rédigé par l'agent » (défaut) envoie à l'agent une demande de commit de ses changements (il rédige le message) ; « Direct, avec un message proposé » ouvre la modale « Commit », même sans agent : portée (« Modifications de <agent> » : son worktree, sinon ses fichiers dans le dossier du projet ; « Modifications de <projet> » : tout le dossier du projet, sans les worktrees), liste des fichiers, champ « Message » pré-rempli par Haiku (`claude -p`, diff plafonné à 60 Ko, style des 10 derniers sujets de commit du dépôt ; « Haiku rédige le message… » pendant que le champ reste éditable, « Régénérer », « Pas de proposition : <raison>. » en cas d'échec), puis « Commiter », désactivé tant que le message est vide : jamais de commit sans ce clic. Pendant le commit, le bouton dit « Commit… » et la modale ne se ferme pas ; un refus de git (un hook) s'y affiche et laisse l'index tel qu'il était. Seuls les chemins listés sont commités. Les fichiers copiés dans les worktrees ne le sont jamais : motif du réglage et ignorés par git (même forcés dans l'index), ou, dans un worktree, pris par la copie (même si l'agent ne les ignore plus). Haiku ne lit le contenu d'aucun fichier qui correspond aux motifs du réglage. Une mise à jour automatique attend la fin d'une proposition ou d'un commit.
- Mode worktree : `<projet>/.claude/worktrees/<agent>`, branche dédiée, avec les fichiers du projet ignorés par git qui correspondent aux « Fichiers copiés dans les worktrees » (`.env*` par défaut). Bouton « Merger dans <branche> » (merge ou squash) ; suppression de l'agent → nettoyage worktree + branche.
- Préparation des worktrees (onglet « Projets » des réglages) : des commandes (shell, ligne de commande, sous-dossier du worktree) lancées sans fenêtre, l'une après l'autre, dans chaque nouveau worktree (agent créé par l'utilisateur ou par un ticket, worktree recréé à la restauration), avec `ESCOUADE_PROJECT_DIR`, `ESCOUADE_WORKTREE_DIR`, `ESCOUADE_BRANCH` (et les ports réservés d'un ticket) ; 20 min max chacune. Pendant ce temps l'agent montre « Préparation… » (barre latérale), « Préparation du worktree · 1/2 · npm ci » (conversation), « Prépare le worktree · … » (carte du Kanban) ; son process Claude Code ne démarre qu'une fois la préparation finie (ses hooks et serveurs MCP la trouveraient à moitié faite), et ses messages attendent. Un agent archivé ou supprimé pendant sa préparation l'arrête, et ne prend jamais le ticket qui l'attendait. La première qui échoue arrête la préparation : « La préparation du worktree a échoué sur `<commande>` (code N). » et ses dernières lignes dans la conversation, et à la suite du premier message d'un ticket ; sinon « Worktree préparé (n commandes, x s). ». Supprimer ou archiver l'agent, fermer le projet ou quitter l'app arrête la préparation et ce qu'elle a lancé. Les commandes de démontage tournent dans le worktree juste avant que l'app le supprime (agent supprimé avec son worktree, ticket validé), toutes même après un échec (5 min max chacune) ; un échec est signalé (« Agent supprimé, mais le démontage du worktree a échoué sur … ») sans empêcher la suppression. « ✦ Remplir automatiquement » : un `claude -p` (Sonnet, outils Read, Glob et Grep seulement, lecture refusée hors du projet, sans session, réglages ni MCP) lit le projet dans son dossier et propose les deux listes (dépendances avec le gestionnaire du lockfile, code généré ; démontage souvent vide), qui remplacent le brouillon ; une commande dont le dossier sort du projet est écartée.
- Restaurer un agent archivé dont le dossier du worktree a disparu (supprimé après une PR ou un push) le recrée depuis sa branche, avec les fichiers copiés et la préparation ; sans sa branche, il reste tel quel.
- Compteurs git rafraîchis par watcher de fichiers (debounce), pas par polling.
- Synchro du checkout principal du projet avec son dépôt distant : commits à tirer / à pousser par rapport à la branche suivie. Fetch en arrière-plan peu après le démarrage puis toutes les 5 min, un dépôt à la fois, sans jamais demander d'identifiants (ni fenêtre Git Credential Manager) ; échecs seulement journalisés. Pull en avance rapide uniquement (branches divergées : message clair, rebase ou merge à faire à la main), Push (une branche sans branche suivie, ou dont la branche distante a été supprimée, est publiée sur origin, ou l'unique dépôt distant), Fetch à la demande. Rien à synchroniser en HEAD détachée ou sans dépôt distant.

## Éditeur

- Mode éditeur dans la zone principale d'un projet. Points d'entrée : « `</>` Éditeur » dans l'en-tête d'un agent et « Ouvrir dans l'éditeur » au clic droit sur un agent (son worktree, ou le projet sans worktree) ; « Parcourir » sur la ligne de la branche, dans le pied de la barre latérale, et « Éditeur » dans la barre d'onglets (branche du projet) ; bouton `</>` et clic droit sur un fichier non commité ; dans la conversation, le chemin du fichier des lignes Edit / Write / MultiEdit (ouvert à la première ligne modifiée) et les fichiers listés par la carte « Tâche terminée ». Un fichier en dehors du dossier de la source ne s'ouvre pas (message). Remplace l'ouverture dans un éditeur externe.
- Choisir un agent dans la barre latérale bascule l'éditeur sur sa source ; « + Nouvel agent », un terminal, une commande de lancement, le Kanban, une notification ou `Ctrl+J` ferment l'éditeur pour montrer ce qu'ils ouvrent (ses onglets sont gardés).
- Sélecteur de source : branche du projet ou worktree d'un agent (nombre de modifications) ; onglets avec point « non enregistré ».
- Arborescence à la manière de l'explorateur de VS Code : fichiers connus de git (ignorés exclus), dossiers d'abord ; chevrons, guides d'indentation, icône colorée par type de fichier ; nom coloré et lettre M / A d'un fichier modifié ou ajouté, point coloré sur ses dossiers ; un dossier qui ne contient qu'un dossier partage sa ligne (`src/lib/editor`) ; le fichier affiché est amené à l'écran. Clavier : ↑ ↓ Début Fin, → déplie un dossier ou y entre, ← le replie ou remonte au parent, Entrée ouvre un fichier ou (dé)plie un dossier. En tête : « Nouveau fichier », « Actualiser », « Tout réduire ».
- Créer un fichier : « Nouveau fichier » (dans le dossier de la dernière ligne cliquée, sinon celui du fichier affiché) ou clic droit (« Nouveau fichier… » dans le dossier, à côté du fichier, ou à la racine sur l'espace libre ; aussi « Copier le chemin » et « Copier le chemin relatif »). Le nom se tape dans l'arbre, icône comprise ; `dossier/nom.ts` crée les dossiers. Entrée crée le fichier vide et l'ouvre, le curseur dedans ; Échap annule ; quitter le champ crée si le nom est valide (passer à une autre fenêtre ne décide rien) ; un refus du disque s'affiche sous le champ, Entrée réessaie. Refusés, avec la raison sous le champ : un nom déjà pris (casse ignorée), un chemin qui commence ou finit par `/`, `.` ou `..`, et sous Windows un nom qu'il modifierait ou réserve (`a.`, `?`, `CON`…). Un fichier ignoré par git s'ouvre, avec un message : l'arborescence ne le montre pas.
- CodeMirror 6 aux couleurs du design : coloration, recherche (Ctrl+F), indentation détectée, marques des lignes modifiées par rapport à HEAD (projet) ou à la branche de départ (worktree), compte dans le fil d'Ariane (« N lignes modifiées vs main »).
- Ctrl+S ou « Enregistrer » enregistre (fins de ligne et BOM conservés, écriture atomique). Un fichier changé sur le disque se recharge s'il n'est pas modifié ; sinon un bandeau propose « Recharger » ou « Garder ma version ». Un fichier supprimé du disque : bandeau « Ce fichier a été supprimé. » avec « Fermer » ou « Le recréer en enregistrant ». Fermer un onglet ou quitter avec des fichiers non enregistrés demande confirmation ; supprimer un agent ou fermer un projet prévient des fichiers non enregistrés qui seront perdus.

## Kanban

- Sélecteur « Agents | Kanban » en haut de la barre latérale (pastille jaune = tickets « À tester »). Le Kanban d'un projet remplace la zone principale (l'éditeur se ferme) : À faire · En cours · À tester · Terminé ; en-tête « <projet> · N tickets · k en boucle », places libres (« n places libres », « Toutes les places sont prises », ou « Quota atteint — reprise à HH:MM »), « ⚙ Après validation : … » (les réglages, sur l'onglet « Kanban » du projet) et « Pilote auto ». Sans Claude Code, « Claude Code introuvable — aucun ticket ne démarre » prend la place des places libres ; de même quand la branche cible ne peut donner aucun ticket : « <cible> n'a encore aucun commit — aucun ticket ne démarre » (dépôt neuf : son premier commit lance la file) ou « Branche cible <cible> introuvable — aucun ticket ne démarre », les cartes « À faire » disant alors « En attente de la branche cible ». Choisir un agent, un terminal ou une commande revient aux agents.
- Ticket : clé `<PRÉ>-<n>` (3 premières lettres du projet, `TIC` à défaut ; numéro jamais réutilisé), titre, description, critères (défaut : « Implémentation conforme au ticket », « Tests verts »), boucles max 3 / 5 / 8. « À faire » : clic → modification, clic droit → Modifier, Passer en tête, Supprimer. Tickets et réglages sont enregistrés avec l'état de l'app. Le premier ticket fixe la branche cible : celle du projet, même sans commit ; sur une HEAD détachée, il est refusé (« Le projet n'est sur aucune branche : choisis la branche cible dans les réglages du Kanban. »).
- Avancement : à chaque bilan, l'agent donne la liste succincte de ce qui est en place (3 à 8 éléments courts) ; le dernier bilan remplace le précédent, un bilan sans liste garde la précédente. La carte « En cours » montre les 3 derniers éléments (« +n » pour les autres), la carte « À tester » toute la liste sous « Ce qui a été fait ». La carte « Bilan des critères » de la conversation et le corps de la PR la reprennent ; elle nourrit le message de commit généré.
- Planificateur : tant que les tickets « En cours » non bloqués sont sous le maximum (1 à 6, 2 par défaut), le premier ticket « À faire » part (pilote auto) ou ceux lancés à la main (« Lancer ») ; rien ne part tant qu'un agent attend la fin de sa limite d'usage.
- Départ : un agent `<clé>-<titre>` (modèle, effort, mode du Kanban) dans un worktree `ticket/<clé>` créé depuis la branche cible, un bloc de 10 ports (depuis 4100 ; aucun quand isola gère le projet : voir *Lancement de test*), les fichiers ignorés par git copiés (`.env*` par défaut, réglable dans l'onglet « Projets » des réglages ; un fichier seulement non suivi ne l'est jamais : il apparaîtrait comme une modification à commiter), sa préparation (voir *Git & fichiers*), le protocole du ticket passé par `--append-system-prompt` (sur une ligne), puis, la préparation finie, le premier message avec les critères numérotés (suivi de l'échec de la préparation, s'il y en a un).
- Boucle : chaque fin de tour est lue (dernier bloc `escouade` du texte de l'assistant) : tous les critères atteints → « À tester » ; limite de boucles → « À tester » avec « Objectif partiel » ; sinon boucle suivante avec les critères manquants et leurs notes. Sans bilan : un rappel, puis « Bilan des critères manquant ». Stop → « Interrompu » ; erreur ou process mort → « Erreur : … » ; limite d'usage → la reprise automatique s'en charge. Un ticket bloqué libère sa place ; « Reprendre » relance son agent. Au démarrage, un tour coupé par l'arrêt de l'app est repris ; une validation coupée laisse « Validation interrompue ».
- Carte « En cours » : « Boucle n/max », critères ✓ / ○, barre de progression, derniers éléments de l'avancement, et l'activité en direct de l'agent (« Lit src/db.ts », « Lance npm test », « Réfléchit »…) ou « Question en attente de ta réponse ». Seules les cartes du Kanban montrent cette activité ; dans la barre latérale, la carte de l'agent porte « ▸ ATL-42 · boucle 2/5 ».
- Validation (« Valider et merger », « Valider + PR », « Valider et pousser », « Valider ») : refusée tant que l'agent travaille (ses fichiers seraient commités en cours d'écriture) ; arrêt des lancements de test (et aucun lancement de test ne part tant que le ticket est en validation) ; tests facultatifs (commande du Kanban, 20 min max, `ESCOUADE_PORT_BASE` défini ; en échec, le ticket repart chez son agent avec les 80 dernières lignes) ; commit des modifications restantes (message Conventional Commits généré par Haiku avec la clé, `feat: <titre> [<clé>]` à défaut ; fichiers copiés exclus) ; sans aucun commit de plus que la cible (aucune modification, ou des modifications défaites), le ticket passe « Terminé » avec « ∅ Aucune modification », sans merge, PR ni push ; refus si un fichier copié du projet y est commité (« … est commité dans la branche », « … est dans l'historique de la branche » s'il en a été retiré depuis) ; puis merge (merge commit, squash ou rebase ; dans le dossier du projet si la cible y est extraite, sinon un worktree temporaire), PR, push, ou rien. Une fois validé (merge, PR, push ou aucune modification ; réglable), le worktree est supprimé après ses commandes de démontage, et sa branche avec lui après un merge ou sans modification (poussée ou proposée, elle reste) ; s'il ne peut l'être, l'issue finit par « · worktree gardé » ; l'agent est archivé (sauf « laisser »). Conflit : me demander (« L'agent résout » / « Annuler »), l'agent résout, annuler. « Renvoyer » rend le ticket au même agent avec « Ce qui ne va pas » ; refusé lui aussi tant que l'agent travaille.
- PR : push de la branche du ticket, puis `gh pr create --repo <propriétaire>/<dépôt>` quand le dépôt distant est sur GitHub et que `gh` est installé (corps passé par l'entrée standard : description, avancement, critères en cases à cocher ; brouillon réglable) ; sans `gh` (ou s'il échoue), la page de comparaison GitHub s'ouvre dans le navigateur, titre et corps remplis, à finaliser ; autre hébergeur : push seul.
- Archiver ou supprimer l'agent d'un ticket « En cours » ou « À tester » le renvoie « À faire » ; l'archiver depuis la barre latérale demande d'abord « Archiver <agent> ? » (« Son ticket <clé> repartira « À faire ». »). Sur une carte « Terminé », « n boucles » compte toutes les boucles de son agent, renvois compris.
- Lancement de test (tout agent à worktree) : « Préparer le lancement » demande la recette à l'agent avec ses ports (pas tant que son ticket est « En cours » : son bilan la donne déjà) ; « ▶ Tester » ouvre une modale qui prépare (une fois par recette), lance chaque processus dans un terminal en lecture seule (groupe au nom de l'agent dans « Lancement »), attend qu'il réponde en HTTP (toutes les 500 ms, 3 min max) puis ouvre le navigateur sur la page de la fonctionnalité. Les lancements de test s'arrêtent à la validation, à l'archivage, à la suppression de l'agent, à la fermeture du projet, et quand l'agent donne une nouvelle recette (qui remplace l'ancienne). Quand son ticket passe « Terminé », ses terminaux de test quittent la section « Lancement », avec leurs logs (et la modale « Tester » de l'agent se ferme).
- isola (github.com/cyucelen/isola) : quand le CLI `isola` est dans le PATH (cherché au plus toutes les 30 s) et que le worktree a un `.isola.toml` (pour un ticket : committé sur la branche cible), isola lance ses services sur ses propres ports et adresses `*.localhost`. Alors : pas de bloc de ports pour un ticket (le protocole dit d'utiliser `isola up` / `isola ls --json` / `isola down` et de donner seulement `"lancement": {"ouvrir": …}`), pas de « Préparer le lancement » ; « ▶ Tester » lance `isola up` dans un terminal en lecture seule (groupe de l'agent ; entrée hors terminal, isola ne demande jamais de mot de passe), lit `isola ls --json` (les services de la branche du worktree), attend que chaque service réponde sur son propre port (le proxy d'isola répond avant lui), puis ouvre l'adresse « ouvrir » de l'agent ou celle du premier service (par le proxy) ; relancé, il revérifie tout. « Tout arrêter », la validation, l'archivage et la fermeture du projet lancent `isola down` ; la suppression du worktree, `isola destroy` (après les commandes de démontage).
- Conversation : un bloc `escouade` s'affiche comme une carte « Bilan des critères » (✓ / ○, critère, note ; puis l'avancement), suivie de « Lancement de test » s'il y a une recette.

## Intégrations (Jira, Trello, GitHub Issues)

- Comptes (onglet « Intégrations » des réglages, connectés tout de suite, hors du brouillon « Enregistrer ») : Jira Cloud (site en https, http seulement vers cette machine, e-mail, jeton d'API ; vérifié par `GET /rest/api/3/myself`), Trello (clé d'API et jeton, « Obtenir un jeton pour cette clé » ouvre la page d'autorisation ; `GET /1/members/me`), GitHub (jeton, ou vide : celui de `gh auth token`, « · via gh » ; `GET /user`). Un refus s'affiche sous le formulaire (« Jira refuse ces identifiants (401) — … »). Les secrets vivent dans `~/.escouade/integrations.json`, à part des réglages, et ne repassent jamais par la fenêtre (elle ne reçoit que « Connecté · <compte> »). Appels par le proxy des réglages ; `ESCOUADE_TRELLO_API` et `ESCOUADE_GITHUB_API` remplacent les adresses des API (tests, démo).
- Sources liées (par projet, enregistrées avec lui) : pour chaque compte connecté, un projet Jira, un tableau Trello ou un dépôt GitHub (le dépôt `origin` du projet en tête, « (dépôt du projet) »), ou « Aucun ». Choisir une source pré-remplit la correspondance : « En cours » et « À tester » → l'état qui ressemble à « en cours », « Terminé » → celui qui ressemble à « à tester », « À faire » inchangé.
- Correspondance des statuts : par colonne du Kanban et par source, l'état externe donné au ticket qui y arrive (statut Jira par sa transition, liste Trello, et pour GitHub « Ouverte », « Fermée » ou une étiquette « ◆ … » qui remplace les autres étiquettes de la correspondance) ou « — inchangé » ; par colonne, « Commenter » (défaut : « À tester » et « Terminé ») : pris par un agent (branche), prêt à tester (critères ✓ / ○, ce qui a été fait), terminé (issue de la validation et son lien), revenu « À faire ».
- Synchronisation (toute l'app) : « Mettre à jour le statut externe » (défaut : oui), « Publier un résumé à chaque boucle » (défaut : non), « Extraire les critères d'acceptation » (défaut : oui : éléments sous « Critères d'acceptation » / « Acceptance criteria » / « Definition of done », sinon les cases à cocher ; Trello : la checklist de ce nom, sinon toutes). Une synchro à la fois, dans l'ordre des changements (une file, un worker) ; un échec est journalisé et noté sur la carte (⚠ et sa raison) jusqu'à la suivante qui réussit, sans bloquer le ticket.
- Import automatique : « Importer les tickets étiquetés » (défaut : non), « Étiquette » (défaut `claude-ready`), « Vérifier toutes les » 5 / 15 / 60 min : premier passage 30 s après le démarrage, les tickets ouverts des sources liées qui portent l'étiquette arrivent dans « À faire » (5 boucles max) avec un toast « 2 tickets importés depuis Jira dans <projet> » ; un ticket déjà importé dans le projet, même supprimé depuis, n'est jamais ramené.
- « ⤓ Importer » (en-tête du Kanban, l'icône seule dans une fenêtre étroite) : sans source liée, « Aucune source liée à ce projet » et « Lier une source » ; sinon une pastille par source (nombre de tickets cochés), « ⚙ Gérer les sources », recherche (300 ms après la frappe : JQL `text ~` ou clé pour Jira, recherche GitHub, filtre local pour Trello), filtres du service (Jira : Assignés à moi, Sprint actif, À faire ; Trello : Mes cartes, une par liste ; GitHub : Assignées à moi, une par étiquette), « Tout sélectionner », ligne : clé externe, titre, type, priorité · assigné · statut, « ✓ n critères détectés » ; « Déjà dans le Kanban » grisé. Pied : boucles max 3 / 5 / 8, « Importer n tickets » → fin de « À faire », toast « 3 tickets importés depuis Jira et Trello ».
- Ticket importé : clé interne `<PRÉ>-<n>` (branche, agent), référence externe gardée ; titre externe, description (Jira : document ADF converti en markdown) suivie de « Ticket Jira ATL-1287 : <adresse> », critères extraits ou ceux par défaut. Importé une fois par projet (même service, même id ; Jira : l'id du ticket, qui reste quand il change de projet). La recherche GitHub d'un numéro (« #42 ») donne l'issue elle-même. Sa carte porte la pastille du service et la clé externe (clic : le ticket externe dans le navigateur).

- Titre : « <projet> · <agent> ». ## Réglages (⚙ barre de statut ou `Ctrl+,` → modale)

Une seule modale pour toute l'app : ses onglets à gauche (point sur un onglet modifié, version d'Escouade en bas), un onglet à la fois sous son titre et sa description. « Enregistrer » enregistre d'un coup ce qui a changé dans tous les onglets et tous les projets, chaque partie par-dessus ce que l'app a alors (le Kanban avance seul) ; refusé, avec la raison, tant qu'un projet n'a pas de nom ou qu'une commande de lancement n'a pas de nom ou de ligne de commande ; ce qui n'a pas pu être enregistré reste dans la modale. « Annuler », Échap ou × jettent tout.

- **Claude Code** : chemin de `claude`, modèle / effort / mode par défaut des nouveaux agents, reprise automatique après la limite d'usage, arrêt des process inactifs.
- **Notifications** : « Me prévenir pour » (questions et autorisations, tâches terminées, erreurs, tickets), notifications Windows, son (activé, « ▶ Tester »).
- **Projets** (sélecteur de projet, celui affiché par défaut) : nom, dossier (« Ouvrir »), couleur ; worktree par agent, fichiers copiés dans les worktrees, commandes de préparation et de démontage des worktrees (« ✦ Remplir automatiquement ») ; commandes de lancement ; « Fermer le projet… » (sa confirmation, acceptée ou non, revient aux réglages, brouillon intact).
- **Kanban** (même sélecteur) : action à la validation (branche cible, stratégie ou PR en brouillon), commande de tests et « Relancer les tests avant », suppression du worktree une fois validé, message de commit généré (avec son aperçu), conflit, pilote auto, agents en parallèle et leurs modèle / effort / mode.
- **Intégrations** (même sélecteur) : comptes Jira, Trello, GitHub, sources liées au projet, correspondance des statuts, synchronisation et import automatique (voir *Intégrations*).
- **Terminaux** : PowerShell 7, Git Bash, distribution WSL (bash sur macOS), shells détectés.
- **Réseau** : proxy et certificats (ci-dessous).
- **À propos** : version, « Rechercher une mise à jour », données locales.
- Raccourcis : « ⚙ Après validation » du Kanban (onglet Kanban de son projet) ; ⚙ et « Configurer » de la section Lancement (onglet Projets, sur ses commandes de lancement), « Réglages du projet… » au clic droit sur un onglet (onglet Projets de ce projet). Chaque onglet, et chaque projet, s'affiche depuis son début.

- **Proxy réseau** : URL HTTP(S) (avec identifiants éventuels) + exclusions `NO_PROXY`. Injecté dans les process `claude` (`HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY`), les appels de quotas, ceux des intégrations et le vérificateur de mises à jour ; option pour l'exporter aussi dans les terminaux intégrés.
- **Certificats** : les requêtes de l'app (intégrations, quotas, mises à jour) font confiance aux autorités habituelles et à celles du magasin du système (le certificat d'un proxy d'entreprise qui y est installé) ; Claude Code garde sa propre liste. « Ignorer la vérification des certificats TLS » (désactivé par défaut), pour un proxy qui déchiffre le trafic avec un certificat que le système ne reconnaît pas (« UnknownIssuer ») : plus aucun certificat vérifié pour les intégrations, les quotas, les mises à jour, ni les process `claude` (`NODE_TLS_REJECT_UNAUTHORIZED=0`, au prochain démarrage de leur process, hérité par les commandes que lancent les agents) ; les terminaux et les commandes des worktrees ne sont pas concernés. Les mises à jour sont donc vérifiées et installées par le backend (le plugin de mise à jour ne lit ce réglage qu'à la compilation), avec les réglages réseau du moment.
- Les coûts enregistrés viennent directement de Claude Code (`costUSD` par modèle). La grille de `pricing.rs` ne sert qu'à l'estimation en cours de tour ; un modèle absent de la grille n'a simplement pas d'estimation.

## Livraison

- UI en français.
- Installeur Windows (NSIS) + auto-update via GitHub Releases (`guillaume-gagnaire/escouade`). L'app cherche une nouvelle version 8 s après son lancement puis toutes les 5 minutes, sans rien dire en cas d'échec ; « Rechercher une mise à jour » dans les réglages vérifie à la demande.
- CI/CD GitHub Actions :
  - `ci.yml` (push / PR) : lint + typecheck + tests frontend, `cargo fmt --check`, `clippy`, `cargo test`, build de vérification.
  - `release.yml` (tag `v*`) : `tauri-action` → build Windows, signature des artefacts de mise à jour (secret `TAURI_SIGNING_PRIVATE_KEY`), publication de la release GitHub avec l'installeur et `latest.json` consommé par l'updater.
- Commits atomiques sur `main`, sans push.
