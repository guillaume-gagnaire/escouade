## Claude Code (stream-json)

Les sections qui suivent, jusqu'à « Codex app-server », sont celles de Claude Code. Le protocole de base est validé empiriquement sur Claude Code 2.1.283 (types de référence : `@anthropic-ai/claude-agent-sdk` 0.3.283, `sdk.d.ts` / `sdk-tools.d.ts`). Les ajouts de la 1.7 l'ont été sur des versions plus récentes, dites à chaque section : 2.1.289 pour les comptes et la copie d'un agent, 2.1.296 pour le serveur MCP et l'avancée d'un plan.

## Lancement d'un agent

```
claude --output-format stream-json --verbose --input-format stream-json
       --permission-prompt-tool stdio --include-partial-messages
       --permission-mode <auto|plan|acceptEdits|bypassPermissions>
       --model <fable|opus|sonnet|haiku> --effort <low|medium|high|xhigh|max>
       [--resume=<session_id> [--fork-session [--resume-session-at=<uuid>]]]
       [--allow-dangerously-skip-permissions]
       --add-dir=<données>/attachments/<agent> [--add-dir=<dossier du ticket>/files]
       [--mcp-config <fichier> | --settings <dossier de données>/mcp-refused.json --disallowedTools mcp__escouade]
```

L'environnement du process est celui de l'app, plus les variables des réglages réseau (`HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY`, `NODE_TLS_REJECT_UNAUTHORIZED`) et, pour un compte autre que Principal, `CLAUDE_CONFIG_DIR=<dossier du compte>` (voir « Comptes Claude ») et, tant que le réglage « Les agents tiennent une liste de tâches » est actif, `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` (voir « Avancée : ce que le flux dit »). `--mcp-config`, ou `--settings` et `--disallowedTools`, sont donnés à la fin, selon l'interrupteur « Les agents peuvent piloter Escouade » et le serveur (voir « Les agents d'Escouade »).

`--add-dir=<dossier>` (ESC-95) rend un dossier lisible sans demander. Escouade ne l'écrit que sous la forme avec `=` : `<données>/attachments/<id de l'agent>` à chaque lancement, flux comme vue Claude Code (le dossier est créé avant), et, pour l'agent d'un ticket qui a des fichiers, `<dossier du ticket>/files` (`<données>/tickets/<id>/files`) en plus (le dossier n'est pas créé pour un ticket sans fichier : pas d'argument). Voir « Fichiers joints ». Sous WSL, le dossier est donné en chemin Linux : `--add-dir` est dans `PATH_OPTIONS` (`engine/program.rs`), la liste des options dont la valeur est un chemin que le `claude` de WSL doit lire (`--mcp-config`, `--settings`, `--add-dir`), traduit comme celui d'un fichier d'Escouade (`/mnt/c/…`), que l'option soit écrite `--add-dir=<dossier>` ou `--add-dir <dossier>` (les deux formes sont traduites, par un test ; seule la première est émise). Un `claude` du système reçoit le dossier tel quel.

Une ligne JSON par message, dans les deux sens (stdin / stdout).

`--resume=<id> --fork-session` (copie d'un agent, vérifié sur 2.1.289 avec `--input-format stream-json`) : la conversation reprise continue sous un nouveau `session_id` (les événements d'un hook `SessionStart`, s'il y en a, le portent dès le démarrage, avec la source `fork`), et le fichier de la session d'origine n'est pas touché, alors qu'un `--resume` simple y ajoute des lignes dès le démarrage. La nouvelle session n'est écrite qu'au premier message : tant qu'aucun `system/init` n'est venu, il faut forker de nouveau. Une session d'origine introuvable échoue comme un `--resume` (« No conversation found with session ID »).

`--resume-session-at=<uuid>` (option cachée, absente de `--help`, vérifiée sur 2.1.289) ne garde de la session reprise que les messages jusqu'à l'entrée `<uuid>` incluse (« any chain-entry UUID, typically the kept turn's last entry »). Le binaire la dit « ignorée hors du mode print », mais nos lancements stream-json sans `-p` y sont : forkée à l'entrée du premier de deux tours, la session ne contient plus que ce tour (`export_conversation`, une requête de contrôle sans paramètre, rend son texte sans appel au modèle). L'`uuid` d'une frame `assistant` du fil principal est celle de son entrée dans le transcript (le CLI la recopie de son message), sauf pour les messages qu'il fabrique (`is_meta`) ; de même pour une frame `user` qui porte un `tool_result` et pour `system/compact_boundary`. Escouade garde comme point de copie la dernière entrée d'assistant ou de résultat d'outil du fil principal (le résultat d'un outil termine un tour interrompu ou en erreur avant toute réponse). Une entrée introuvable fait échouer le démarrage (« No message found with message.uuid of: <uuid> », code 1) : la copie forke alors la session entière.

Compaction : la chaîne repart de l'entrée `compact_boundary` (`parentUuid: null`). Forkée à une entrée d'avant la frontière, la session est refusée comme ci-dessus ; à la frontière ou au résumé qui la suit, elle est acceptée mais ne garde que ces entrées-là (`export_conversation` ne rend aucun message), et à une entrée d'après, elle garde le résumé et ce qui suit jusqu'à elle (vérifié sur une session faite à la main). Escouade oublie donc son point de copie à chaque `compact_boundary`, jusqu'à la prochaine entrée. Limite connue : si l'original compacte après la copie et que la copie redémarre avant son premier tour, son point de copie n'est plus dans la session, et elle reprend celle-ci entière, telle qu'elle est alors (avec l'avis « Point de copie introuvable… »).

## Hôte → CLI

- Message utilisateur :
  `{"type":"user","message":{"role":"user","content":<string|blocks>},"parent_tool_use_id":null,"uuid"?,"priority"?:"now"|"next"|"later"}`
  - `content` peut contenir des blocs `image` (base64) et `document` (`"title":<nom>` ; PDF : `"source":{"type":"base64","media_type":"application/pdf","data":…}`, texte : `"source":{"type":"text","media_type":"text/plain","data":<texte>}`) ; `priority` gère la file d'attente pendant un tour en cours.
  - Un fichier que l'API ne lit pas dans le message (ESC-95) n'est pas un bloc : c'est du texte, une ligne de plus à la fin du texte du message, donc à la fin du bloc `text` quand il y a aussi des blocs `image` ou `document`, ou de la chaîne `content` sinon (voir « Fichiers joints »).
- Requête de contrôle : `{"type":"control_request","request_id":"req_N","request":{"subtype":...}}`
  - `initialize` → réponse : `commands` (slash commands + skills), `models`, `account`.
    - `models` : `[{value, resolvedModel, displayName, description, supportsEffort…}]`, l'alias ou l'id et le modèle qu'il lance (2.1.284 : `opus` → `claude-opus-5-5`, `sonnet` → `claude-sonnet-5-5`, `haiku` → `claude-haiku-4-5-20251001`). Fable n'y figure que par ses ids complets (`claude-fable-5-1`, `claude-fable-5`…), mais `--model fable` lance bien le plus récent.
    - Ce que prend chaque modèle (ESC-121) : `supportsAutoMode: true` pour un modèle qui prend le mode `auto`, **absent** sinon ; `supportsEffort` et `supportedEffortLevels` (ses efforts), `supportsAdaptiveThinking`, `supportsFastMode` (absent : non), et depuis la 2.1.302 `supportsThinkingOff`. Escouade garde `supportsAutoMode` de chaque modèle annoncé, par compte, avec la version du `claude` qui l'a dit (`PersistedState::account_models`, lu à chaque démarrage de process) : le Composer, les tickets et la passation le suivent (`Core::takes_auto`, `modelTakes`) ; la règle en dur (`supports_auto` : tout sauf un Haiku plus ancien que 5, l'alias `haiku` compris) ne sert qu'avant la première réponse du compte, ou pour un modèle qu'il ne liste pas. Une liste où aucun modèle n'a le champ ne dit rien : la règle décide.
    - La liste des modèles d'un compte (ESC-124) : Escouade prend `models` tel quel pour le menu « Modèle » des agents du compte, dans son ordre, sous son `displayName`, avec `supportedEffortLevels` quand `supportsEffort` est vrai (aucun effort sinon, Haiku 4.5) et `supportsAutoMode` ; l'entrée `default` (le choix de Claude Code, « Default (recommended) ») n'est pas un modèle du menu, mais marque celui qu'elle fait tourner (même `resolvedModel`) comme modèle par défaut du compte. Un modèle que le compte a en plus y apparaît, un modèle qu'il n'a pas disparaît. Une liste sans aucun `displayName` (gardée avant ESC-124) ne fait pas de menu : la liste figée sert. Lue aussi sans agent : `claude` lancé avec le `CLAUDE_CONFIG_DIR` du compte et les options du flux, plus `--no-session-persistence --strict-mcp-config`, ne reçoit que `initialize` puis est arrêté (aucun tour, aucun appel à l'API, aucune session écrite ; environ 7 s sur ce poste). Essai réel du 2026-10-18 sur le Principal (2.1.302) : les 13 entrées listées (`default`, `opus`, `fable`, `sonnet`, `haiku`, puis les ids `claude-haiku-4-5-20251001`, `claude-sonnet-5`, `claude-opus-5`, `claude-fable-5`, `claude-opus-4-8`, `claude-opus-4-7`, `claude-opus-4-6`, `claude-sonnet-4-6`) sont celles du `/model` de Claude Code ; Haiku 5.5 y prend un effort (`low` à `max`).
    - Essai du 2026-10-18 (Claude Code natif sous Windows, versions jetables par `npm install @anthropic-ai/claude-code@<version>` dans `%TEMP%`, compte Principal ; `initialize` seul, sans appel à l'API, puis `claude -p --model <m> --permission-mode auto` qui doit écrire un fichier, en flux JSON, quelques dixièmes de centime chacun) :
      - **2.1.302** : `haiku` → `claude-haiku-5-5`, `supportsAutoMode: true` (et un effort de `low` à `max`) ; `system/init` dit `permissionMode: "auto"`, le fichier est écrit sans demande. `claude-haiku-4-5-20251001` est listé à part, sans `supportsAutoMode` : `--model claude-haiku-4-5 --permission-mode auto` part en `permissionMode: "default"` et l'écriture est refusée (`permission_denials`), sans erreur ni avertissement.
      - **2.1.283 et 2.1.292** : `haiku` → `claude-haiku-4-5-20251001`, sans `supportsAutoMode` ; `--model haiku --permission-mode auto` part en `default`. Mais `--model claude-haiku-5-5 --permission-mode auto` part bien en `auto` sur la 2.1.283 (avec `[claude-code:unrecognized_model]` sur stderr) : le mode suit le modèle, pas la version ; c'est l'alias qui change.
      - **2.1.293** à 2.1.301 : `haiku` → `claude-haiku-5-5`, en `auto`. L'alias passe à Haiku 5.5 avec la 2.1.293.
      - Modèles vus sur ce poste (2.1.302) : `default` et `opus` (Opus 5.5), `fable` (Fable 5.1), `sonnet` (Sonnet 5.5), `haiku` (Haiku 5.5), puis les ids `claude-haiku-4-5-20251001`, `claude-sonnet-5`, `claude-opus-5`, `claude-fable-5`, `claude-opus-4-8`, `claude-opus-4-7`, `claude-opus-4-6`, `claude-sonnet-4-6` ; tous en `supportsAutoMode` sauf Haiku 4.5. La réponse dit aussi `claude_code_version` depuis la 2.1.302 (Escouade lit la version par `--version`).
  - `interrupt` (`cancel_queued?: bool`).
  - `set_model` `{model}` · `set_permission_mode` `{mode}` · `apply_flag_settings` `{settings:{effortLevel}}`.
  - `get_usage` `{skip_behaviors:true}` → `rate_limits.five_hour/seven_day.{utilization (0-100), resets_at}`, `subscription_type`, coût de session.
  - `file_suggestions` `{query}` → `{suggestions, cwd}` (autocomplétion `@`).
  - `rename_session` `{title, source:"host"}` : change bien le titre de la session distante sur claude.ai quand le remote control est allumé (« Session title updated successfully », vérifié sur Claude Code 2.1.300 et 2.1.301).
  - `remote_control` `{enabled, name?, keep_session_on_exit?, reattach_session_id?}` : le remote control du flux. `enabled:true` avec `name` (« projet · agent ») ouvre la session distante ; la réponse donne `session_url` (le lien claude.ai) et `bridge_session_id`, et des frames `system/bridge_state` disent l'état du lien. Escouade l'ouvre avec `keep_session_on_exit:true` pour pouvoir la rattacher après un redémarrage (`reattach_session_id`, le même `bridge_session_id`, donc le même lien). **Fermer la session** : `enabled:false` n'archive pas une session ouverte avec `keep_session_on_exit` (« skipArchive » : elle restait orpheline sur claude.ai). Escouade envoie donc `enabled:false`, puis `enabled:true` avec `reattach_session_id` et `keep_session_on_exit:false`, puis `enabled:false` (« Archive … status=200 »). Une seconde requête `enabled:true` alors que c'est déjà allumé ne change rien. Escouade garde le `bridge_session_id` de l'agent tant que cette séquence n'a pas réussi en entier ; sans process vivant lié à claude.ai (juste après le démarrage, après un lien raté, process mort), rien ne peut l'envoyer : le prochain démarrage d'un process de l'agent ferme la session, ou la reprend (`reattach_session_id`, même lien) si le remote control est revenu. Ce qui ouvre le lien et ce qui ferme la session passent l'un après l'autre, par agent.
  - `get_context_usage`, `cancel_async_message`…
  - `stop_task` `{task_id}` → `{}` : arrête une tâche en cours, un sous-agent compris. « Arrêter » d'un sous-agent en arrière-plan s'en sert (mesuré sur 2.1.300 : voir « Un sous-agent, sa conversation et son arrêt »).
  - `send_task_message` (écrire à une tâche) est dans les listes de sous-types du binaire, mais 2.1.300 le refuse ; `get_task_output` ne sert que pour une commande ou une surveillance, pas pour un sous-agent (mesuré, même section). Escouade n'utilise ni l'un ni l'autre.
- Réponse à une requête du CLI :
  `{"type":"control_response","response":{"subtype":"success","request_id":<id du CLI>,"response":<payload>}}`

## Répondre à `can_use_tool`

- Autoriser : `{"behavior":"allow","updatedInput":<input>,"toolUseID":<tool_use_id>}` ; « toujours » : ajouter `updatedPermissions` (reprendre `permission_suggestions`).
- Refuser : `{"behavior":"deny","message":"…","toolUseID":…}`.
- **AskUserQuestion** : `allow` avec `updatedInput = {...input, answers: {"<question>": "<label>"}}` (multi-select : labels séparés par des virgules ; réponse libre = texte saisi).
- **`Read` d'un fichier joint par son origine** (ESC-95) : Escouade répond `allow` d'elle-même, sans carte, quand le `file_path` de l'`input` est exactement un fichier accordé à l'agent (comparaison normalisée, voir « Fichiers joints ») ; `Read` seulement, jamais `Edit` ni un autre outil. Si le process ne prend plus la réponse, la demande suit son cours (carte).

## Fichiers joints (ESC-95)

Ce que l'API de Claude lit dans le message y reste, en blocs `image` ou `document` : image PNG, JPEG, GIF ou WebP (5 Mo), PDF (18 Mo), texte (256 Ko), 18 Mo en tout. Tout autre fichier, ou un fichier lisible mais trop gros, n'est pas dans le message : Escouade en donne le chemin à Claude, qui le lit avec ses outils. Trois choses en découlent : la ligne ajoutée au message, ce que Claude Code a le droit de lire sans demander, et ce qu'il demande pour le reste.

- **La ligne.** Le texte du message, une ligne vide, puis une ligne par fichier : `Fichier joint : <nom>, <chemin>` (`Attached file: <nom>, <chemin>` selon « Langue des textes rédigés par Claude »). Sans texte, les lignes seules. Un saut de ligne dans le nom ou le chemin devient une espace : une ligne par fichier, jamais deux. Le `<chemin>` est celui que lit le `claude` de l'agent : celui de Windows, ou `/mnt/c/…` sous WSL ; le backend le recalcule (`Program::file_path`) au lieu de croire celui de la fenêtre. La conversation d'Escouade montre le message complet, lignes comprises. Au premier message d'un agent de ticket (aussi à « Reprendre », quand l'agent ne l'a jamais reçu), les lignes sont à la fin, après les critères et la ligne de boucle (« Boucle 1/N… »), puis, pour un fichier que la purge a effacé, une phrase (« Fichier absent du dossier du ticket, non joint : <nom>. », au pluriel « Fichiers absents du dossier du ticket, non joints : … » ; `Files missing from the ticket’s folder, not attached: …` en anglais) ; seule la note d'un échec de préparation du worktree, s'il y en a un, vient après.
- **Une copie** (`<données>/attachments/<agent>/<uniq>/<nom>`, hors du dépôt, `<uniq>` = 8 caractères hexadécimaux au hasard) est dans le dossier de `--add-dir` : Claude Code est censé la lire sans demander (voir plus bas ce qui n'est pas vérifié). Un ticket garde les siennes dans `<dossier du ticket>/files/<uniq>/<nom>`, que l'agent du ticket reçoit aussi par `--add-dir` quand le ticket a des fichiers.
- **Un fichier d'origine** (réglage « Joindre le fichier d'origine », activé par défaut) n'est pas copié : il est hors de tous les dossiers donnés par `--add-dir`, dont Escouade ne peut pas connaître le bon au lancement. Claude Code le demande donc par une requête `can_use_tool` de `Read`. Au moment de l'envoi, Escouade revérifie le fichier (un chemin que le pont a rendu, absolu, sans caractère de contrôle, le fichier existe, c'est un fichier ordinaire, il est lisible, sous le plafond de « Taille maximale d'un fichier joint ») et l'accorde à l'agent, avant son tour (`AgentMeta.granted_files`, le chemin tel que son `claude` le lit, enregistré avec lui ; les 200 derniers, `MAX_GRANTED_FILES`) ; elle répond ensuite `{"behavior":"allow","updatedInput":<input>,"toolUseID":<tool_use_id>}` à la demande de `Read` dont le `input.file_path` est exactement l'un de ces fichiers. « Exactement » : les séparateurs (`\` ou `/`), un préfixe `\\?\` et, pour un chemin Windows (une lettre de lecteur, un partage `\\serveur\…` ou `/mnt/c/…` sous WSL), la casse ne comptent pas ; rien n'est lu sur le disque et aucun `..` n'est résolu (un chemin détourné vers le fichier n'est pas ce fichier). Rien d'autre n'est autorisé ainsi : ni un autre chemin, ni son dossier, ni un autre outil (`Edit`, `Write`, `Bash`…), jamais une écriture ; les autres demandes suivent leur cours (carte, sous-agent, mode de permission), donc aussi celles d'un modèle qui ouvrirait le fichier par un autre outil que `Read`.
- **Le chemin d'origine** est lu par l'application elle-même : la WebView ne donne pas le chemin d'un `File` (le glisser-déposer natif de Tauri est coupé), et la fenêtre ne tient qu'un identifiant, sans pouvoir en fournir un autre. Windows seulement, WebView2 : la page envoie à l'hôte `postMessageWithAdditionalObjects('{"escouadeFileOrigin":"<id>"}', [file])` ; un second gestionnaire de `WebMessageReceived` (ajouté à celui de wry : Tauri reçoit aussi le message et le laisse tomber, avec un `console.error` dans la page pour seule réaction) lit `AdditionalObjects` puis `ICoreWebView2File::Path` et garde ce chemin sous l'identifiant ; la commande `file_origin(id)` attend ce chemin (2 s au plus) et dit si le fichier en a un. `attach_origin(owner, id)` retrouve ensuite le chemin par l'identifiant, jamais par un chemin que la fenêtre donnerait. Un chemin que le pont n'a jamais rendu est refusé, à l'attache comme à l'envoi du message ; un fichier du dossier de données d'Escouade ne se joint jamais par son chemin : il est refusé. Vérifié sur la vraie app : un fichier du disque, déposé ou collé depuis l'Explorateur, donne son chemin ; un `File` en mémoire (une capture collée) n'en donne pas, WebView2 refusant le message dans la page même : copie. Sous Linux et macOS : aucun chemin d'origine, copie. Sans chemin connu : copie.
- **Le terminal copie toujours.** Le process de la vue Claude Code est lancé une fois, avec les `--add-dir` de ce moment-là : on ne peut pas lui ajouter ensuite un dossier lisible, et seul celui de l'agent l'est sans demander. Le terminal copie donc le fichier (collé ou déposé) dans le dossier de l'agent puis tape son chemin (voir « Vue Claude Code »). De même, un ticket copie toujours : l'agent lit ses fichiers plus tard, quand l'original peut avoir bougé ou disparu.
- **Vérifié sur le vrai Claude Code** (2.1.301, essai réel du 2026-10-16 : un `claude -p` Haiku en flux JSON avec `--permission-prompt-tool stdio`, `--permission-mode default`, `--tools Read`, `--setting-sources ""`, `--add-dir=<dossier>`, un tour, environ 0,002 $) : un fichier sous le dossier donné par `--add-dir=` (forme avec `=`) est lu sans aucune demande ; un fichier hors de ce dossier arrive en `can_use_tool` (`Read`) dont `input.file_path` est exactement le chemin écrit dans le message (mêmes séparateurs `\`, même casse) : c'est ce que compare l'autorisation d'Escouade pour un fichier d'origine.
- **Non vérifié sur un vrai Claude Code** : le chemin `/mnt/c/…` donné par `--add-dir` sous WSL (seule la traduction est testée, avec un `wsl::Program` fabriqué), la forme séparée `--add-dir <dossier>` (Escouade ne l'émet pas), et ce que le modèle fait d'un fichier de format quelconque (archive, tableur, vidéo…) dont on lui donne le chemin ; les essais automatiques de bout en bout utilisent le faux `claude` (`tests/fixtures/fake-claude.mjs`, qui lit les lignes « Fichier joint » avec `Read` et demande la permission hors des dossiers `--add-dir`).

## Transcripts

`<dossier de config du compte>/projects/<cwd encodé>/<session_id>.jsonl` (`~/.claude/` pour Principal, `CLAUDE_CONFIG_DIR` pour un autre compte) — pas de titre généré en mode `-p` ; l'app tient son propre journal de conversation normalisé.

## Comptes Claude (`CLAUDE_CONFIG_DIR`)

Un compte est un dossier de config de Claude Code : `CLAUDE_CONFIG_DIR` (défaut `~/.claude`) en contient la configuration, la connexion et les transcripts. Essais du 2026-10-10 sur Claude Code 2.1.289, dossiers jetables :

- **Principal se lance sans toucher à `CLAUDE_CONFIG_DIR`**, même vers `~/.claude` : sous macOS, le nom du service du trousseau en dépend. Lu dans le binaire : `Claude Code-credentials` quand la variable n'est pas définie, `Claude Code-credentials-<h>` sinon, `<h>` étant les 8 premiers caractères hexadécimaux du SHA-256 de la valeur normalisée en NFC (`CLAUDE_SECURESTORAGE_CONFIG_DIR`, s'il est défini, prend le pas) ; le trousseau passe avant le fichier. Définir la variable changerait donc l'entrée lue et déconnecterait l'utilisateur ; un autre compte reçoit exactement la chaîne dont Escouade calcule le hachage. Chaque dossier a sa connexion : les comptes multiples marchent sous macOS.
- Sous Windows (et hors macOS), la connexion est `<dossier>/.credentials.json` (`claudeAiOauth.accessToken`, `expiresAt`). Un drapeau distant, `tengu_windows_credman`, pourrait la faire passer au Gestionnaire d'identification avec les mêmes noms : hors périmètre. L'e-mail du compte est `oauthAccount.emailAddress` du `.claude.json`, qui est `<dossier>/.claude.json` quand la variable est définie, sinon `~/.claude.json` (à côté de `~/.claude/`, pas dedans).
- **Reprise dans un autre dossier** : un transcript `projects/<cwd encodé>/<id>.jsonl` copié dans le `CLAUDE_CONFIG_DIR` d'un autre compte est trouvé par `claude -p --resume <id>` lancé depuis le même dossier de travail (sans connexion, le refus porte sur elle : « Not logged in » ; un identifiant inconnu donne « No conversation found with session ID »). Escouade copie `projects/*/<id>.jsonl` et le dossier voisin `<id>/` (sous-agents, résultats d'outils), pas `file-history/`, `todos/` ni `session-env/`, après avoir arrêté le process de l'agent. **Non vérifié avec un second compte réel** : que l'API accepte une conversation commencée sur un autre compte (blocs de réflexion signés) ; un refus arrive comme un `result` en erreur au premier tour.
- Quota d'un compte : `get_usage` sur un process vivant du compte, sinon l'endpoint de `/usage` avec le jeton OAuth de sa connexion (voir « CLI → hôte » pour `rate_limit_event`).

### Connexion qui ne se rafraîchit pas (lu dans le binaire 2.1.309, ESC-162)

« Failed to authenticate: OAuth session expired and could not be refreshed » est le texte de l'erreur `OAuthRefreshDeadError` (« OAuth refresh token is no longer valid »). Claude Code la lève quand il n'a pas de jeton d'accès utilisable et que son jeton de rafraîchissement est connu pour mort.

- **Le rafraîchissement.** Il passe par un verrou du dossier du compte (`<dossier>/.oauth_refresh.lock`, périmé après 60 s). Pendant l'attente, Claude Code fait 5 essais espacés de 1 à 2 s, et prend le verrou d'un détenteur dont le processus est prouvé mort. Sous le verrou, il relit le fichier : si un autre processus a déjà écrit un autre jeton, il prend celui-là (`race_resolved`). S'il échoue, il relit encore (`race_recovered`). Un processus qui a attendu le verrou trop longtemps finit sur « Failed to refresh OAuth token: another Claude Code process is refreshing it or exited mid-refresh ».
- **Le jeton mort.** Un refus `invalid_grant` (jeton de rafraîchissement expiré, révoqué ou déjà utilisé) le met dans un ensemble en mémoire. Si le fichier le contient encore, Claude Code le vide (`accessToken`, `refreshToken` à `""`, `expiresAt` à 0), ce qu'Escouade lit comme « Pas connecté ». Le processus relit le fichier à chaque changement de sa date, et un jeton inutilisable au plus toutes les 30 s (`Mbn=30000`). Entre-temps, chacun de ses tours échoue tout de suite.
- **Essais du 2026-10-23, sur un dossier jetable** (faux jetons, jamais ceux de l'utilisateur) : `claude -p` avec un jeton expiré et un faux jeton de rafraîchissement rend exactement ce texte (`result` en erreur, `subtype: success`) et vide le fichier. Un processus stream-json à qui l'on n'envoie qu'`initialize` rafraîchit aussi au démarrage, sous le verrou : sa réponse n'arrive qu'après (5 à 8 s), si bien que l'arrêt d'une lecture des modèles juste après sa réponse ne coupe pas un rafraîchissement.
- **Le cas réel** (conversation du 2026-10-04) : un tour de 2 h 18 échoue à 09:37:59 UTC, le message suivant à 09:38:26 (27 s après), puis « continue » repart à 09:38:58. C'est le même processus, aucun lancement dans `app.log` : il a relu le disque après ses 30 s. Une bonne connexion y était donc arrivée, écrite par un autre processus du compte (Escouade en lance beaucoup : agents, `claude -p`, lecture des modèles).
- **Ce qu'Escouade en fait** (`signin.rs`). À la fin d'un tel tour, il relit la connexion du compte (`usage::read_stored`). Si le jeton est en date, ou si la connexion n'est plus celle du lancement du processus (`launch_stamp`), il arrête le processus et le relance sur sa session avec « continue », au plus deux fois (3 s puis 10 s). Sinon, l'agent attend une nouvelle connexion (`AgentMeta::sign_in`, lue toutes les 20 s). Le tour porte `signIn: true` et ne bloque pas un ticket (`TurnEnd::SignIn`). Les lancements d'un compte au jeton expiré passent un par un (`RefreshGate`) : le premier part et rafraîchit, les suivants attendent que la connexion change, 20 s au plus. Ils ne font donc pas la queue au verrou de Claude Code, qui ne patiente que 8 à 17 s.

## Avancée : ce que le flux dit

Escouade tient pour chaque agent une avancée (`AgentMeta.plan`, `src-tauri/src/plan.rs`) : sa liste de tâches, ses sous-agents, ses workflows. Elle est dérivée du flux, par un seul réducteur, que la fenêtre ne recalcule pas. Chaque forme ci-dessous est datée : « mesuré » (un vrai `claude`, sans appel à l'API : dossier de config jetable), « mesuré sur un flux réel » (un vrai `claude` 2.1.296 lancé par l'application sur un plan superpowers 6.4.1, le 2026-10-11 : voir « Ce que les flux réels ont montré » plus bas ; les enregistrements sont `tests/fixtures/real-run-*.jsonl`) ou « lu dans le binaire 2.1.296 » (schémas et code de Claude Code, pas de sa documentation : ils peuvent changer). **Rien de ce qui touche aux workflows n'a été vu sur un flux réel** : le support repose sur ces schémas et sur les scénarios du faux `claude` des tests.

### Les outils de liste de tâches ne sont pas toujours là

Deux familles. Ce qui est **mesuré** sur 2.1.296, avec les options de lancement ci-dessus : lesquelles sont dans la liste `tools` de `system/init`, selon le modèle et la variable d'environnement (plus bas). Ce qui est **lu dans le binaire 2.1.296** (pas dans sa documentation) : la forme de leurs entrées, ci-dessous, sauf `TaskCreate { subject, description }` et `TaskUpdate { taskId, status }`, que les flux réels ont confirmés (« Ce que les flux réels ont montré ») :

- `TodoWrite` `{ todos: [{ content, status: pending|in_progress|completed, activeForm }] }` : la liste entière à chaque appel, elle remplace la précédente.
- « Task v2 » : `TaskCreate { subject, description, activeForm?, metadata? }`, `TaskUpdate { taskId, status?: pending|in_progress|completed|deleted, subject?, activeForm?, addBlocks?, addBlockedBy?, owner?, metadata? }`, `TaskGet`, `TaskList` ; par défaut à la place de `TodoWrite`.

Avec les modèles actuels (`opus`, `sonnet`, `fable`, `haiku` → ids 5.x ou `claude-haiku-4-5-20251001`), **aucune des deux familles n'est dans `tools`** : un agent d'aujourd'hui n'émet aucune liste de tâches, même quand un skill lui dit d'en tenir une. Elles y sont avec `--model claude-opus-4-6` ou `claude-haiku-4-5` (mesuré), et avec la variable d'environnement `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` (mesuré : `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate` ; avec en plus `CLAUDE_CODE_ENABLE_TASKS=false`, `TodoWrite` à leur place ; variable lue dans le binaire, pas dans la documentation). Escouade la met au lancement de chaque agent (`Settings::agent_env`) tant que le réglage « Les agents tiennent une liste de tâches » est actif (`todoTools`, activé par défaut) ; désactivé, elle n'ajoute rien et ne force jamais la valeur contraire (l'environnement de l'utilisateur reste maître). Les autres lancements de `claude` (nom de l'agent, message de commit, connexion d'un compte) ne l'ont pas. Contrepartie : les outils entrent dans le prompt de chaque agent (quelques centaines de jetons). Ils sont **différés** dans Claude Code : même avec la variable, le modèle doit les charger avant de s'en servir, ce que les essais réels n'ont pas vu faire sur un plan superpowers (voir « Ce que les flux réels ont montré »).

### La liste de tâches, comme Claude Code la reconstruit lui-même (lu dans le binaire 2.1.296)

Son observateur interne ne lit que les frames `assistant` du fil principal (`parent_tool_use_id` nul). Escouade reprend ses règles :

- `TodoWrite` remplace la liste (id de chaque tâche = son rang, à partir de 1).
- `TaskCreate` ajoute une tâche en attente tout de suite ; son id n'est connu qu'au `tool_result`, dont le texte est `Task #<id> created successfully: <subject>` (regex `^Task #(\S+) created successfully`). Un `tool_result` en erreur retire la tâche.
- `TaskUpdate` agit par `taskId` : `status`, `subject`, `activeForm`, `addBlockedBy` (les tâches qu'elle attend) ; `addBlocks` dit la même dépendance de l'autre côté ; `deleted` retire la tâche ; un id inconnu crée l'entrée.
- `TaskGet` et `TaskList` ne changent rien.
- Un même appel reçu deux fois (même `tool_use_id`) compte une fois ; un `TaskCreate` quand toutes les tâches sont faites ouvre une nouvelle liste.

### Les sous-agents

L'outil s'appelle `Task` dans la liste `tools` de 2.1.296 mais ses appels arrivent sous le nom `Agent` (mesuré sur un flux réel), et `Task` dans d'autres versions : Escouade prend les deux. Entrée (lu dans le binaire) : `{ description (3-5 mots), prompt, subagent_type?, name?, run_in_background?, model?, isolation? }` ; le plan d'Escouade ne garde pas le `prompt` (il ne sert qu'à trouver la tâche d'un plan), mais la conversation le garde sur l'élément de l'appel, 16 000 octets au plus (voir « Un sous-agent, sa conversation et son arrêt »).

- **Au premier plan** : les frames `assistant` et `stream_event` du sous-agent portent `parent_tool_use_id` = l'id du `tool_use` qui l'a lancé (même pour un sous-agent de sous-agent) ; le `tool_result` du parent porte `tool_use_result` `{ status: "completed", agentId, content, totalToolUseCount, totalDurationMs, totalTokens, usage }` (lu dans le binaire).
- **En arrière-plan** (`run_in_background` ; un vrai Claude Code 2.1.296 les lance tous ainsi, même sans cette option : voir « Ce que les flux réels ont montré ») : le `tool_result` est tout de suite « Async agent launched successfully. agentId: … » (`tool_use_result.status` `async_launched`) ; la fin n'arrive que par `system/task_notification`, que Claude Code rejoue ensuite à Claude (voir `on_replay` dans `agent.rs`).

### Frames `system` sur les tâches (lu dans le binaire 2.1.296)

### Les workflows (lu dans le binaire, jamais vu sur un flux réel)

Outil `Workflow` (dans `tools`) ; sa tâche a `task_type: "local_workflow"` et un `workflow_name`. Pendant l'exécution, des `task_progress` ; la fin par `task_notification`. Escouade en fait une exécution (`WorkflowRun`) : son titre, sa phase courante (`now`), ses totaux (`usage`), son état.

### Le plan et le registre superpowers du dossier de l'agent (superpowers 6.4.1)

Pour un agent qui n'a pas de liste de tâches (réglage coupé, ancien flux, ou modèle qui n'en tient pas : voir « Ce que les flux réels ont montré ») mais qui suit un plan superpowers, Escouade lit **en lecture seule** le plan et le registre d'exécution que les skills `writing-plans`, `executing-plans` et `subagent-driven-development` laissent dans son dépôt (`src-tauri/src/planfiles.rs`). Les formes viennent des scripts et des `SKILL.md` de superpowers **6.4.1** (`sdd-workspace`, `task-brief`, `task-start`, `task-done`), pas d'une documentation : une autre version peut les changer.

**Ce qui est lu, et seulement cela.** Sous la racine du dépôt de l'agent (`git rev-parse --show-toplevel` de son dossier, sinon son dossier) :

- `.superpowers/sdd/<nom du plan>/progress.md`, le registre, le plus récent (date de modification) dont la ligne 1 est `# SDD ledger — plan: <chemin du plan>` et dont le plan existe ; les noms des fichiers `task-<id>-brief.md` du même dossier (leurs noms, jamais leur contenu) ; à défaut de chemin utilisable dans la ligne 1 (écrit depuis un autre dossier : `../…`), le fichier `plan-path` du dossier (`sdd-workspace` y écrit le chemin du plan, relatif au dépôt) ;
- le plan, que cette ligne désigne : un fichier `.md` du dépôt (chemin relatif à la racine ou absolu, avec l'une ou l'autre barre) ;
- sans registre, un plan de `docs/superpowers/plans/*.md` que l'agent a écrit ou modifié dans cette conversation (chemins des `tool_use` `Write`, `Edit` et `MultiEdit` du fil principal, et les plans qu'une commande `Bash` du fil principal **écrit** : une redirection (`cat > docs/superpowers/plans/x.md <<'EOF'`, `>>`, `2>`), `tee`, la destination d'un `cp` ou d'un `mv` ; pas un plan qu'elle lit, cherche, compte, `git add` ou copie, ni un motif, ni une variable ; cinq au plus, un même fichier une seule fois quelles que soient les barres et la casse ; seuls comptent ceux qu'une activité a touchés depuis le début de la conversation, un plan ancien n'empêche pas d'en trouver un écrit avant lui).

Jamais un autre fichier, jamais `~/.claude`. **Un chemin écrit dans ces fichiers n'est jamais interrogé au disque tant qu'il n'est pas, d'après son écriture seule, sous la racine** : un chemin absolu qui ne commence pas par celui de la racine (ou son chemin réel) est refusé sans appel au système de fichiers ; un chemin vers une autre machine ou un périphérique est refusé quelles que soient les barres (`\\hôte\partage`, `//hôte/partage`, `\/hôte/partage`, `/\hôte\partage`, `\\?\`, `\\.\`, `\??\` : Windows lit `/` et `\` comme une seule barre, donc le contrôle se fait sur le chemin aux barres unifiées), sauf si le dépôt est lui-même sur le réseau ; un nom avec `:` (flux `a.md:s`) ou de périphérique (`CON`, `NUL.md`, `COM1`…) est refusé. Les chemins que l'agent a écrits, donnés comme il écrit son dossier (lien, nom court), sont ramenés à la racine que dit git quand son dossier est le dépôt. Ensuite tout chemin passe par `paths::contained` (pas de `..`, pas de lien qui sort du dépôt) ; un dossier de travail, un registre ou un fichier de brief qui est un lien n'est pas suivi ; le plan et `plan-path` ne sont ouverts que si ce sont des fichiers ordinaires (`symlink_metadata` avant `contained` : jamais un lien, même vers un fichier du dépôt, ni un dossier, ni un tube, qu'ouvrir bloquerait la lecture). Fichiers lus au plus 256 Kio (au-delà : coupés, jamais un échec ; un registre plus gros donne ses deux bouts, la ligne 1 et les dernières lignes), hors du verrou de l'agent. Un registre ou un plan qu'aucune activité n'a touché depuis le début de la conversation de l'agent (le plus récent de `progress.md` et des briefs) n'est pas le sien : il vient d'une autre conversation ou d'un autre agent du même dépôt.

**Le plan** (`writing-plans`) : le titre est le premier `# ` hors bloc de code, sans le suffixe « Implementation Plan » (ou « plan d'implémentation ») s'il y en a un, coupé à 160 caractères ; une tâche est un en-tête `## Task <id>: <titre>` à `#### …` (`<id>` : `3`, `L1`, `3b` ; séparateur `:`, `.`, `—` ou `-`) hors des blocs de code, la première pour un même id, cent au plus ; ses étapes sont les cases `- [ ]` / `- [x]` de sa section (jusqu'à l'en-tête suivant de son niveau ou au-dessus) : `steps` = (cochées, toutes). Un plan sans en-tête de tâche donne une liste vide. BOM et fins de ligne `\r\n` sont acceptés.

**Le registre** : des lignes `Task <id>: <texte>` ; `complete` en tête du texte (y compris `complete (commits a..b, tests: … → …)`) = faite ; `dispatched`, `implementer`, `review`, `re-review` ou `fix round …` = au travail ; le reste (`Ruling`, `minor (deferred)`, `parked`, lignes libres, tableaux) n'a pas d'effet. Une ligne qui commence par `Task <id>: …` peut en dire plusieurs, après un point-virgule, un point, une flèche ou un tiret (`Task M4: complete (…); Task M3: complete (…)`, `… accepted without re-review; Task K7: complete`) : chacune compte ; une tâche nommée dans une phrase, ou une ligne qui ne commence pas par `Task`, n'est qu'une note. De deux lignes sur une même tâche, la dernière qui dit quelque chose l'emporte (un `fix round` après un `complete` la rouvre). Le script `task-brief` (et `task-start`) écrit `task-<id>-brief.md` au début de chaque tâche : une tâche qui a son brief et aucune ligne `complete` est **en cours** quand aucune ligne de travail ne dit laquelle l'est, et alors **la première** (dans l'ordre du plan) : un contrôleur qui fait tous les briefs d'avance (`task-brief` pour chaque tâche, mesuré sur un flux réel) n'a pas toutes ses tâches en cours à la fois. Les ids sont comparés tels quels.

**Précédence.** La liste de tâches de l'agent (`TodoWrite`, `TaskCreate`) l'emporte dès qu'il en a une non vide ; les fichiers donnent alors seulement le titre et le chemin du plan (`title`, `planFile`), **et seulement si une tâche de la liste de l'agent est une tâche du plan** (même titre, au mot près et sans casse ni ponctuation, ou la forme « Task 2: Titre » des todos des skills, ou un titre plus long qui contient l'autre entier, d'au moins 8 caractères) : deux agents du même dépôt lisent le même dossier, et le plan de l'un n'est pas celui de l'autre ; la fenêtre ne reçoit qu'une liste. **Pour la fenêtre : `source` dit qui a fait la liste, pas qu'elle existe.** Un `TodoWrite` vide d'un agent qui a des sous-agents laisse `source: "tools"` avec `tasks: []` : la fenêtre décide qu'il y a une liste d'après `tasks.length`, jamais d'après `source` ni d'après la présence de `planFile`. Sans liste, c'est celle des fichiers (`source: "plan"`). Une tâche donnée faite par le registre ne repasse jamais à « à faire ». Quand l'agent se met à tenir sa propre liste, celle des fichiers lui laisse la place. Une lecture qui échoue, ou qui ne trouve rien, ne change rien et ne dit rien (jamais un message dans la conversation).

**Quand relire.** Au `tool_result` d'un `Bash`, d'un sous-agent (`Task` / `Agent`), de l'écriture d'un plan ou d'un fichier de `.superpowers/sdd/` (registre, brief) par le fil principal, et à la fin de chaque tour ; au plus une fois toutes les 2 s par agent (une demande reçue pendant ce délai donne une relecture au bout), et les fichiers ne sont relus que si la date ou la taille de `progress.md` ou du plan, ou la liste des briefs, a changé.

### Ce que les flux réels ont montré (Claude Code 2.1.296, superpowers 6.4.1, 2026-10-11)

Quatre lancements de l'application sur un dépôt jetable (un agent en worktree, Sonnet, effort bas, un plan de deux tâches : `slugify`, son test) : trois avec `subagent-driven-development` et le réglage de la liste de tâches actif (le deuxième suivi d'un message qui demande `TaskCreate`), un avec `executing-plans` et le réglage coupé ; les frames de deux d'entre eux (le deuxième et le troisième) sont gardées (`tests/fixtures/real-run-subagents.jsonl`, `real-run-inline.jsonl` : sans les événements de flux, les chaînes longues coupées à 300 caractères, le nom de l'utilisateur remplacé) et rejouées par les tests de `agent.rs`. **Aucun workflow n'a été lancé** (décision du contrôleur) : ce qui touche aux workflows reste lu dans le binaire.

- **Les outils de liste de tâches** : avec `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`, `system/init` liste `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate` (avec `Task`, `TaskStop`, `Workflow`, `ToolSearch`) ; réglage coupé, les quatre en sont absents (restent `Task`, `TaskStop`, `Workflow`…). **Ils sont différés** : le modèle les charge d'abord par `ToolSearch { query: "select:TaskCreate,TaskUpdate", max_results: 2 }` ; sur les trois plans exécutés avec le réglage actif (tous avec `subagent-driven-development`), **il n'a jamais appelé ni `ToolSearch` ni `TaskCreate`** : la liste du bandeau venait des fichiers. Demandé en toutes lettres, il l'a fait : `TaskCreate { subject, description }` → `tool_result` « Task #1 created successfully: Alpha », `tool_use_result { task: { id: "1", subject } }` ; `TaskUpdate { taskId: "1", status: "in_progress" }` → « Updated task #1 status », `tool_use_result { success: true, taskId, updatedFields: ["status"], statusChange: { from, to } }`. Les formes du réducteur (`Task #<id> created successfully`, `taskId` en chaîne) étaient les bonnes. Le réglage rend donc la liste possible, pas certaine.
- **Les sous-agents** : `system/init` dit `Task`, les appels arrivent sous le nom `Agent` (`{ description, subagent_type, model, prompt }`, sans `run_in_background`) et **tous sont lancés en arrière-plan** : ordre des frames `assistant` (`tool_use`) → `system/task_started` (`run_id`, `is_backgrounded: true`, `spawn_depth: 1`, `task_type: "local_agent"`, `prompt`) → `user` (`tool_result` « Async agent launched successfully. agentId: … », `tool_use_result { isAsync: true, status: "async_launched", agentId, description, resolvedModel, prompt, outputFile, canReadOutputFile, canContinueAgent }`). Le tour du contrôleur finit là (`result`) ; les frames du sous-agent portent `parent_tool_use_id` = l'id de l'appel `Agent` ; un `system/task_progress` accompagne chaque outil qu'il utilise (`description` « Reading … », « Writing … », « Running … », `usage` cumulé, `last_tool_name`) — **sans l'option SDK `agentProgressSummaries`**, contrairement à ce qu'on lisait dans le binaire ; il rend son rapport par l'outil `SubagentHandback` ; à sa fin, au même instant, `task_updated { patch: { status: "completed", end_time } }` puis `task_notification { run_id, tool_use_id, status, output_file, summary, usage { total_tokens, tool_uses, duration_ms }, handback: "send", handback_report { text } }` et `background_tasks_changed { tasks: [] }`, après quoi Claude Code rejoue à Claude deux messages (`<agent-message from="…">[Subagent hand-back]…`, `<task-notification>…`) et ouvre un nouveau tour (`system/init` de nouveau, même `session_id`). Un sous-agent au premier plan (`tool_use_result { status: "completed", … }`) n'a pas été vu : il reste celui du faux `claude`. Un `Bash` long donne aussi un `task_started` `local_bash` (`is_backgrounded: false`) et sa `task_notification`, sans `usage` : ignorés par le réducteur à l'époque (2.1.296) ; depuis ESC-14, une commande en fond est une rangée de `bgTasks` (voir « Les tâches de fond d'un agent »), une commande au premier plan reste une ligne d'outil.
- **Le registre** : `task-brief` pour toutes les tâches d'un coup (d'où « la première » ci-dessus) ; des lignes libres (`Preflight: …`, `Ruling: …`) et plusieurs déclarations sur une ligne (`Task 1: minor (deferred): …; Task 1: complete (commits 8557575..f7e9e69, review clean)`) ; avec `executing-plans`, les scripts `task-start` / `task-done` écrivent `Task 1: complete (commits 5769021..f972361, tests: … → …)` eux-mêmes. **La fin d'un plan** : les deux skills disent « Final review clean: delete this plan's workspace » ; le contrôleur l'a fait en une seule commande avec la dernière ligne du registre : `echo "Task 2: complete (…)" >> .superpowers/sdd/<plan>/progress.md; rm -rf .superpowers/sdd/<plan>; git status --short`. Aucun regard ne voit cette ligne : **une commande du fil principal qui supprime le dossier de travail du plan suivi (`rm`, `rmdir`, `rd`, `del`, `Remove-Item` visant `.superpowers/sdd/<nom du plan>`, directement, ou par une variable que la commande définit comme exactement ce dossier, quand elle est à elle seule l'argument (avec ou sans `/` ou `/*`) ; pas un fichier de ce dossier, pas `"$W/fichier"`, pas une autre variable, pas un autre plan) met toutes les tâches d'un plan de fichiers à faites** à son `tool_result` (si la commande n'a pas échoué) ; les regards qui suivent ne trouvent plus rien et ne rouvrent rien. La liste de tâches de l'agent, elle, est la sienne.
- **Un plan sans registre** : un contrôleur peut ne pas faire de dossier de travail du tout (le plan écrit par `cat > docs/superpowers/plans/… <<'EOF'`, les sous-agents lancés avec « Read docs/superpowers/plans/…md, implement ONLY "Task 1" »). Le plan est trouvé par la commande qui l'a écrit ; ses tâches restent à faire (rien dans les fichiers ne dit où l'on en est) ; les sous-agents se voient (« ↳ Implement Task 1 slugify », liés à la tâche par leur `description`).
- **Ce que fait un sous-agent** : presque chaque commande de ses outils `Bash` commence par `cd "<le worktree>" && …` ; le « pas » dit ce que la commande lance après le `cd`.

### Ce qu'Escouade en garde

`AgentMeta.plan` (`PlanState`, voir `src/lib/types.ts`) : `tasks` (100 au plus), `agents` (30 : toutes celles qui tournent, puis les dernières terminées ; chaque rangée a, en plus de son état, de ses totaux et de ce qu'elle fait, `parent`, l'appel du sous-agent qui l'a lancée (le `parent_tool_use_id` de son appel, sinon la rangée dont la tâche est le `parent_task_id` de son `task_started`), et `taskId`, la tâche de Claude Code (le `task_id` de son `task_started`, sinon l'`agentId` du résultat de lancement), ce que « Arrêter » nomme ; tous deux envoyés à la fenêtre, comme le reste de la rangée), `launched` (tous les sous-agents lancés depuis la remise à zéro), `workflows` (10), `bgTasks` (les tâches de fond : commandes, surveillances, agents distants, coéquipiers ; toutes celles qui tournent puis les 10 dernières finies, 40 au plus ; chaque rangée a son `id` (le `task_id` de Claude Code), son `kind`, son titre, sa commande de 2 000 caractères au plus, son état, ses heures, le `summary` de Claude Code, l'appel qui l'a lancée, `parent` (la tâche du sous-agent qui l'a lancée) et `outputFile` : voir « Les tâches de fond d'un agent » et « Dans Escouade »). Hors du plan, sans l'enregistrer, l'agent garde la mémoire de ces tâches (`BgMemory`, `AgentRt::plan_memory`, gardée même quand le plan n'a rien à montrer) : les 64 derniers appels `Bash`, `PowerShell` et `Monitor` (leur commande et leur description, que les frames d'une tâche ne portent pas), et les commandes vues au premier plan (32 au plus), que le départ en fond fera lister. Le sous-agent d'une tâche (`planTask`) est celle que son `prompt` ou sa `description` nomme (`task-<id>-brief.md` ou `task-<id>-report.md`, puis `Task <id>`) si la liste l'a, sinon la seule tâche en cours. Ce que fait un sous-agent (`doing`) vient de ses propres appels d'outils, dans les mêmes mots que `activity`. Remise à zéro : une nouvelle session Claude, ou le premier message d'un tour quand le plan est fini (toutes les tâches faites, ou aucune, et rien qui tourne : ni sous-agent, ni workflow, ni tâche de fond) ; elle oublie aussi le titre et le plan des fichiers, et les fichiers du dossier ne sont relus que s'ils ont été touchés depuis. Quand le processus meurt, les rangées qui tournaient passent à `interrupted`, tâches de fond comprises ; une rangée au premier plan l'est aussi à la fin du tour, pas une tâche de fond, qui continue après le tour.

### Un sous-agent, sa conversation et son arrêt (mesuré sur Claude Code 2.1.300, 2026-10-15, ESC-13)

Essai du 2026-10-15 sur un vrai Claude Code 2.1.300 (Haiku, mode de permission `default`, compte réel, 0,01 $ environ), en stream-json. Un script a fait lancer un sous-agent en arrière-plan à l'agent (il écrit un fichier, puis lance `sleep 100 && echo done`), puis a envoyé des requêtes de contrôle : `initialize`, le message, puis, 3 s après le premier `Bash` du sous-agent, `send_task_message` et `get_task_output` sur sa tâche, et 1,5 s plus tard `stop_task`. « Mesuré » dit ce que cet essai a montré ; « lu dans le binaire » ce que le code de Claude Code dit, sans que l'essai l'ait vu.

#### Ce que la conversation garde d'un sous-agent

Le plan ne garde que 30 rangées et se remet à zéro (voir ci-dessus) : ce que la fenêtre montre d'un sous-agent ne peut pas dépendre de sa seule rangée. La conversation (`agent.rs`) garde donc :

- **Son fil** : les éléments dont `parent` est l'id de l'appel qui l'a lancé (les frames qui portent un `parent_tool_use_id`).
- **Sur l'élément de l'appel** (`Agent` ou `Task`) :
  - `input.prompt`, sa consigne, jusqu'à 16 000 **octets** (`MAX_PROMPT` ; les autres textes d'une entrée d'outil sont coupés à 4 000). `truncate` compte en octets, pas en caractères : la coupe tombe sur une frontière de caractère et ajoute « … » (3 octets de plus) ;
  - `report`, 16 000 octets au plus (`MAX_REPORT`, même coupe) : le texte du `handback_report` de la `task_notification` ou, quand le sous-agent finit **sans** `SubagentHandback` (la notification n'a pas de champ `handback`, et son état est `completed`), le `summary` de la notification, qui est alors son rapport — mesuré sur 2.1.300 (voir « Lui écrire » : la notification y a un `summary` qui est le texte final du sous-agent). Ailleurs le `summary` n'est pas un rapport : à côté d'un `handback`, il dit seulement où le rapport est allé, et celui d'une tâche arrêtée ou en échec n'est que sa description. Les versions plus anciennes de Claude Code (et le faux `claude`) donnent aussi, pour un sous-agent terminé, une ligne générique en guise de `summary`, `Agent "<titre>" finished` (ou `completed`, `failed`, `stopped`, avec ou sans point final, une seule ligne) : elle dit seulement que le sous-agent a fini, Escouade ne la garde pas (`is_generic_summary`), et le rapport d'un sous-agent au premier plan est alors le résultat de son appel (point suivant). Le rapport est rangé sur l'appel dont la rangée a pour `taskId` le `task_id` de la notification, sinon sur l'appel que nomme son `tool_use_id` ; la notification d'un sous-agent arrêté n'en a pas (voir plus bas) ;
  - le rapport d'un sous-agent **au premier plan** n'est pas ce `report` : c'est le texte du résultat de son appel (`result.text` de l'élément, le `tool_result` de l'outil `Agent`), coupé à 8 000 octets (`MAX_TEXT`, même coupe en octets), que la fenêtre lit là (`subagentInfo`) quand l'appel n'a pas de `report` ;
  - `run` = `{ status, tokens?, tools, startedAt, endedAt }`, écrit quand sa rangée du plan finit, ou quand ses totaux arrivent après sa fin, et aussi quand le process meurt (les rangées interrompues : écrit dans le journal sans événement vers la fenêtre, qui a la rangée du plan en attendant).
- Après un redémarrage ou une remise à zéro du plan, la vue d'un sous-agent se lit depuis ces éléments : son fil, sa consigne, son rapport, son bilan. Un appel resté « en cours » dans le journal, sans `run` et sans rangée, est dit interrompu : le plan garde toutes les rangées qui tournent. Sa tâche (`taskId`) n'est que dans sa rangée du plan : quand le plan l'a oubliée, on ne peut plus ni l'arrêter ni lui écrire.

#### Une demande d'un sous-agent (mesuré)

- Le `control_request` `can_use_tool` d'un outil appelé par un sous-agent porte `agent_id`, la tâche du sous-agent (le `task_id` de son `task_started`, l'`agentId` du résultat de lancement), en plus de `tool_use_id` et `display_name`. Les frames `assistant` et `user` du sous-agent portent aussi `agent_id` à côté de `parent_tool_use_id` (et `subagent_type`, `task_description`) ; ses blocs `tool_use` ont `caller: { type: "direct" }`, comme ceux du fil principal. Pas d'`agent_id` pour le fil principal.
- Escouade met `sub` = l'id de l'appel du sous-agent sur l'élément `permission` ou `question` : par `agent_id`, la rangée du plan dont `taskId` est cette tâche ; sinon le `parent` de l'élément d'outil que nomme `tool_use_id`, s'il est l'appel d'un sous-agent (`Agent` ou `Task` : pas le fil d'un agent de workflow), pour une version sans `agent_id`.
- L'élément reste dans la conversation de l'agent (pas de `parent`, il y est où il était) et paraît aussi dans la vue du sous-agent, où l'on y répond ; la réponse se donne comme d'habitude (voir « Répondre à `can_use_tool` »).

#### Arrêter un sous-agent (`stop_task`)

Requête : `{"subtype":"stop_task","task_id":"<tâche>"}`, la tâche étant celle du sous-agent (son `taskId`). Ordre mesuré, tout dans la même milliseconde ou presque :

1. `system/task_updated { task_id, patch: { status: "killed", end_time } }` ;
2. `system/task_notification { task_id, tool_use_id, status: "stopped", output_file, summary }`, **sans `usage` ni `handback_report`** ;
3. `system/background_tasks_changed` ;
4. la `control_response` `success`, avec `{}`.

Ensuite (mesuré) : une frame `user` dans le fil du sous-agent (« [Request interrupted by user] ») ; la commande en arrière-plan que le sous-agent avait lancée lui-même (`task_started` `local_bash` avec `parent_task_id` = la tâche du sous-agent et `owned_by_subagent: true`) est tuée aussi, avec sa propre notification « stopped » ; enfin Claude Code ouvre de lui-même un tour de l'agent (`system/init`, puis une réponse de l'agent sur la fin du sous-agent). **Arrêter un sous-agent coûte donc un tour de l'agent.**

Lu dans le binaire : une tâche inconnue répond en erreur (« No task found with ID: … »). `initialize` accepte `perTaskStopAffordance` : l'hôte déclare un bouton d'arrêt par tâche, et un `interrupt` épargne alors les sous-agents et les workflows en arrière-plan. Escouade ne le déclare pas : « Arrêter » de l'agent (`interrupt`) arrête tout, comme avant.

Une demande de permission que le sous-agent attend quand on l'arrête (mesuré, second essai du même jour, la permission laissée sans réponse, 0,013 $ environ) : Claude Code envoie d'abord `control_cancel_request` pour elle, puis `task_updated` (`killed`), `task_notification` (`stopped`), `background_tasks_changed`, la réponse à `stop_task`, et dans le fil du sous-agent un `tool_result` en erreur (« The user doesn't want to proceed with this tool use… ») suivi de « [Request interrupted by user for tool use] ». Escouade traite l'annulation comme toute autre (`on_cancel` : la carte est marquée annulée et ne compte plus parmi les demandes qui attendent) ; le faux `claude` fait de même.

Dans Escouade :
- la commande `stop_subagent(id, call)` envoie `stop_task` (15 s pour répondre). Elle est refusée si le sous-agent ne tourne pas, s'il travaille au premier plan (« Ce sous-agent travaille au premier plan : l'agent l'attend, et « Arrêter » de l'agent l'arrête avec son tour. »), si sa tâche n'est pas connue (aucune frame ne l'a dite), en vue Claude Code (son interface s'en charge), ou si l'agent n'a pas de process. Le premier plan est refusé parce qu'arrêter seul un sous-agent qui y travaille n'a jamais été essayé sur un vrai flux (l'essai ci-dessus ne porte que sur un sous-agent en arrière-plan) : l'agent l'attend, et « Arrêter » de l'agent l'arrête avec son tour ;
- elle ne change aucun état elle-même : la fin arrive par les frames ci-dessus, comme n'importe quelle fin (la rangée passe à `stopped`, avec `run` sur son appel). La commande en arrière-plan du sous-agent n'est pas une rangée (le réducteur ne compte que les `local_agent` et les `local_workflow`) ;
- la fenêtre ne montre « Arrêter » dans la vue du sous-agent que pour un sous-agent en arrière-plan qui tourne, grisé avec une explication tant que sa tâche n'est pas connue ; jamais pour un sous-agent au premier plan, ni en vue Claude Code ;
- le serveur MCP appelle la même commande : `stop_background_work` (ESC-107) arrête un sous-agent en arrière-plan par son id d'appel ou son `taskId`, avec les mêmes refus, et `list_background_work` en montre l'issue (voir « Sous-agents et tâches de fond » dans « Outils qui agissent »).

#### Lui écrire (le message passe par l'agent : vérifié)

- `send_task_message` est dans les listes de sous-types du binaire (lu), mais 2.1.300 répond `Unsupported control request subtype: send_task_message` (mesuré).
- `get_task_output` sur une tâche `local_agent` répond `get_task_output: no shell or Monitor task with that task_id in this session` (mesuré) : il est réservé aux commandes et aux surveillances.
- Claude Code dit lui-même au modèle, pour un sous-agent en arrière-plan qui tourne, qu'il peut lui envoyer un message avec l'outil `SendMessage` (lu dans le binaire ; le résultat du lancement le dit aussi : « Use SendMessage with to: '<agentId>'… », avec `canContinueAgent: true`, mesuré).
- **Retenu : le message va à l'agent, à qui l'on demande de le transmettre.** La commande `message_subagent(id, call, text)` envoie à l'agent, dans la langue des textes qu'Escouade rédige pour Claude : « Transmets ce message au sous-agent « <titre> » (agentId <tâche>) avec l’outil SendMessage, tel quel, puis reprends ce que tu faisais : », une ligne vide, puis le texte. Ce n'est pas un message de l'utilisateur : il ne sert jamais à nommer l'agent. Il paraît dans la conversation de l'agent comme tout message envoyé, et lui coûte un tour (Claude Code l'intègre à l'étape suivante si l'agent travaille déjà).
- **Essai réel** (mesuré, Claude Code 2.1.300, Haiku, 2026-10-15, 0,01 $ environ ; frames dans `tests/fixtures/real-run-send-message.jsonl`, rejouées par `agent::tests::a_report_handed_back_without_subagent_handback_is_the_summary_of_its_notification`) : un sous-agent en arrière-plan lançait deux `ping -n 20 127.0.0.1` l'un après l'autre, et l'agent lui a transmis, pendant le premier, « The secret word is BANANA. Put it in your final report. ».
  - L'agent charge d'abord l'outil, différé comme ceux des tâches (`ToolSearch { query: "select:SendMessage", max_results: 1 }`), puis appelle `SendMessage { to: "<agentId>", message, summary, … }`. Claude Code répond par un `tool_result` dont le texte est du JSON : `{"success":true,"message":"Message queued for delivery to <agentId> at its next tool round. If it finishes first, it is resumed with the message and notifies again, so wait for that notification before resending.","pin":{…}}`. Le message arrive donc au sous-agent à son prochain outil ; s'il a fini avant, Claude Code le reprend avec le message.
  - Le message **n'apparaît pas comme une frame** du flux : la seule trace est le `SendMessage` de l'agent (`parent_tool_use_id` nul) et son résultat. Il atteint pourtant le sous-agent : son texte final le cite mot pour mot.
  - Ce texte final est le `summary` de sa `task_notification` (`completed`, `usage`, sans `handback` ni `handback_report`) : le sous-agent a fini sans `SubagentHandback`, d'où le rapport tiré du `summary` (voir « Ce que la conversation garde d'un sous-agent »). Claude Code ouvre ensuite un tour de l'agent (`system/init`), qui rapporte la fin du sous-agent.
- **Refus du backend.** `message_subagent` refuse, sans rien envoyer : un texte vide (« Le message est vide. »), un agent archivé, la vue Claude Code (on y écrit à un sous-agent depuis l'interface de Claude Code), un sous-agent au premier plan (« Ce sous-agent travaille au premier plan : l'agent ne lui transmettrait le message qu'une fois fini. ») et un sous-agent qui tourne mais n'a pas de tâche (« Claude Code n'a pas donné la tâche de ce sous-agent : on ne peut pas lui écrire. »). Il refuse aussi un sous-agent qui ne tourne plus (terminé, arrêté, en échec ou interrompu, même avec une tâche donnée) ou dont la rangée n'existe pas : « Ce sous-agent ne tourne plus. », le texte d'« Arrêter » (`stop_subagent`). Claude Code reprendrait un sous-agent fini avec le message (`canContinueAgent`, et le texte ci-dessus), mais le plan ne rouvre jamais une rangée finie, le sous-agent repris serait encore dit « Terminé », et le tour de l'agent, qui doit transmettre le message, serait dépensé pour rien. Le refus est dans la fonction du cœur (`Core::subagent_target`, que `Core::message_subagent_from` appelle), donc la commande de la fenêtre y est soumise comme l'outil du serveur, même si la fenêtre n'offrait déjà l'envoi qu'à un sous-agent qui tourne. L'outil `message_subagent` du serveur MCP (ESC-107) appelle la même commande, avec les mêmes refus : le texte est celui de l'appelant, coiffé de son nom (voir « Outils qui agissent »).
- Dans la fenêtre, la vue du sous-agent a un champ « Lui écrire, par <agent> », qui dit que Claude Code ne permet pas d'écrire directement à un sous-agent et que le message passe par l'agent (`SendMessage`). Le champ n'est là que pour un sous-agent **en arrière-plan** qui tourne et dont la tâche est connue, et jamais en vue Claude Code ni pour un agent archivé (un sous-agent au premier plan : le message ne lui arriverait qu'à sa fin). Ctrl+Entrée y envoie le message ; il ne répond pas à une demande qui attend (le champ garde ses touches : `data-own-keys`, voir `answersHere`). Un brouillon reste, en mémoire de la session, quand le sous-agent finit ou qu'on change de vue ; le champ reste alors, l'envoi grisé.
- **Limites** : c'est une demande faite au modèle de l'agent, que rien n'oblige à appeler `SendMessage` (il l'a fait dans l'essai, qui n'a été fait qu'une fois, avec Haiku) ; la fenêtre ne voit pas le message arriver au sous-agent, seulement le `SendMessage` de l'agent. Si une version future de Claude Code accepte `send_task_message`, l'utiliser à la place.

#### En vue Claude Code

Ni le flux ni les hooks ne disent ce que fait un sous-agent. Mesuré sur 2.1.300, dans le dossier de transcript de l'essai ci-dessus (une session du flux, `entrypoint: "sdk-cli"`) : son fil est dans un transcript **à lui**, `<dossier du transcript de l'agent>/<session>/subagents/agent-<agentId>.jsonl`, à côté de `<session>.jsonl`, avec `agent-<agentId>.meta.json` : `{"agentType","description","toolUseId","spawnDepth","requestShape","model","stoppedByUser"}`, où `toolUseId` est l'id de l'appel `Agent` qui l'a lancé (l'id de sa rangée) et `agentId` sa tâche (`task_id`). Les entrées ont la forme de celles du transcript de l'agent, avec `isSidechain: true` et `agentId` : une `user` d'abord, la consigne (un texte) ; puis des `assistant` (un bloc par entrée : `thinking`, `text`, `tool_use`), des `user` avec des `tool_result` (et un `toolUseResult` structuré), des `attachment`, et des `api-request`, `api-request-blob`, `api-request-shape`. La réflexion arrive vide (`thinking: ""`, la signature seule). Un sous-agent arrêté se termine par un texte « [Request interrupted by user] ». **Vérifié ensuite sur une vraie session interactive** (Claude Code 2.1.283, `entrypoint: "cli"`, pas enregistrée dans le dépôt) : l'interface écrit les mêmes fichiers au même endroit. Dans cette session, le hand-back d'un sous-agent était rejoué (`origin.kind: "peer"`, voir « sa fin » plus bas) ; aucune `task-notification` d'un sous-agent ne l'était, seulement celles de commandes. **Pas encore vu** : une session interactive plus récente qui rejouerait aussi la `task-notification` d'un sous-agent ; le code accepte les deux, et le hand-back suffit à finir la rangée. Enregistrement du flux : `tests/fixtures/real-sidechain.jsonl` et `.meta.json` (que les `user` et `assistant`, signatures retirées, chaînes coupées à 300 caractères, le nom de l'utilisateur remplacé par « dev »).

Dans Escouade, en vue Claude Code :
- `transcript.rs` écarte toujours les entrées `isSidechain` de l'agent (rien d'un sous-agent ne se dit de l'agent). La commande `subagent_transcript(id, call, cursor?)` (`Core::subagent_transcript`) lit celui du sous-agent, en lecture seule : refusée hors vue Claude Code ; le transcript de l'agent est celui qu'Escouade lit (`transcript_read`), sinon celui de sa session dans le dossier de son compte (`find_transcript`). `agent/sidechain.rs` cherche `agent-<tâche>.jsonl` (la tâche de la rangée du plan, si elle ne contient que `[A-Za-z0-9_-]`), sinon le `*.meta.json` (200 au plus, 64 Kio chacun) dont `toolUseId` est l'appel. Jamais un lien (`symlink_metadata`, fichier ordinaire seulement, ni pour les dossiers) ; un fichier de plus de 8 Mio est lu par sa fin, à partir d'une fin de ligne. Pas de fichier : une lecture sans élément ni curseur, pas une erreur ;
- **ne relire que ce qui a changé** (la fenêtre appelle la commande toutes les 2 s) : la réponse est `{ items, cursor, ended }` ou `null`. `cursor` = `{ len, mtime }`, la taille du transcript en octets et sa date de modification en ms, **la plus tardive de celles du transcript et de son `meta.json`** (Claude Code écrit celui-ci de son côté : `stoppedByUser` ne doit pas rester inaperçu d'un transcript qui ne bouge plus) ; il est pris **avant** la lecture, pour que ce qui s'écrit pendant elle soit lu la fois d'après. Donné à l'appel suivant, il fait répondre `null` (rien lu, rien analysé) tant que taille et date sont les siennes ; sans curseur, la réponse porte toujours tout le fil. Le curseur est `null` tant qu'il n'y a pas de fichier (la lecture d'après le cherche de nouveau). Le chemin trouvé est gardé dans le `Core` (`sidechains`, clé : agent + appel ; 256 au plus, le plus ancien part le premier ; ceux d'un agent s'en vont avec lui, comme avec son projet) : les `meta.json` ne sont plus parcourus tant que le fichier est là. Un chemin dont le fichier n'est plus un fichier ordinaire dans les dossiers ordinaires `<session>/subagents` (supprimé, ou remplacé par un lien) est oublié et cherché de nouveau ;
- les entrées deviennent les éléments que le flux fait des mêmes blocs (`text`, `thinking`, `tool` avec `status` puis `result`, et le diff d'un `Edit`), tous avec `parent` = l'appel. Ne sont pas gardés : la première `user` (la consigne, dite par l'en-tête) et toute `user` qui n'est pas un résultat d'outil, les `attachment` et `api-request*`, les blocs sans mots (la réflexion vide), les doublons d'id. Un appel `SubagentHandback` garde son `message` (le rapport) jusqu'à `MAX_REPORT` ;
- la fenêtre lit le fil à l'ouverture de la vue, puis toutes les 2 s tant que le sous-agent tourne (et une dernière fois à sa fin), en repassant le curseur de la lecture précédente. Une réponse `null` ne change rien (ni la liste ni l'erreur éventuelle, qu'elle efface seulement : la lecture a réussi) ; la liste (`$state.raw`) est remplacée d'un bloc par chaque lecture qui répond, jamais modifiée sur place. Elle n'a ni « Arrêter » (`stop_subagent` y est refusé) ni « Lui écrire » (`message_subagent` y est refusé aussi : on agit dans l'interface de Claude Code) ; le rapport est celui de l'appel, sinon le `message` du dernier `SubagentHandback` du transcript ;
- **sa fin** : sans frame `system`, la rangée d'un sous-agent en arrière-plan ne finissait jamais. Deux entrées `user` que Claude Code rejoue dans le transcript de l'agent la finissent, l'une ou l'autre, la première qui vient (une rangée déjà finie ne change pas : en flux, la vraie frame est passée avant) :
  - le hand-back (`origin.kind` `peer`) : `<agent-message from="<agentId>">[Subagent hand-back] … The report follows: …`, le rapport étant ce qui suit, sans l'indentation de deux espaces dont Claude Code le décale. C'est la fin que la session interactive observée (2.1.283) a donnée. `keep_handback` range le rapport sur l'appel de la rangée dont la tâche est `from` (ou l'`origin.from`), s'il n'a pas déjà de `report`, puis applique au plan un `task_notification` `completed`. Un sous-agent arrêté n'a pas de hand-back (sa notification n'a pas de `handback_report`, mesuré en flux) : sa fin n'est alors dite que par sa `task-notification`, ou par ses fichiers (ci-dessous) ;
  - la `<task-notification>` (`origin.kind` `task-notification`) : `on_replay` lit son `task-id`, son `tool-use-id` et son `status` (`completed`, `failed`, `stopped` ou `killed`) et l'applique au plan comme la frame `task_notification`. Son `summary` n'est pas un rapport (il dit souvent où le rapport est allé). Aucune n'a été vue pour un sous-agent dans la session interactive observée.
- **un sous-agent arrêté dans l'interface, ou en échec** : ni frame, ni forcément de `task-notification` ni de hand-back rejoués, et la rangée restait « En cours » pour toujours. Ses fichiers le disent (`sidechain::how_it_ended`, fonction pure sur son `meta.json` et la fin de son transcript) :
  - **arrêté** : `"stoppedByUser": true` dans son `meta.json` (mesuré sur un sous-agent arrêté par `stop_task`, voir la fixture `real-sidechain.meta.json`), ou sa dernière entrée de la conversation est une `user` dont le texte commence par « [Request interrupted by user » (« [Request interrupted by user] » ou « … for tool use] », mesuré : c'est la dernière ligne de `real-sidechain.jsonl`) ;
  - **en échec** : sa dernière entrée est une `assistant` marquée `isApiErrorMessage: true` (l'API a renoncé) ;
  - sinon rien : il tourne peut-être encore, ou a fini normalement, ce que disent son hand-back ou sa notification rejoués. La dernière entrée est celle de la conversation (`user`, `assistant`, `isSidechain: true`) : les `attachment`, `api-request*` et les lignes illisibles qui la suivent ne comptent pas ; un sous-agent repris par un message (une entrée après l'interruption) n'est plus fini. Une rangée terminée n'est jamais rouverte par le plan ;
  - **à la lecture du transcript** : `subagent_transcript` rend cette fin (`ended`: `"stopped"` ou `"failed"`, sinon `null`). Si la rangée de ce sous-agent tourne encore, elle est terminée comme une `task_notification` (`stopped` ou `failed`, avec `run` écrit sur son appel, par `AgentRt::end_subagent`), l'agent est enregistré et envoyé à la fenêtre (rien n'est envoyé si la rangée avait fini) : la barre latérale et la vue changent, et la fenêtre, dont `running` devient faux, relit une dernière fois puis arrête sa minuterie. La fenêtre n'utilise pas `ended` elle-même. C'est l'effet de l'ouverture de la vue, et d'elle seule : `get_background_output` d'un sous-agent (ESC-107) lit le même transcript pour en tirer le rapport sans rien terminer (`Core::read_sidechain`), car un outil de lecture ne change pas l'état du plan ;
  - **au hook `Stop`** (fin d'un tour de l'agent, `Core::end_stopped_subagents`, appelée par `on_tui_hook`) : quand la vue du sous-agent n'est pas ouverte, rien ne le lit et la barre latérale resterait « En cours ». Le `meta.json` de chaque sous-agent **en arrière-plan** dont la rangée tourne encore (30 au plus : un petit fichier chacun, lu hors du verrou de l'agent ; le chemin se trouve et se garde comme ci-dessus) est donc regardé, et ceux qui ont `stoppedByUser` sont terminés en `stopped`. Un sous-agent au premier plan finit avec le tour de son agent, comme avant. Seul `stoppedByUser` est regardé ici : lire la fin de chaque transcript à chaque tour coûterait plus cher que ce que le hook y gagne.

### Les tâches de fond d'un agent : commandes, surveillances (mesuré sur Claude Code 2.1.301, 2026-10-16, ESC-14)

Cinq essais du 2026-10-16 sur un vrai Claude Code 2.1.301 (Haiku, mode de permission `default`, compte réel, 0,045 $ en tout), en stream-json, par des sondes jetables (hors dépôt) qui autorisent les outils, enregistrent chaque frame et envoient des requêtes de contrôle : (1) une commande en fond qui compte (`Ticker`, 10 lignes en 20 s), une autre à arrêter (`sleep 300`), une surveillance (outil `Monitor`) et un sous-agent en fond, avec `get_task_output` sur chaque tâche toutes les 2,5 s et `stop_task` sur la commande à arrêter au bout de 14 s ; (2) une commande en fond qui échoue (`exit 3`), une qui écrit 300 lignes (13,7 Ko), un sous-agent ; (3) la même commande de 300 lignes et une commande lancée **au premier plan** puis passée en fond par la requête `background_tasks` ; (4) une commande en fond dont on lit le fichier de sortie à côté de `get_task_output` ; (5) les mêmes tâches avec des hooks de commande (`PreToolUse`, `PostToolUse`, `Stop`) pour la vue Claude Code. Les frames des essais 1 et 3 (stdout, nettoyées comme celles d'ESC-13) sont `tests/fixtures/real-run-background-tasks.jsonl` et `tests/fixtures/real-run-foreground-flip.jsonl`. Les schémas des frames sont aussi lus dans le binaire 2.1.301 (leurs descriptions disent le contrat).

#### Ce que les frames disent d'une tâche de fond (mesuré)

| Moment | Frames, dans l'ordre vu |
|---|---|
| Une commande part en fond (`Bash` `run_in_background`) | `assistant` (`tool_use` : `input.command`, `input.description`) → `system/background_tasks_changed` (la tâche y est **déjà**) → `system/task_started { task_id, run_id, tool_use_id, description, is_backgrounded: true, task_type: "local_bash" }` → `user` (`tool_result` « Command running in background with ID: <tâche>. Output is being written to: <chemin>.output. You will be notified when it completes. To check interim output, use Read on that file path. », `tool_use_result { stdout: "", backgroundTaskId, … }`) |
| Une surveillance (outil `Monitor`, deferred : `ToolSearch select:Monitor` d'abord) | même suite : `task_started` a `task_type: "local_bash"` **aussi** (seul le nom de l'outil de son `tool_use_id`, `Monitor`, la distingue d'une commande) ; `tool_use_result { taskId, timeoutMs, persistent }` (pas de `backgroundTaskId`), `tool_result` « Monitor started (task <tâche>, expires in 1m unless the source ends first… ». Chaque ligne de sortie est un événement que Claude Code passe à Claude : un **tour de l'agent par événement** (6 lignes = 6 tours dans l'essai 1) |
| Une fin | `system/task_updated { task_id, patch: { status: "completed" \| "failed" \| "killed", end_time } }` → `system/task_notification { task_id, run_id, tool_use_id, status: "completed" \| "failed" \| "stopped", output_file, summary }` → `system/background_tasks_changed` (sans la tâche) |
| `summary` | `Background command "Ticker" completed (exit code 0)`, `Background command "Failer" failed with exit code 3`, `Monitor "Watch loop output" stream ended` ; pour une tâche arrêtée, seulement sa description (`Sleeper`). Pas de `usage` pour une commande |
| Une commande au premier plan | `task_started { is_backgrounded: false }`, **aucune entrée** dans `background_tasks_changed`, `task_notification` avec `output_file: ""` à sa fin. C'est aussi le cas de la commande qu'un sous-agent lance lui-même (`owned_by_subagent: true`, `parent_task_id` = la tâche du sous-agent) |
| Une commande passe du premier plan au fond (`background_tasks { tool_use_id }` ou Ctrl+B) | `background_tasks_changed` (avec la tâche) → `task_updated { patch: { is_backgrounded: true } }` → `tool_result` « Command was manually backgrounded by user with ID: … » (`backgroundedByUser: true`, `backgroundTaskId`). La requête répond `{ backgrounded: true }` |

`background_tasks_changed { tasks: [{ task_id, run_id, task_type, subagent_type?, description, parent_task_id?, ambient?, awaited? }] }` est un **niveau** (« REPLACE semantics », lu dans le schéma) : les tâches de fond vivantes après le changement, **sous-agents compris** (`task_type: "local_agent"`), jamais celles du premier plan. Il n'a ni la commande, ni l'heure de début, ni le résumé, ni l'état final. Aucune frame n'est émise au démarrage d'un process. `description` est celle de l'outil (« Ticker »), pas la commande, qui n'est que dans l'`input` du `tool_use`.

#### Quelle source dit le mieux ce qui tourne

Les deux, pour deux rôles :

- **les bords** (`task_started`, `task_updated`, `task_notification`) font les rangées : seuls à porter le `tool_use_id` (donc la commande, lue dans l'`input` de l'appel déjà vu), l'état de fin (`completed` / `failed` / `stopped`), le résumé (code de sortie compris) et `output_file` ; seuls à distinguer un premier plan d'un fond (`is_backgrounded`) ;
- **le niveau** (`background_tasks_changed`) est le filet : il dit ce qui est vivant sans dépendre d'une notification (la description de la frame le dit elle-même : « a missed bookend cannot wedge a stale running indicator »). Il précède `task_started` pour une tâche qui démarre en fond, et suit sa notification pour une qui finit : une rangée qui tourne et qui n'est plus dans le niveau est finie, et une entrée du niveau sans rangée en ouvre une (tâche lancée avant une remise à zéro du plan). L'ordre exact n'est pas promis par Claude Code (« do not correlate it with the edge stream »), d'où le filet et non la source.

#### La sortie en direct : `get_task_output` ou le fichier ? (mesuré)

- **`get_task_output { task_id }`** (requête de contrôle, lue dans le schéma : « Read-only and no model turn; a host polls it while the task runs ») → `{ output, total_bytes, truncated }` : **la fin de la sortie, 8 Kio au plus** (`truncated: true` et `output` de 8 192 octets, qui commence au milieu d'une ligne, pour la commande de 300 lignes : `total_bytes` 13 692, puis 13 718 à la fin). Mesuré vivant : la sortie grossit ligne à ligne (`tick 1\n` 7 octets, puis `tick 1\ntick 2\n` 14 octets…), vide tant que la commande n'a rien écrit. Servi aussi **après** la fin, avec `\n[exited with code 0]\n` (ou `\n[killed]\n`, 10 octets, pour une tâche arrêtée) au bout. Pour un sous-agent : réponse d'erreur `get_task_output: no shell or Monitor task with that task_id in this session` (même mesure qu'ESC-13). Une tâche inconnue : même erreur. La commande qu'un sous-agent lance au premier plan répond (vide : `output: ""`, `total_bytes: 0`) ; une commande du fil principal ne répond qu'à partir du moment où elle passe en fond (non essayé avant).
- **Le fichier `output_file`** (`<dossier temporaire>/claude/<dossier de travail codé>/<session>/tasks/<tâche>.output`) : mesuré **écrit en direct** (7, 14, 21, 35, 42, 49, 56 octets aux lectures successives, identique à `get_task_output`), **entier** (13 718 octets pour la commande de 300 lignes, contre 8 192 pour la requête) et **gardé après la fin** (avec le `[exited with code N]`)  ; il reste sur le disque quand le process est arrêté (relu après la fin de la sonde). Mais son chemin n'est dit qu'au texte du `tool_result` (« Output is being written to: … », pas dans `tool_use_result`) et, à la fin, par `task_notification.output_file` (vide pour une commande de premier plan) ; il est sur la machine de Claude Code (un agent sous WSL a un chemin Linux). Le fichier d'un sous-agent est vide à sa fin (`outputFile` du résultat de lancement : 0 octet).
- **Retenu : `get_task_output` tant que le process de l'agent vit**, le fichier en repli. La requête ne demande ni chemin ni accès au disque (elle marche pour un agent sous WSL), ne coûte aucun tour et rend la même fin de 8 Kio que la vue détaillée de Claude Code (`/tasks`) ; le fichier sert quand il n'y a plus de process (redémarrage, process mort) et en vue Claude Code, où aucune requête de contrôle n'est possible ; une tâche finie se lit d'abord dans le fichier, plus loin que ces 8 Kio (voir « Dans Escouade »). Le nom du fichier est contrôlé avant lecture : exactement `<tâche>.output`, dans un dossier `tasks`, jamais sur une autre machine (voir « Dans Escouade »).

#### « Arrêter » une tâche de fond (`stop_task`, mesuré)

`stop_task { task_id }` sur une commande en fond : 0,15 s après la requête, `task_updated { patch: { status: "killed", end_time } }`, `task_notification { status: "stopped", output_file, summary: "<description>" }`, `background_tasks_changed` (sans elle), puis la réponse `{}` ; la sortie se termine par `\n[killed]\n`. Comme pour un sous-agent, Claude Code **ouvre un tour de l'agent** pour lui annoncer l'arrêt (l'agent de l'essai a répondu qu'il ne l'avait pas arrêté lui-même : « the notification says it was stopped by the user »). Le même `stop_task` vaut pour une surveillance et un workflow (« Stops a running task », lu dans le schéma ; une tâche inconnue répond `No task found with ID: …`).

#### En vue Claude Code (hooks et transcript, mesuré)

Ni frames `system` ni requêtes de contrôle : ce que la vue peut dire d'une tâche de fond tient aux **hooks** et au **transcript** (même format que la session du flux : `entrypoint` mis à part).

- **Hooks de commande** (`PreToolUse` / `PostToolUse`, essai 5) : le `PostToolUse` d'une commande en fond a `tool_input { command, description, run_in_background: true }` et `tool_response { stdout: "", stderr: "", interrupted: false, backgroundTaskId }` ; celui d'un `Monitor`, `tool_response { taskId, timeoutMs, persistent }`. **Pas de hook de fin de tâche** : `Stop` part à chaque fin de tour (cinq dans l'essai, les tours que les notifications ouvrent compris) et ne dit rien d'une tâche.
- **Transcript** : le `tool_use` (`input.command`, `input.description`), son `tool_result` avec `toolUseResult.backgroundTaskId` (ou `taskId`), puis des entrées `queue-operation` `enqueue` et des `user` d'`origin` `{ kind: "task-notification", producer: "session-task", runId? }` dont le texte est `<task-notification><task-id>…</task-id><tool-use-id>…</tool-use-id><output-file>…</output-file><status>completed|failed|killed</status><summary>…</summary></task-notification>` — la **fin**. Un événement de surveillance est rejoué de la même façon mais **sans `<status>`** (`<summary>Monitor event: "…"</summary><event>watch 1</event>`) : il ne finit pas la tâche. Tâche arrêtée : `<status>killed</status>`, `<summary>Task "Sleeper" was stopped by the user</summary>`.
- **Retenu** : le début d'une tâche vient du résultat de l'outil (`on_tool_result` : `backgroundTaskId` / `taskId`, la commande de l'appel déjà vu), sa fin de la notification rejouée (`end_replayed_task`, qui ignore une notification sans statut) ; le début n'est donc pas daté à la seconde près. Les hooks, redondants avec le transcript, ne sont pas utilisés pour cela. « Arrêter » n'est pas offert dans cette vue (l'interface de Claude Code s'en charge) ; la sortie se lit dans le fichier, dont le chemin est celui du `tool_result`.

#### Dans Escouade

- **Le réducteur du plan** (`plan.rs`, fonctions `bg_*`) fait des rangées de `PlanState.bgTasks`.
  - `task_started` d'un type gardé (`local_bash`, `monitor_mcp`, `remote_agent`, `in_process_teammate`) ouvre la rangée : son titre est la `description` de la frame, sinon celle de l'appel, sinon la première ligne de la commande, sinon l'id ; sa commande est celle de l'appel que nomme le `tool_use_id` (mémoire de l'agent, 64 appels) ; son `kind` est `monitor` quand cet appel est un `Monitor`. Une commande (`local_bash`) n'est listée que si `is_backgrounded` est vrai ; les autres types le sont sauf `is_backgrounded: false`. Sinon elle est seulement retenue (32 au plus, jusqu'à sa fin ou à la fin du tour) : `task_updated { is_backgrounded: true }`, le niveau qui la liste ou le `tool_result` qui donne son `backgroundTaskId` la fait alors lister, avec l'heure de son départ.
  - `task_updated` renomme (`description`) et finit (`completed`, `failed`, `killed`) ; `task_notification` finit (`completed`, `failed`, `stopped` ou `killed`), garde le `summary` et l'`output_file`, et ne finit rien sans un de ces états. Les fins closent la rangée dans n'importe quel ordre, comme pour un sous-agent ; une rangée close ne rouvre pas.
  - `background_tasks_changed` est le filet (voir plus haut). Le `tool_result` d'un `Bash` / `PowerShell` ou d'un `Monitor` ouvre la rangée qu'aucune frame n'a ouverte (c'est tout le début d'une tâche en vue Claude Code) et note le fichier de sortie que son texte nomme (« Output is being written to: … »), seulement quand il s'appelle `<tâche>.output` ; jamais un autre nom. Ni lui ni l'`output_file` d'une `task_notification` ne sont gardés quand le chemin que disent les frames commence par deux séparateurs (`\\hôte\partage`, `\\?\…`, `\\.\…`, `//hôte/…`, quelle que soit la plateforme) : Windows ouvrirait une connexion réseau, avec les identifiants de l'utilisateur, pour le lire (`taskout::safe_origin`). Le chemin Linux d'un `claude` sous WSL (`/tmp/claude/…`) n'est pas dans ce cas.
  - Les rangées se rangent à 10 finies et 40 en tout (la finie la plus ancienne sort d'abord, puis, au-delà de 40, la plus ancienne). `is_finished` et `runs_something` les comptent : un plan dont une tâche de fond tourne n'est pas fini (pas de remise à zéro au message suivant) et l'agent n'est pas « au repos » (l'arrêt des process inactifs le laisse, `restart_process` refuse « Relancer » et l'interface le grise ; `running_count` compte aussi les sous-agents et les workflows qui tournent, et le redémarrage automatique de l'application pour une mise à jour attend : `Snapshot.background` en fait la somme pour chaque agent non archivé qui a un process, `Busy::Background`, car un redémarrage tue ces tâches avec le process).
- **`stop_bg_task(id, tâche)`** envoie `{ subtype: "stop_task", task_id }` (15 s pour répondre) pour une rangée de `bgTasks` ou un workflow ; le plan n'est pas touché, la fin vient des frames qui suivent. Refus : tâche inconnue du plan (« Cette tâche de fond n'est pas connue de l'agent. »), qui ne tourne plus (« Cette tâche de fond ne tourne plus. »), agent en vue Claude Code (« En vue Claude Code, une tâche de fond s'arrête depuis son interface. ») ou sans process (« Le processus de l'agent ne tourne pas. »).
- **`task_output(id, tâche)`** rend `{ output, totalBytes, truncated, source }`, la fin de la sortie coupée à un caractère : **8 Kio au plus pour une tâche qui tourne** (`MAX_OUTPUT`, tout ce que `get_task_output` rend), **256 Kio au plus pour une tâche finie** (`MAX_FINISHED_OUTPUT`, lue dans le fichier : la première erreur d'un build raté n'est pas dans les 8 derniers Kio). Une tâche inconnue du plan est refusée ; un agent distant ou un coéquipier (ni commande ni surveillance) rend `source: "none"`. Sinon, pour une tâche qui tourne, avec un process vivant hors vue Claude Code : `get_task_output { task_id }` (10 s, sans tour du modèle) ; sa réponse `{ output, total_bytes, truncated }` donne `source: "process"`. Une erreur de Claude Code (une tâche qu'il ne connaît pas) ou une réponse d'une autre forme n'arrête rien : repli sur le fichier `outputFile` de la rangée (converti pour un `claude` sous WSL), lu par sa fin sur 8 Kio, `source: "file"`. Une tâche finie (terminée, en échec, arrêtée, interrompue) prend l'ordre inverse : le fichier d'abord (256 Kio) et, s'il manque, est illisible ou refusé, `get_task_output` quand le process vit (8 Kio). Le fichier n'est ouvert que s'il s'appelle exactement `<tâche>.output`, qu'il est dans un dossier nommé `tasks` (`<…>/<session>/tasks/<tâche>.output`) et que c'est un fichier ordinaire (`symlink_metadata` : ni lien, ni dossier). **Jamais un chemin d'une autre machine** : un chemin donné par les frames qui commence par deux séparateurs (UNC `\\hôte\partage`, verbatim `\\?\…`, périphérique `\\.\…`, `//hôte/…`) n'est ni gardé dans la rangée ni lu (`taskout::safe_origin`, demandé au chemin tel que les frames le disent, avant toute conversion) : Windows l'ouvrirait par le réseau en envoyant les identifiants de l'utilisateur, et aucune connexion ne part. Le chemin Linux d'un `claude` sous WSL (`/tmp/claude/…`), converti par Escouade en `\\wsl.localhost\<distribution>\…` (`Wsl::windows_path`), reste lu : c'est un partage de la machine, sur un chemin déjà accepté. Sans process ni fichier : `source: "none"`. Le verrou de l'agent n'est tenu ni pendant la requête, ni pendant la lecture du fichier.
- **Par le serveur MCP** (ESC-107), les mêmes fonctions : `list_background_work` donne les rangées du plan (sous-agents, `bgTasks`, workflows) comme la barre latérale, `get_background_output` appelle `task_output` pour une commande ou une surveillance (ses bornes, sa vérification du fichier et ses `source` sont celles de la fenêtre ; son `bytes`, de 1 à 65 536, coupe seulement ce qu'elle rend : un client MCP ne peut pas demander les 256 Kio qu'elle lit) et `stop_background_work` appelle `stop_bg_task` ; refus compris, avec le même texte. Voir « Outils de lecture » et « Outils qui agissent ».
- **En vue Claude Code**, `end_replayed_task` (`agent.rs`) lit la `<task-notification>` que Claude Code rejoue dans le transcript (`<task-id>`, `<tool-use-id>`, `<status>`, `<summary>`, `<output-file>`) et en fait la frame `task_notification` du réducteur. Une notification sans `<status>` (l'événement d'une surveillance, `<event>…`) ne finit rien et n'est pas appliquée. Les échappements que Claude Code met dans les textes (`&amp;`, `&lt;`, `&gt;`, les guillemets) sont défaits dans le résumé et le fichier ; une rangée de tâche de fond garde l'un et l'autre, une rangée de sous-agent ni l'un ni l'autre.
- **La fenêtre** reçoit `bgTasks` avec le plan (aucun événement nouveau) et range ces rangées et les workflows en une liste (`src/lib/bgtasks.ts`). `TaskView.svelte` lit `task_output` à son ouverture, toutes les 1,5 s tant que la tâche tourne et que la fenêtre est visible, et une dernière fois à sa fin ; chaque réponse remplace l'affichage.
- **Les flux rejoués** : `tests/fixtures/real-run-background-tasks.jsonl` (essai 1 : `Ticker`, `Sleeper` arrêté par `stop_task`, `Watch loop output` et un sous-agent) et `tests/fixtures/real-run-foreground-flip.jsonl` (essai 3 : `Loud`, en fond d'emblée, et `Foreground loop`, passée du premier plan au fond) sont rejoués par les tests de `agent.rs`. Le faux `claude` (`tests/fixtures/fake-claude.mjs`, scénarios « commande de fond », « surveillance de fond » et « commande premier plan ») refait les mêmes séquences, écrit un fichier de sortie et répond à `stop_task` et à `get_task_output`.

#### Ce qui n'a pas été vu sur un flux réel

Les types `monitor_mcp`, `remote_agent` et `in_process_teammate` (lus dans le binaire : `task_type` de `task_started`), une surveillance `persistent`, une tâche `ambient`, la requête `background_tasks` sans `tool_use_id`. Le support de ces types repose sur les schémas et sur les scénarios du faux `claude`.

## Vue Claude Code (l'interface de Claude Code, dans un terminal)

Un agent peut tourner dans l'interface de Claude Code elle-même (son TUI, `claude` sans `-p`) plutôt que sur le flux stream-json (`src-tauri/src/tui.rs`, `src-tauri/src/engine/claude/terminal.rs`, `src-tauri/src/agent/transcript.rs` ; l'interface commune aux harness : docs/ENGINES.md, « La vue terminal »). Une session n'a qu'un process à la fois : changer de vue arrête l'un et reprend la session dans l'autre (`--resume`). Essais du 2026-10-12 sur Claude Code 2.1.296, avec un vrai TUI piloté dans un pseudo-terminal ; les flux enregistrés sont `tests/fixtures/tui-transcript.jsonl` et `tests/fixtures/tui-hooks.jsonl`.

**Lancement.** Les mêmes arguments que le flux, sans ceux du flux : `--model`, `--effort`, `--permission-mode`, `--allow-dangerously-skip-permissions`, `--append-system-prompt`, `--mcp-config`, `--add-dir` (ESC-95). La session est toujours connue d'avance : `--resume=<id>` seulement si son transcript est dans le dossier du compte de l'agent, sinon `--session-id=<nouvel uuid>` ; une copie fait `--resume=<original> --fork-session [--resume-session-at=<entrée>] --session-id=<nouvel uuid>` (vérifié : le transcript du fork porte bien l'id donné).

**Session à reprendre.** Claude Code ne reprend pas une session qu'il ne trouve pas : sur un `--resume=<id>` sans transcript `<dossier du compte>/projects/*/<id>.jsonl`, il écrit « No conversation found with session ID: <id> » sur sa sortie d'erreur (le flux stream-json lit la même phrase sur la sienne), puis quitte avec le code 1. Et il n'écrit le transcript qu'au premier message : un agent qui n'a rien envoyé n'a aucune session à reprendre, bien que `--session-id` en ait fixé une. Avant chaque lancement (`settle_session`, `check_session`), Escouade cherche donc ce transcript, celui de l'original pour une copie qui n'a pas encore sa propre session, dans le dossier du compte de l'agent, puis, s'il n'y est pas, dans celui des autres comptes du même côté (Windows ou WSL : une session ne passe pas de l'un à l'autre, WSL nomme le dossier de travail à sa façon). Trois issues :
- trouvé dans le dossier du compte : `--resume`, comme avant ;
- trouvé seulement dans celui d'un autre compte (l'agent a changé de compte) : copié dans celui du compte de l'agent (`accounts::copy_session` : le transcript et le dossier du même nom, sous le même dossier de projet), puis repris ; la conversation de l'agent le dit (information) ;
- trouvé nulle part (aucun message envoyé, transcript effacé, original d'une copie perdu) : la session est abandonnée (`session_id`, `last_entry`, `fork_of` et `fork_at` oubliés) et l'interface démarre une nouvelle session par `--session-id`. La conversation l'avertit si l'agent avait quelque chose à perdre (des messages envoyés, ou des entrées lues) ; un agent qui n'a jamais rien envoyé repart sans rien dire ; une copie dont l'original manque le dit toujours. Une copie impossible (le dossier du compte refuse l'écriture) avertit aussi, en nommant les deux comptes, et repart en nouvelle session.

Avec un `claude` de WSL dont le dossier du compte ne répond pas (la distribution est arrêtée), rien n'est vérifié : Claude Code tranche seul, et la sortie de l'interface (ci-dessous) rattrape le cas.

**Sortie de l'interface.** Au départ du process (`on_tui_exit`), Escouade a gardé les premiers 8 Ko de ce qu'il a écrit et classe sa fin :
- « aussitôt » (`quick`) : moins de 20 s après son lancement et un code autre que 0. Un `/exit` rend 0 : jamais « aussitôt », même tout de suite. Un process tué (pas de code) l'est s'il est tombé dans les 20 s ;
- « session perdue » (`sessionLost`) : aussitôt, et la sortie contient « No conversation found » (la fin du flux du pseudo-terminal peut arriver après la sortie : Escouade attend 12 × 40 ms au plus, tant que la sortie grandit et ne le dit pas encore). L'agent abandonne alors sa session comme ci-dessus, avec l'avertissement dans sa conversation ; son prochain lancement est une nouvelle session.

La fenêtre le reçoit avec l'agent (`tuiExit { code, quick, sessionLost }`, `code` à null si le process a été tué ; remis à null au lancement suivant). C'est la vue qui relance l'interface, jamais le backend, et au plus une fois d'elle-même : session perdue, elle repart sur la nouvelle session, sous la note « Session Claude introuvable : l'interface repart en nouvelle session. » ; si cette interface sort aussi aussitôt, ou pour toute autre raison (plantage, argument refusé), elle ne relance rien et dit « Claude Code s'est arrêté dès son lancement (code N). Regarde sa sortie ci-dessus, puis relance-le. » avec « Relancer ». Une interface qui sort sans être « aussitôt » (un `/exit`) dit « Claude Code s'est arrêté. » et « Relancer ». La garde est aussi côté Rust : l'agent compte ses sorties « aussitôt » de suite (`tui_quick_exits`), remis à zéro par toute autre sortie, par un lancement manuel et par un changement de vue, et `agent_terminal` refuse, à la deuxième, un lancement que la vue fait d'elle-même (`manual` faux) : « Claude Code s'arrête dès son lancement (2 fois de suite) : regarde sa sortie, puis clique sur « Relancer ». ». « Relancer » envoie `manual: true` et passe toujours. Le bug d'origine (ESC-106) : l'effet de la vue repartait à chaque mise à jour de l'agent, dont celle de la fin de l'interface, et ouvrait une interface qui sortait à son tour, sans fin ; il ne dépend plus que de l'identité de l'agent.

**Hooks.** `--settings <fichier>` (dans `<données>/tui/<agent>.json`, sans secret) déclare des hooks `"type": "http"` vers `http://127.0.0.1:<port>/hook`, un petit serveur d'Escouade démarré avec la première interface. L'en-tête `Authorization: Bearer $ESCOUADE_HOOK_TOKEN` est lu dans l'environnement (`allowedEnvVars`) : un jeton par interface, jamais sur la ligne de commande. Vérifié :
- les hooks inline s'ajoutent à ceux de l'utilisateur ;
- `SessionStart` ne part pas en HTTP (commande seulement ; revu sur 2.1.301 : « HTTP hooks are not supported for SessionStart », de même pour `Setup`), d'où la session fixée d'avance (`--resume` ou `--session-id`), sans attendre de hook. Escouade ne l'écoute donc pas (il n'est pas dans les hooks du fichier `--settings`) : l'interface prête se reconnaît autrement (voir « Messages et interruption ») ;
- chaque appel porte `session_id`, `transcript_path`, `cwd`, `permission_mode` et `hook_event_name` ;
- `PermissionRequest` arrive quand l'interface affiche une autorisation (avant la réponse), avec `tool_name`, `tool_input` et `permission_suggestions` ; une réponse `{}` ne décide rien et l'interface demande comme d'habitude ;
- `Notification` (`notification_type: permission_prompt`) suit quelques secondes après, `idle_prompt` bien plus tard : Escouade s'en tient à `PermissionRequest`, et à `PreToolUse` d'`AskUserQuestion` pour une question ;
- `Stop` termine un tour qui n'a pas été interrompu ; une interruption (Échap) n'en envoie pas.

Les appels vers la boucle locale contournent le proxy (`NO_PROXY` complété).

**Transcript.** `<dossier du compte>/projects/<cwd encodé>/<session>.jsonl`, une entrée par ligne :
- `user` : un message tapé (`origin.kind: human`, `promptSource: typed`), un résultat d'outil (`toolUseResult`, comme `tool_use_result` du flux), une commande locale (`<command-name>/model</command-name>…`, sa sortie en `<local-command-stdout>`), `isMeta` pour ce que Claude Code ajoute lui-même, et `[Request interrupted by user]` à l'interruption. Depuis 2.1.302, une commande locale est écrite deux fois sous le même `promptId` : tapée (`/compact`, sans `origin`), puis en `<command-name>` ; Escouade n'en montre qu'une ;
- `assistant` : un bloc de contenu par entrée (même `message.id`, même `usage` répété), comme les frames `assistant` du flux ; `isApiErrorMessage` et `error` pour une erreur d'API ;
- `system` : `stop_hook_summary` puis `turn_duration` (`durationMs`) à la fin de chaque tour, `compact_boundary`, et `local_command` pour une commande locale qui échoue (`content` en `<local-command-stderr>`, `commandOutcome.kind: failed`). Une commande locale n'a ni `turn_duration` ni `Stop` : sa sortie (`<local-command-stdout>`, `-stderr>` ou `local_command`) finit son tour, en erreur si elle a échoué, et seulement le tour d'une commande (un `/cost` tapé pendant un tour du modèle le laisse courir). Le mode `!` écrit `<bash-input>` puis `<bash-stdout>…</bash-stdout><bash-stderr>…</bash-stderr>` dans une entrée. Toutes ces balises, en chaîne ou en blocs de texte, dans le flux, ses messages rejoués et le transcript, sont lues par `agent/localcmd.rs` (ESC-154) : la commande telle que tapée (`/model opus`, `! ls`), sa sortie en avis `output` (lignes et colonnes gardées, codes ANSI retirés : la conversation n'est pas un terminal), son erreur en avis `error` ou sur la carte du tour qu'elle finit, rien du caveat ni d'une sortie vide. Les conversations enregistrées avant, qui gardent ces balises dans un message de l'utilisateur, sont lues de même au rendu (`src/lib/localcmd.ts`), sans migration : rien n'est réécrit ;
- `permission-mode` quand l'utilisateur change de mode (Maj+Tab), `ai-title`, `last-prompt`, `attachment`, `file-history-*` ;
- `cost-state` (`modelUsage`, `totalCostUSD`, comme le `result` du flux) seulement à la sortie du process, pas à chaque tour.

Escouade lit le transcript toutes les 400 ms (et juste avant chaque hook) par lignes complètes, et rejoue `user` et `assistant` dans le traducteur du flux. La fin d'un tour (`turn_duration`, l'interruption, ou `Stop` sans `turn_duration` 1,8 s après) devient un `result` fait maison, dont `modelUsage` cumule l'usage de chaque message aux tarifs publics (`pricing`) : le coût d'un tour en vue Claude Code est une estimation. L'offset lu est gardé (`transcriptRead`) : ce qui a été écrit pendant que l'app ne lisait pas l'est au lancement suivant ; sans offset gardé, les entrées d'avant le lancement (l'historique d'une session reprise ou copiée) sont ignorées.

**Messages et interruption.** Un message de la fenêtre ou du serveur MCP est collé dans l'interface (collage entre crochets, `ESC[200~…ESC[201~`, ses sauts de ligne en `\r`, puis Entrée), refusé pendant que l'interface attend une réponse ; une interruption y envoie Échap. Pas de pièce jointe. `send_message` avec des fichiers joints y est refusé (« Pas de pièce jointe en vue Claude Code : colle-la dans son terminal. ») : voir « Fichiers collés ou déposés », plus bas. Un agent de ticket reste toujours sur le flux. Tant qu'une interface n'est pas prête, le message est refusé : écran du premier lancement d'un compte ; dossier jamais approuvé, « Quick safety check » dont le choix par défaut est « No, exit », où le texte tapé choisirait une option. Une interface est prête quand une fenêtre l'a montrée, ou que Claude Code a donné un de ces signes, qui n'arrivent qu'une fois prêt (vérifié sur 2.1.301 le 2026-10-16, jamais sur ces deux écrans) :
- l'inscription de l'interface dans le registre des sessions de Claude Code, `<dossier de config du compte>/sessions/<pid>.json` : `sessionId`, `kind: "interactive"`, `entrypoint` (`cli` pour l'interface, `sdk-cli` pour le process du flux de la même session), `status`, et `bridgeSessionId` seulement quand le remote control de la session est actif. Le fichier est écrit en moins de 2 s une fois l'interface prête ; sur l'écran du premier lancement et la boîte de confiance, seul un `<pid>.<hash>.key` s'y trouve. Escouade lit ce dossier toutes les 400 ms, avec le transcript, tant que cela lui apprend quelque chose (interface pas encore prête, ou lien attendu) : fichiers `<pid>.json` seulement, 512 au plus et 64 Kio chacun, un fichier mal lu (en cours d'écriture, vide, pas du JSON) est relu au passage suivant ; le fichier de l'interface une fois trouvé est seul relu (un `/clear` change le `sessionId`) ;
- une entrée `system`/`bridge_status` ou `bridge-session` du transcript, écrite depuis le lancement.

Aucun hook HTTP ne part à ce moment-là, et, sans remote control, le transcript n'est écrit qu'au premier message (d'où le registre). Le refus : « L'interface de Claude Code de cet agent n'est pas encore prête (premier lancement ou dossier à approuver) : ouvre l'agent pour la voir. »

Vu à l'essai réel sous Windows (ESC-12, 2026-10-18, 2.1.301 puis 2.1.302, ConPTY, `claude.exe` natif, compte Principal ; `tui_tests::real_claude_view`) :
- **sauts de ligne collés** : Claude Code laisse tomber un `\n` collé (« A\nB » arrive « AB »). Escouade colle donc les sauts de ligne en `\r`, comme xterm.js et les terminaux (`engine::terminal::bracketed`) ;
- **mode de collage** : juste après son inscription au registre (et la boîte de confiance), Claude Code coupe le collage entre crochets (`ESC[?2004l`) et ne le remet (`ESC[?2004h`) que 0,5 à 7,5 s plus tard. Collé entre-temps, un saut de ligne vaut Entrée : la première ligne part seule. Escouade suit ce mode dans la sortie du terminal (`TuiOutput::mode`) et attend, avant de coller, qu'il soit remis (15 s au plus, puis colle quand même) ;
- **Échap avant la réponse** : pendant la réflexion, avant tout texte, Échap annule le tour et remet le message dans la zone de saisie de Claude Code, sans rien écrire de plus au transcript et sans hook. Seul le registre le dit : `status` passe de `busy` à `idle` (`statusUpdatedAt`). Pendant un tour, Escouade relit donc le fichier du registre de l'interface et, s'il la dit `idle` depuis 3 s (après le début du tour) sans que le transcript ait fini le tour, le finit, interrompu (`IDLE_ENDS_TURN_MS`). Échap pendant la réponse écrit `[Request interrupted by user]`, comme avant ;
- **Le message remis en saisie** (ESC-118) : le message suivant d'Escouade, collé à la suite, partirait avec lui (vu : « Écris les nombres… sans outil.Lance un seul sous-agent… »). Escouade compte les touches que la fenêtre envoie au terminal (`PtyManager::write_from_window`, `pty::typing` : pas les réponses du terminal à l'interface, ni le focus, ni la souris, ni Échap seul, qui ne tape aucun texte), et note où en était ce compte quand la saisie était vide pour la dernière fois (au lancement, au début de chaque tour, après l'avoir vidée) et quand elle a collé son message. Au tour fermé par le registre, elle sait donc si la saisie ne contient que son message (rien de tapé depuis qu'elle l'a collé dans une saisie vide). Avant de coller le message suivant :
  - son message seul : elle vide la saisie par un seul Ctrl+C (Claude Code vide ainsi une saisie qui contient du texte), puis colle après 300 ms. Jamais deux Ctrl+C à moins d'une seconde, qui quittent l'interface : un seul, et une fois par annulation ;
  - sinon (un brouillon tapé dans le terminal avant ou après, ou un message tapé là par l'utilisateur) : rien n'est vidé, le message s'ajoute à ce que contient la saisie, et la conversation le dit (avertissement « Claude Code a remis dans sa saisie le message annulé avant sa réponse, et du texte a été tapé dans son terminal : Escouade ne l'a pas vidée, ce message s'ajoute à ce qu'elle contient. »). Un brouillon n'est jamais perdu sans que l'utilisateur le sache.

  Le début d'un tour (saisie envoyée) oublie l'annulation. Essai réel (2026-10-18, 2.1.302, Windows, Principal, Haiku ; `tui_tests::real_claude_view_cancelled`, à la main comme `real_claude_view`, 0,07 $) : Échap 300 ms après le début du tour l'annule avant la réponse, le message revient dans la saisie ; un seul Ctrl+C la vide sans quitter l'interface, et le message suivant arrive seul (« Réponds seulement : A », réponse « A »). Avec un brouillon tapé après l'annulation, rien n'est vidé : le message envoyé est « <message annulé> <brouillon> <message suivant> », et la conversation l'a dit ;
- **compaction** : `/compact` réussi écrit `compact_boundary` (« Contexte compacté »), le résumé (`isCompactSummary`) et `<local-command-stdout>Compacted…` ; la même session continue. Une fois, sur Haiku, la compaction a échoué (« Error during compaction: API Error: Output blocked by content filtering policy », entrée `local_command`) : le tour finit alors en erreur ;
- **sous-agent** : lancé en arrière-plan par Claude Code de lui-même ; sa ligne du plan finit « terminée » et sa conversation se lit dans son transcript (`<session>/subagents/agent-<id>.jsonl`) ;
- **`/clear`** : une nouvelle session, que le hook suivant donne ; le message suivant y répond.

**Remote control.** Vérifié le 2026-10-15 sur Claude Code 2.1.300 et 2.1.301, interface lancée dans un pseudo-terminal comme le fait l'app :
- le remote control d'un agent en vigueur au lancement de son interface (à la main ou par un réglage) lui est donné par `--remote-control=<projet · agent>`, en un seul argument : un nom qui commence par « - » n'est pas pris pour une option ;
- Claude Code affiche alors « /rc active » et le lien de la session en moins de 3 s, et écrit dans le transcript une entrée `system`/`bridge_status` avec `url` (Escouade s'en sert pour le lien et l'état « connecté ») et des entrées `bridge-session` (`bridgeSessionId` : un identifiant non vide suffit à l'état « connecté », avant l'adresse) ;
- quand l'interface reprend sa session (`--resume`) avec l'option, Claude Code rattache la même session distante (« Reattaching to persisted bridge session »), avec le même lien ; une interface fermée archive elle-même sa session distante. Escouade ferme donc en douceur une interface qu'elle arrête pour de bon (retour en vue Escouade, archivage, suppression, interface jamais affichée dont le remote control s'éteint) : deux Ctrl+C à 700 ms l'un de l'autre, puis arrêt forcé au bout de 5 s, un démarrage demandé pendant ce temps attendant que l'ancienne soit partie (jamais deux process sur une session) ; et pas à la fermeture de l'app, pour que le lien revienne au prochain démarrage ;
- compte sans abonnement claude.ai : « Remote Control requires a claude.ai subscription… » puis « --rc flag ignored. » ; l'interface continue sans remote control, elle ne se ferme pas. Ce texte n'arrive jamais dans le terminal (vérifié dans la capture brute du pseudo-terminal, le 2026-10-16) : Claude Code l'intercepte et ne l'écrit que dans son journal de debug. Escouade ne le repère donc pas, il le déduit : une entrée `bridge_status` sans `url` dans le transcript d'une interface lancée avec l'option, ou aucun signe d'un lien (`bridge_status` avec `url`, `bridge-session`, `bridgeSessionId` du registre) 20 s après l'inscription de l'interface au registre des sessions. L'état de l'interface est alors `unavailable`, et un lien qui vient après le remet à « connecté ». Une interface qui se ferme dans les 10 s sans qu'une fenêtre l'ait jamais montrée est prise pour un échec de l'option (repli : relancée tout de suite en fond sans elle, et les lancements suivants aussi) ; une interface qu'une fenêtre a montrée ne l'est jamais ;
- Escouade n'a pas de requête pour l'allumer ou le couper dans une interface ouverte : c'est sa commande `/remote-control`, et un changement vaut au prochain lancement.

Une interface lancée en fond (agent en remote control au démarrage d'Escouade) garde sa sortie côté backend, et la fenêtre s'y rattache à l'ouverture.

**Images collées.** L'interface ne lit l'image du presse-papiers que sur une touche à elle (`chat:imagePaste` : `Alt+V` sous Windows, `Ctrl+V` ailleurs), jamais sur le collage du terminal, qu'xterm.js fait du seul texte. Le collage d'images sans texte dans le terminal de l'agent (`terminals.ts`, `pastedContent`) les écrit donc dans `<données>/tui/pastes/<agent>-<uuid>.<png|jpg|gif|webp>` (commande `paste_image`) et colle leurs chemins, un par collage, tels que le `claude` de l'interface les lit (`/mnt/c/…` dans WSL). Une image de plus de 18 Mo est refusée (avant sa lecture dans la fenêtre, puis par la commande), et la commande n'écrit que du PNG, JPEG, GIF ou WebP reconnu à ses premiers octets, nommé d'après eux. Ces fichiers sont effacés avec l'agent ou son projet, et ceux de plus d'un jour au collage suivant et au démarrage. L'image vient du collage de la WebView (WebView2, WKWebView), du presse-papiers du système sous Linux (WebKitGTK ne la donne pas) ; sans image, le collage vide d'xterm.js part quand même. Du texte reste à xterm.js, même à côté d'une image (des cellules d'un tableur) mais pas un simple saut de ligne ; collé pendant qu'une image s'écrit, il attend son tour. Sous macOS, `Ctrl+V` va au terminal (`Cmd+V` colle).

Vérifié le 2026-10-15 sur Claude Code 2.1.299 et 2.1.300 sous Windows, dans un pseudo-terminal puis dans l'app :
- un chemin d'image collé entre crochets devient « [Image #1] », avec ou sans espaces, avec ou sans guillemets ;
- deux chemins dans un même collage deviennent deux images s'ils n'ont pas d'espace, mais restent du texte entre guillemets ; deux collages à la suite donnent « [Image #1] [Image #2] », espaces compris ;
- `ESC v` (`Alt+V`) lit aussi l'image du presse-papiers ; `Ctrl+V` (0x16) et un collage vide ne font rien sous Windows ;
- le message envoyé garde l'image en base64 dans le transcript (`imagePasteIds: [1]`), suivi d'un message `isMeta` « [Image: source: <chemin>] » qui donne son chemin au modèle ; une reprise (`--resume`) après l'effacement du fichier répond encore sur l'image. Le fichier ne sert donc qu'au collage, et au modèle qui voudrait l'ouvrir dans les tours suivants : un jour suffit.

Passer la touche aurait laissé l'image à la lecture du presse-papiers par Claude Code (xclip ou wl-paste sous Linux, PowerShell sous WSL) et à ses raccourcis, que l'utilisateur peut changer. Sous macOS, la sonde `scripts/macos-paste-probe.swift` (workflow « macOS paste probe ») montre qu'un WKWebView reçoit en fichier `image.png` (image/png) la capture d'un `screencapture -c` collée par `paste:`, comme le Coller du menu de l'app. Pas encore essayé : le vrai Claude Code sous macOS, sous Linux et dans WSL.

**Fichiers collés ou déposés** (ESC-95). Un fichier qui n'est pas une image, collé ou déposé sur le terminal de l'agent (`pasteImages` et `dropFiles` dans `src/lib/terminals.ts`, la même file : un dépôt est pris comme un collage de fichiers, et une image déposée suit la route des images collées, ci-dessus), est copié par les commandes `attach_open`, `attach_chunk` (octets bruts, morceaux de 4 Mo au plus) et `attach_finish`, avec l'agent pour propriétaire, dans `<données>/attachments/<agent>/<uniq>/<nom>` ; Escouade tape ensuite le chemin de la copie, tel que le `claude` de l'interface le lit (`claudePath` : `/mnt/c/…` dans WSL), comme `paste_image` le fait pour une image (ESC-16). Il y a toujours copie, jamais le fichier d'origine, quel que soit « Joindre le fichier d'origine » : le process de l'interface n'est lancé qu'une fois, avec le seul dossier de l'agent lisible sans demander (`--add-dir`), et aucun dossier ne peut lui être ajouté ensuite. Ce dossier est celui des fichiers du chat. Les images collées gardent leur propre dossier (`tui/pastes/`, ci-dessus). Le plafond de « Taille maximale d'un fichier joint » s'applique (refus par `attach_open`) ; il n'y a pas d'avertissement de taille, faute de puce. Pas vérifié sur un vrai Claude Code : ce qu'il fait d'un chemin de fichier quelconque collé entre crochets (les chemins d'image y deviennent « [Image #1] »).

**Taille du terminal.** Avec `"tui": "fullscreen"` dans les réglages de Claude Code (champ de saisie ancré en bas de l'écran), l'interface se dessine sur les lignes de la pseudo-console, et sur elles seules : ce que la fenêtre montre de plus reste vide. Vérifié le 2026-10-16 sur Claude Code 2.1.301 sous Windows, dans l'app (ConPTY, xterm.js, WebGL) : une pseudo-console restée à 127×25 pendant qu'xterm.js montrait 46 lignes (message `term_resize` retenu 7 s) donne une interface dessinée sur 25 lignes, 53 % de la hauteur de la zone, puis redessinée en entier dès que la taille arrive ; lancée à 159×46, elle l'est dès sa première image, que le message passe ou non. Dans ces essais, Claude Code n'a pas demandé la taille à xterm.js (les seules écritures de la fenêtre au démarrage : la réponse à la demande de position du curseur de ConPTY et le signal de focus), et ses écrans d'accueil et de choix du thème, dessinés en haut, ne montrent rien de ce défaut. Un redimensionnement de la fenêtre, tout au long de la vie de l'interface, est suivi dans les deux sens. D'où `openAgentTerminal(agentId, room)` (`terminals.ts`) : le terminal est lancé à la taille de la zone qui l'affichera, au lieu de celle du terminal caché de 900×500 px (127×25) corrigée ensuite ; les redimensionnements suivants partent un à la fois et dans l'ordre, et un que le backend n'a pas pris est renvoyé avec la sortie suivante.

**Confiance du dossier.** L'interface demande, au premier lancement dans un dossier, si on lui fait confiance ; un dossier parent accepté suffit (vérifié), donc les worktrees de `<projet>/.claude/worktrees/` héritent de la réponse donnée pour le projet. Un « Dossier des worktrees » hors du projet (`../app-worktrees`) n'en hérite pas : l'interface pose la question au premier lancement de chaque worktree, et Escouade ne répond jamais à la place de l'utilisateur (accepter une fois le dossier des worktrees lui-même, `claude` lancé dedans, la règle pour tous). Le flux (stream-json), sans interface, ne la pose pas.

## Terminaux intégrés : le chemin d'une frappe

Une frappe : xterm.js (`onData`) → `invoke('term_write')`, traité sur le fil principal de la fenêtre dans l'ordre d'arrivée des requêtes → file d'entrée du terminal (`PtyManager::write` ne fait que la remplir) → fil d'écriture du terminal (`write_all` dans l'entrée du pseudo-terminal : ConPTY sous Windows) → le programme, qui renvoie l'écho → fil lecteur du terminal (lectures de 32 Ko au plus) → un message de sa `Channel` Tauri (évalué dans la WebView par le fil principal ; par une requête de plus au-delà de 1 Ko) → `term.write` → l'image suivante. Jusqu'au 2026-10-15, `term_write` écrivait lui-même dans le pseudo-terminal, sur le fil principal, sous un verrou commun à tous les terminaux : un programme qui ne lit pas son entrée aurait gelé la fenêtre et la saisie de tous les terminaux.

## Codex app-server (ESC-37)

Codex est le second harness (docs/ENGINES.md). Testé avec **Codex 0.163.0** (`tested()` : de la 0.163.0 à la 0.163.0), d'après l'essai réel du 2026-10-16 (ESC-22, docs/TODO-1.8.md, point 0) dont les flux sont dans `tests/fixtures/codex/`. Son schéma, `codex app-server generate-json-schema --experimental` de la 0.163.0, est gardé dans `tests/fixtures/engines/codex-0.163.0.schema.json` ; deux tests le tiennent (`engine/codex/schema_tests.rs`) : tout ce qu'Escouade envoie et lit y est, et tout champ des flux enregistrés aussi.

### Lancement

```
codex app-server -c tools.update_plan.enabled=true
      [-c mcp_servers.escouade.url=<url> -c mcp_servers.escouade.bearer_token_env_var=ESCOUADE_MCP_TOKEN
       | -c mcp_servers.escouade.enabled=false]
```

Refusé, `enabled=false` n'est passé que si le `config.toml` du compte déclare une entrée `escouade` : sans elle, une entrée faite du seul `enabled` n'a pas de transport, et Codex ne démarre pas (« invalid transport in `mcp_servers.escouade` », vu à l'essai réel du 2026-10-17).

Le programme est le binaire natif : sous Windows, le `codex.exe` du paquet de la plateforme, à côté du lanceur npm (`node_modules/@openai/codex-win32-x64/vendor/x86_64-pc-windows-msvc/bin/codex.exe`), lancé sur place pour qu'il trouve ses `codex-resources/` ; sinon le `codex` du PATH, puis celui de l'app de bureau (`%LOCALAPPDATA%\Programs\OpenAI\Codex\bin\codex.exe`, souvent plus ancien). Il est mis dans le Job de l'agent dès son lancement : ses enfants y restent, bac à sable compris. L'environnement est celui des agents (réseau des réglages), plus `CODEX_HOME` pour un compte autre que Principal, et le jeton du serveur MCP d'Escouade dans `ESCOUADE_MCP_TOKEN`, jamais sur la ligne de commande. `update_plan` n'est plus offert au modèle par défaut (0.163) : sans ce `-c`, le bandeau « Plan » n'aurait pas d'étapes. Rien ne passe par la `config` de `thread/start`, qui ferait perdre les `-c` de `mcp_servers`.

Dans une build de debug, `ESCOUADE_CODEX` (les e2e) donne le programme quand aucun chemin n'est réglé, ou `none` pour aucun : jamais celui de la machine. Les tests unitaires ne cherchent jamais le `codex` de la machine.

### Le protocole

JSON-RPC, une ligne par message sur stdio. Le process (`engine/codex/process.rs`) répond lui-même à ses requêtes et passe tout le reste à la traduction (`agent/codex.rs`) : les notifications, et les requêtes de Codex (approbations, questions), dont il garde l'id, la méthode et les paramètres jusqu'à la réponse.

| Étape | Message | Ce qu'Escouade y met |
|---|---|---|
| Ouverture | `initialize` puis `initialized` | `clientInfo` (`escouade`), `capabilities.experimentalApi: true` (le mode Plan seul en a besoin) |
| Conversation neuve | `thread/start` | `cwd`, `model`, `approvalPolicy`, `approvalsReviewer`, `sandbox`, `developerInstructions` (le protocole d'un ticket : Codex le garde dans le rollout, une reprise n'a pas à le redonner) |
| Reprise | `thread/resume` | `threadId` (la session de l'agent) ; un fil que Codex ne trouve plus en donne un neuf, et la conversation dit « La conversation Codex n'a pas pu être reprise » |
| Copie | `thread/fork` | `threadId` de l'original, `lastTurnId` (son dernier tour au moment de la copie, `fork_at`) ; la copie a son propre fil |
| Modèles | `model/list` | lu une fois par process : le menu du composer (`Ready.catalog`) |
| Un message | `turn/start` | `input` (texte, images en URL `data:`, fichiers texte en texte), `model`, `effort`, `summary: auto`, et le mode (ci-dessous) ; modèle, effort et mode valent à chaque tour |
| Pendant un tour | `turn/steer` | `expectedTurnId` du tour en cours ; un message arrivé pendant que le tour démarre attend son id |
| Interrompre | `turn/interrupt` | `threadId`, `turnId` ; Codex finit le tour en `interrupted` |
| Quota | `account/rateLimits/read` | ses fenêtres, en compteurs (`{"meters": […]}`, que `usage::parse_windows` lit) |
| Titre | `thread/name/set` | |

Une requête refusée qu'Escouade n'attendait pas (`turn/start`, `turn/steer`) revient à la traduction comme une notification `error` (`refused`) : un tour qui n'a pas pu démarrer finit en erreur avec sa raison.

### Les modes

| Escouade | `approvalPolicy` | `sandboxPolicy` (`sandbox` du fil) | `approvalsReviewer` | `collaborationMode` |
|---|---|---|---|---|
| Plan | `on-request` | `readOnly` (`read-only`) | `user` | `plan` |
| Demander | `on-request` | `workspaceWrite`, réseau coupé (`workspace-write`) | `user` | `default` |
| Accepter les modifications | `on-request` | `workspaceWrite`, réseau coupé | `user` | `default` |
| Auto | `on-request` | `workspaceWrite`, réseau coupé | `auto_review` | `default` |
| Sans permissions | `never` | `dangerFullAccess` (`danger-full-access`) | `user` | `default` |

En `workspace-write`, Codex protège tout `.git` : un agent en worktree ne peut pas commiter sans élévation (essayé). En « Demander », la carte d'un `git add` ou d'un `git commit` le dit (« git écrit dans le dépôt du projet, hors du bac à sable de Codex »). En « Édits auto » et en « Auto », Escouade accepte d'office `git add` et `git commit` dans le worktree de l'agent (`engine/codex/git.rs`), et rien d'autre : une commande acceptée ainsi tourne hors du bac à sable, avec le réseau. La décision porte sur la commande que Codex lancera (`params.command` de la demande : son argv joint comme le lirait un shell POSIX, `pwsh.exe -Command '<script>'` sous Windows, `bash -lc '<script>'` ailleurs), jamais sur son résumé (`commandActions`), qui doit dire la même chose. Le script est lu comme le lit son shell, guillemets compris (PowerShell prend aussi les guillemets typographiques pour des guillemets), et tout doute fait demander : un opérateur hors guillemets autre que `&&` entre deux commandes acceptées (`&`, `;`, `|`, `||`, `>`, `(`, `{`, `@`, `#`, `,`, `--%`…), `$`, l'accent grave ou un saut de ligne n'importe où, une option de git avant la sous-commande (`-c`, `-C`, `--git-dir`, `--work-tree`, `--exec-path`, `--config-env`…), une autre sous-commande que `add` et `commit` (`branch`, `tag`, `stash`, `checkout -b`… touchent ce que partagent tous les worktrees du projet), un mode interactif ou un commit sans message (il attendrait un éditeur). Le dépôt doit avoir une configuration que le bac à sable protège (`<worktree>/.git`, ou le dossier `.git` du projet ; un fichier `.git` qui pointerait vers le worktree ou un dossier temporaire est refusé), et un commit ne passe d'office que si ses hooks sont ceux de ce `.git` (`git rev-parse --git-path hooks` ; avec `core.hooksPath` dans le worktree, husky ou `.githooks/`, il demande). Ce qui n'est pas accepté d'office garde sur sa carte « git écrit dans le dépôt du projet, hors du bac à sable de Codex » quand c'est une commande git qui écrit. Le réseau (`push`, `fetch`, `ls-remote`…) et le reste demandent. Le mode que dit `thread/settings/updated` revient sur l'agent (« Demander » et « Édits auto » sont le même pour Codex : celui de l'agent est gardé).

### Le flux

Les messages d'un sous-agent arrivent sur la même connexion, sous son `threadId` : ils sont rangés sous sa `Task`, et la fin de son tour (`turn/completed` de son fil) n'est pas celle du tour de l'agent. Un fil inconnu est écarté.

| Codex | Dans la conversation |
|---|---|
| `item/agentMessage/delta`, `item/completed` `agentMessage` | un `text`, en direct puis entier (`commentary` et `final_answer` pareils) ; le passage à lire d'une conversation vocale est mis à part par la partie commune |
| `item/reasoning/summaryTextDelta` (ou `textDelta`), `item/completed` `reasoning` | un `thinking` dès ses premiers mots ; un raisonnement sans résumé n'est pas montré |
| `commandExecution` | `Bash`, sa commande telle que le modèle l'a écrite (`commandActions[].command`), son résultat (`aggregatedOutput`), en erreur si `failed`, `declined` ou code de sortie non nul |
| `fileChange` | un `Write` par fichier ajouté, un `Edit` sinon, avec son diff (`structuredPatch` comme Claude Code) et ses +N −M ; le fichier parmi ceux de l'agent |
| `mcpToolCall` | `mcp__<serveur>__<outil>`, ses `arguments`, le texte de `result.content` ou `error.message` |
| `webSearch`, `imageView`, `dynamicToolCall` | `WebSearch` (`query`), `Read` (`file_path`), l'outil sous son nom |
| `subAgentActivity` `started` / `completed` | une `Task` (sa description : le nom de `agentPath`), sa ligne dans le bandeau « Plan », finie avec le dernier message du sous-agent comme rapport ; `collabAgentToolCall` (`wait`…) n'est pas montré |
| `turn/plan/updated` | les tâches du bandeau « Plan » (`pending`, `inProgress`, `completed`), comme un `TodoWrite` |
| `contextCompaction` | « Contexte compacté » |
| `plan` (mode Plan) | à la fin du tour, la carte « Plan à approuver » (`ExitPlanMode`) : le tour reste ouvert ; approuvé, Escouade démarre son travail (« Mets le plan en œuvre. ») en « Demander » (en « Accepter les modifications » avec « Approuver et accepter les édits ») ; refusé, le message de refus part en mode Plan |
| `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval` | une carte de permission (`Bash` avec sa `reason`, `Edit` ou `Write` avec son diff, `Permissions` dite en mots) ; « Autoriser » `accept`, « Pour cette session » `acceptForSession` (pour une permission : `scope: session`), « Refuser » `decline` (Codex n'entend pas de raison : celle que l'utilisateur écrit lui est passée par `turn/steer`). `acceptWithExecpolicyAmendment` (une règle gardée pour toutes les sessions) n'est pas proposé |
| `item/tool/requestUserInput` | la carte des questions, ses questions gardant leur `id` ; la réponse `{answers: {<id>: {answers: [<libellé>]}}}` |
| `serverRequest/resolved` | une carte encore en attente est close (tour interrompu) |
| `thread/tokenUsage/updated` | les tokens du tour : la différence des `total` de chaque fil (sous-agents compris) entre le début et la fin du tour ; la fenêtre de contexte (`modelContextWindow`) |
| `account/rateLimits/updated` | les fenêtres du compte (libellées par `windowDurationMins`), et la remise à zéro d'une limite atteinte (`rateLimitReachedType`) |
| `turn/completed` | la fin du tour : fini, `interrupted`, `failed` (son `error.message`, celui de l'API quand c'en est un), arrêté par la limite (`codexErrorInfo` `usageLimitExceeded` ou `rateLimitExceeded`) ; son id est le point de copie (`last_entry`) |

En « Auto », une décision du relecteur automatique de Codex (`guardianWarning`, « Automatic approval review approved… ») est dite dans la conversation, puisque personne n'a été interrogé.

Tout le reste est ignoré sans casser le tour : `turn/moderationMetadata`, `skills/changed`, `mcpServer/startupStatus/updated`, `remoteControl/status/changed`, `thread/readState/changed`, `turn/diff/updated`, `deprecationNotice`, et toute méthode, tout élément ou champ inconnus. Un flux enregistré (`{"dir", "msg"}` par ligne) se rejoue tel quel : seul ce que Codex a dit (`s2c`) est traduit.

### Les comptes (ESC-38)

Un compte est un `CODEX_HOME` : Principal est `~/.codex` (ou le `CODEX_HOME` de l'environnement de l'app), lancé sans toucher à la variable ; les autres sont sous `<données>/codex/<nom>`. Un nouveau compte peut reprendre de Principal `config.toml`, `AGENTS.md` et les dossiers `skills`, `prompts` et `rules` (liés ou copiés), jamais `auth.json` (la connexion, dont le jeton change à chaque renouvellement) ni ses sessions. Il se connecte par `codex login` dans le dossier du compte, depuis un terminal intégré : la fenêtre dit « Connecté au compte » avec l'adresse du compte ChatGPT dès qu'`auth.json` est écrit. Un compte sans `auth.json` (une connexion gardée dans le trousseau, que Codex sait faire) passe pour non connecté. Le Principal de Codex n'est fait qu'au premier agent ou ticket Codex (`Core::accounts_of`).

Le rafraîchissement de la connexion (lu dans le binaire 0.144.5, ESC-162) : avant de rafraîchir, Codex relit `auth.json` et ne rafraîchit pas si la connexion a changé entre-temps (« Skipping token refresh because auth changed after guarded reload »). Il n'y a pas de verrou entre processus. Deux app-servers du même `CODEX_HOME` peuvent donc envoyer le même jeton de rafraîchissement, et le second reçoit « Your access token could not be refreshed because your refresh token was already used. Please log out and sign in again. ». Le risque existe, mais il est faible : le jeton d'accès de Codex dure longtemps, et sa relecture gardée couvre le cas courant. Aucun cas dans les conversations ni dans `app.log` au 2026-10-23 : Escouade ne fait rien de plus pour Codex.

### Le quota et le coût (ESC-38)

`caps.quota` vaut `windows` : les fenêtres du compte, libellées par leur durée (`windowDurationMins` : « 5h », « 7j », ou une seule « 30j » avec l'offre gratuite). Elles viennent de `account/rateLimits/updated` et `account/rateLimits/read` pendant qu'un agent tourne ; pour un compte sans agent, d'un `codex app-server` du compte lancé au plus toutes les 5 minutes le temps d'un `account/rateLimits/read` (aucun fil, aucun tour). Un tour arrêté par la limite (`usageLimitExceeded`) attend la remise à zéro puis reprend seul, et les nouveaux agents passent au compte Codex suivant sous le seuil, comme ceux de Claude Code.

Le coût n'est pas dans le flux : `caps.cost` vaut `estimated`. Escouade le calcule d'après les tokens du tour (sous-agents compris, `thread/tokenUsage/updated`) et la grille publique d'OpenAI (`pricing::estimate_openai`), et l'écrit « ≈ … estimé » partout où un coût se montre. Un modèle hors de la grille (celui d'un autre harness après une passation) coûte 0.

### Le serveur MCP d'Escouade (ESC-38)

Donné, par les `-c` du lancement (ci-dessus) : `mcp_servers.escouade.url` et `bearer_token_env_var=ESCOUADE_MCP_TOKEN`, le jeton dans l'environnement du seul process (`grant_file` à `None`). Essayé sur la 0.163.0 : `bearer_token_env_var` l'emporte sur une entrée `escouade` de l'utilisateur, c'est le jeton de l'agent qui arrive. Refusé, `-c mcp_servers.escouade.enabled=false`, seulement si le `config.toml` du compte a une entrée `escouade` (sans elle, Codex ne démarre pas). Les outils s'appellent `mcp__escouade__<outil>` dans la conversation (élément `mcpToolCall`). La déclaration pour l'utilisateur (son `config.toml`) : « Serveur MCP d'Escouade » › « Déclaration dans les harness ».

### Les textes rédigés (ESC-38)

`codex exec` (`engine/codex/exec.rs`), essayé sur la 0.163.0 :

```
codex exec --ephemeral --skip-git-repo-check --ignore-user-config --ignore-rules --sandbox read-only
           --json --color never -m gpt-6-luna -c model_reasoning_effort="low"          (la question par l'entrée)
           [--disable shell_tool --disable apps --disable plugins --disable browser_use --disable computer_use]
```

- La question arrive sur son entrée ; `codex exec` n'a pas de prompt système : les consignes la précèdent entre `<instructions>`. La réponse est le dernier message de l'agent du flux `--json`.
- Un texte court (`Weight::Light`) se passe de shell : avec lui, le modèle explore le dossier même pour un nom (29 000 tokens au lieu de 12 000, essayé). Un texte qui lit le dossier (`Weight::Reading`, effort `medium`) garde le shell en lecture seule ; `--ignore-user-config` retirant le bac à sable de Windows, celui du `config.toml` du compte est redonné par `-c` (sans lui, toute commande est refusée).
- `--ephemeral` ne laisse rien dans le dossier de Codex (vérifié). La question part sur le compte Codex de l'agent ou du projet. « Modèle des textes rédigés » le nomme « Codex (GPT-6-Luna) ».

### Vue Codex (ESC-47)

`codex resume <fil>` (ou `codex` pour une conversation neuve), avec `--no-daemon`, les hooks et leur confiance en options de ce seul process (`-c hooks.…`), le mode, le modèle et l'effort de l'agent, dans un terminal intégré ; la conversation se remplit depuis le rollout de la session. Les choix et les essais : docs/ENGINES.md, « La vue Codex ».

### Ce qui n'est pas pris en charge

Les PDF joints (Codex ne les lit pas : le bouton les refuse en le disant), « Reprendre sur <compte> » (une conversation reprise sur un autre compte), les commandes `/` dans le composer, Remote Control, les tâches de fond et l'arrêt d'un sous-agent, le réglage « Les agents tiennent une liste de tâches » (`update_plan` est toujours offert), et `acceptWithExecpolicyAmendment` (une règle gardée pour toutes les sessions). En vue Codex, le bandeau « Plan », les sous-agents et le coût ne sont pas suivis.

## OpenCode serve (ESC-44)

OpenCode est le troisième harness (docs/ENGINES.md). Testé avec **OpenCode 1.19.3** (`tested()` : de la 1.19.3 à la 1.19.3, paquet npm `opencode-ai`), d'après l'essai réel du 2026-10-17 avec des modèles locaux par Ollama (ESC-25, docs/TODO-1.8.md, point 0, « OpenCode ») dont les flux sont dans `tests/fixtures/opencode/` et rejoués depuis `tests/fixtures/replays/opencode/`. Le schéma OpenAPI de la 1.19.3 (`GET /doc`) est dans `tests/fixtures/engines/opencode-1.19.3.openapi.json`.

**OpenCode 2** (`@opencode/cli`, `opencode --version` : `opencode v2.0.32`) est une autre API, encore expérimentale : il est reconnu à sa version (2 ou plus) et refusé avec sa raison (`Engine::unsupported_line`) : état « Non pris en charge » dans Réglages › Harness, et l'agent ne démarre pas.

### Lancement : un serveur par compte

```
opencode serve --hostname 127.0.0.1 --port 0
```

Un serveur sert tous les agents d'un même compte (même programme, même environnement : `engine/opencode/server.rs`). Il est lancé au premier agent et arrêté avec le dernier, dans un Job (tout son arbre est tué avec lui), dans un dossier à lui (`escouade-opencode` du dossier temporaire) : jamais celui d'un agent, qu'un worktree supprimé trouverait tenu. Chaque agent est une session dans son dossier (`?directory=<dossier>` sur chaque requête) ; quand le dernier agent d'un dossier s'en va, Escouade le dit au serveur (`POST /instance/dispose`), qui lâche le dossier. Un serveur qui tombe arrête tous ses agents (ils redémarrent au message suivant, leur session reprise). Repli possible si un serveur commun pose problème : un serveur par agent (0,7 Go chacun).

- `--port 0` prend 4096 s'il est libre, sinon un port au hasard : l'adresse est lue sur sa sortie (`opencode server listening on http://127.0.0.1:<port>`).
- `OPENCODE_SERVER_PASSWORD` : tiré au hasard (24 octets) pour chaque serveur, en Basic `opencode:<mot de passe>`. Il ne sort jamais d'Escouade (`GET /config` rend la config résolue, jeton du serveur MCP compris).
- `OPENCODE_CONFIG_CONTENT` (fusionnée avec la config de l'utilisateur) : `model` et `small_model` (le modèle du premier agent : sans eux, OpenCode part sur OpenCode Zen sans compte, vu à l'essai), `autoupdate: false`, `share: "disabled"`, `permission` (les règles de « Demander », pour toutes les sessions du serveur : celle d'un sous-agent ne prend pas les règles de la session de son agent, et sans elles ses commandes passaient sans question, vu à l'essai réel), et `mcp.escouade.enabled: false` (le serveur MCP d'Escouade est gardé hors de tous les dossiers, une entrée `escouade` de l'utilisateur comprise : chaque agent reçoit la sienne par l'API, voir « Le serveur MCP d'Escouade » plus bas). Plus `OPENCODE_DISABLE_AUTOUPDATE=1` et `OPENCODE_ENABLE_QUESTION_TOOL=1`.
- Le programme est le binaire natif : sous Windows, l'`opencode.exe` du paquet npm (`node_modules/opencode-ai/bin/opencode.exe`, à côté du lanceur `opencode.cmd`), sinon l'`opencode` du PATH. Dans une build de debug, `ESCOUADE_OPENCODE` (les e2e) donne le programme quand aucun chemin n'est réglé, ou `none` pour aucun.
- Le flux est lu sur `/global/event` (SSE, enveloppe `{directory, payload}`), et chaque événement va à l'agent dont il concerne la session, ou à celui dont la session a ouvert celle d'un sous-agent (`session.created` avec `parentID`).

### Les sessions

| Étape | Requête | Ce qu'Escouade y met |
|---|---|---|
| Conversation neuve | `POST /session` | `title` (« Escouade » : un titre donné n'est pas écrit par un modèle) et `permission`, les règles du mode |
| Reprise | `GET /session/:id` | la session de l'agent ; introuvable, une neuve est ouverte et la conversation dit « La session OpenCode n'a pas pu être reprise » ; ses règles sont redonnées (`PATCH`) |
| Copie | `GET /session/:id/message`, puis `POST /session/:id/fork` | OpenCode copie les messages d'avant celui qu'il reçoit : Escouade lui donne celui qui suit le dernier message de l'original au moment de la copie (`fork_at`), aucun quand c'est le dernier ; la copie reçoit les règles de son mode (OpenCode ne les copie pas) |
| Modèles | `GET /config/providers`, `GET /config` | lus une fois par serveur : le menu du composer (`Ready.catalog`) |
| Un message | `POST /session/:id/prompt_async` | `parts` (texte, images en `file` avec une URL `data:`, fichiers texte en texte), `model` (`providerID`, `modelID`), `agent` (`plan` en mode Plan, `build` sinon), `variant` (l'effort, si le modèle l'a), `system` (les consignes ajoutées, le protocole d'un ticket : elles ne valent que pour ce prompt) |
| Interrompre | `POST /session/:id/abort` | OpenCode tue la commande en cours et finit le tour (`MessageAbortedError`) |
| Mode | `PATCH /session/:id` | `permission` : OpenCode fusionne les règles, la dernière qui correspond l'emporte ; chaque mode les redonne toutes |
| Permission | `POST /permission/:id/reply` | `once`, `always` (OpenCode garde pour la session le motif qu'il proposait, `always`), `reject` avec le message de refus |
| Question | `POST /question/:id/reply` | `answers` : pour chaque question, dans l'ordre, les libellés choisis |
| Titre | `PATCH /session/:id` | `title` |

**Un message pendant un tour** serait pris au vol par OpenCode, et la demande du premier perdue (`mid-turn.jsonl`) : Escouade le garde (`caps.mid_turn` `queued`) et l'envoie, avec les autres gardés, dès la fin du tour. La fin du tour est le `session.idle` de la session de l'agent, une fois celle-ci vue occupée (`session.status` `busy`) depuis le dernier message : celui d'un sous-agent arrive avant, et un `idle` du tour précédent peut arriver après le message suivant.

**Le modèle** est toujours donné : celui de l'agent s'il est parmi ceux des fournisseurs connectés, sinon celui par défaut (le `model` de la config de l'utilisateur, sinon le défaut du premier fournisseur), que la conversation reprend (`escouade.model`). Un agent dont le modèle n'est d'aucun fournisseur connecté (vide, celui d'un autre harness après une passation, un nouvel agent avant qu'un serveur ait listé les modèles) prend, avant son lancement, le modèle par défaut que liste `opencode models --verbose` (sans serveur, sans appel à un modèle : `Engine::list_models`, `Core::settle_model`) ; sans aucun fournisseur connecté, il est refusé avant qu'un serveur démarre, et le message le dit. Ainsi aucun serveur ne tourne sans `model` ni `small_model`, que les agents suivants du compte réutiliseraient. Ce qu'OpenCode fait de lui-même avec un modèle est couvert : un titre ou un nom (`small_model`, et Escouade donne de toute façon le titre de ses sessions), ce qui retombe sur le modèle par défaut (`model`) ; la compaction prend le modèle de la session, donc celui de l'agent.

### Les modes

OpenCode n'a pas de bac à sable : seules ses règles de permission protègent (`rules` d'`engine/opencode/mod.rs`), et le menu le dit.

| Escouade | Agent | `bash` | `git add *`, `git commit *` | `edit` | `webfetch` | `external_directory` |
|---|---|---|---|---|---|---|
| Demander | `build` | `ask` | `ask` | `allow` | `ask` | `ask` |
| Accepter les modifications | `build` | `ask` | `allow` | `allow` | `ask` | `ask` |
| Plan | `plan` | `ask` | `ask` | `ask` | `ask` | `ask` |

Comme chez Codex, les fichiers du dossier de l'agent changent sans question en « Demander », et `git add` et `git commit` passent d'office en « Accepter les modifications ». « Auto » n'est pas proposé (OpenCode n'a pas de relecteur). Un sous-agent suit les règles de « Demander » de la config du serveur, quel que soit le mode de son agent : ses commandes demandent, et sa carte est rangée sous sa `Task`. En Plan, un tour fini par l'agent `plan` (son message dit `agent: plan`) reste ouvert sur la carte « Plan à approuver » (`ExitPlanMode`) : approuvé, le mode passe à « Demander » (« Accepter les modifications » avec « Approuver et accepter les édits ») et Escouade envoie « Mets le plan en œuvre. » ; refusé, le message de refus part en mode Plan.

| `todo.updated` | les tâches du bandeau « Plan » (`pending`, `in_progress`, `completed` ; `cancelled` compte comme faite, un statut inconnu comme à faire) |
| `task` et `session.created` (`parentID`) | une `Task`, sa ligne dans le bandeau « Plan » ; les messages et outils de la session enfant (liée par `metadata.sessionId`) sont rangés sous elle, ses tokens et ses outils comptés ; son rapport est le `<task_result>` de la sortie |
| `permission.asked` | une carte : `Bash` (la commande), `Edit` (le fichier, son diff), `WebFetch` (l'adresse), `Permissions` pour un chemin hors du dossier (« Hors du dossier de l'agent : … ») ; elle dit le motif que « Toujours autoriser » retiendra quand ce n'est pas la demande elle-même. Une demande d'un sous-agent est montrée dans l'agent et dans le sous-agent |
| `question.asked` | la carte des questions (`multiple` : plusieurs choix) |
| `permission.replied`, `question.replied`, `question.rejected` | une carte répondue ailleurs (`opencode attach`) dit la réponse et se ferme |
| `message.updated` (`role: user`) et sa part de texte | un message tapé ailleurs (`opencode attach`) : le message de l'utilisateur, une fois. Le process le reconnaît : un message `user` de la session qui arrive sans prompt d'Escouade en attente d'être vu est marqué `typedElsewhere` (décidé à son premier `message.updated`, par son id) ; ceux d'Escouade, déjà affichés à l'envoi, sont laissés de côté |
| `session.status` `busy` | le tour en cours (un tour lancé ailleurs aussi) |
| `session.error` | `MessageAbortedError` : le tour est interrompu ; une autre erreur (`UnknownError`, `ProviderAuthError`, `APIError`…) : sa première ligne, dite à la fin du tour |
| `session.idle` | la fin du tour (voir plus haut) |

Tout le reste est ignoré sans casser le tour : `plugin.added`, `catalog.updated`, `server.heartbeat`, `session.diff`, `file.edited`, `file.watcher.updated`, `integration.updated`, `reference.updated`, `project.directories.updated`, et tout type ou champ inconnu. Un flux enregistré (`{"dir", "msg"}` par ligne) se rejoue tel quel : les événements, et la session qu'a faite son `POST /session`.

### Le coût et le garde-fou (ESC-45)

Le coût d'un tour est celui qu'OpenCode donne (`cost` de chaque `step-finish`, au prix du fournisseur ; 0 avec un modèle local), sans estimation d'Escouade (`caps.cost` `exact`). Il va aux stats avec la colonne `engine` `opencode` (filtre « Harness », vue « Par harness ») et au coût du jour. OpenCode n'a pas de quota d'abonnement (`caps.quota` `none`) : la barre d'état montre, à la place des barres, le coût du jour du compte de l'agent affiché, sur son budget quand il en a un.

**Garde-fou** (décidé par l'utilisateur le 2026-10-18) : « Budget par jour ($) » dans Réglages › Comptes, pour un compte d'un harness sans quota (`Account::daily_budget`), vide par défaut. Rempli, et le coût du jour du compte l'atteint, le compte est retenu jusqu'à minuit (heure locale) comme à un quota épuisé (`board::account_pause`, `PauseReason::Budget`) : le pilote auto ne lance plus de ticket sur lui, et les outils MCP qui démarreraient un ticket ou un agent le refusent en disant pourquoi ; « Reprendre maintenant » le lève jusqu'à minuit. Passé minuit, le coût du jour est relu (`UsageSnapshot::day_over`) et le compte repart. Un modèle local (coût 0) ne l'atteint jamais.

### Le serveur MCP d'Escouade (ESC-45)

Le serveur `opencode serve` est commun aux agents d'un compte : une entrée de sa config (`OPENCODE_CONFIG_CONTENT`) vaudrait pour toutes ses sessions, et ne pourrait porter ni le jeton propre à un agent (le serveur MCP d'Escouade sait qui l'appelle par ce jeton) ni la décision de lui donner ou non le serveur. Essayé sur la 1.19.3 (2026-10-18, deux dossiers sur un serveur, un petit serveur MCP qui note l'en-tête reçu) : `POST /mcp?directory=<dossier>` ajoute un serveur MCP **à l'instance de ce dossier seulement**. Le dossier A s'est connecté avec le jeton A, le dossier B avec le jeton B, un dossier C n'en avait aucun ; `POST /mcp/:nom/disconnect` le coupe pour son dossier ; `POST /instance/dispose` le retire avec l'instance. Une session du dossier A, avec `qwen3-coder:30b-32k`, a appelé l'outil `escouade_whoami` et reçu sa réponse, avec le jeton A. Rien n'est écrit dans la config sur le disque.

Escouade s'en sert ainsi (`process::give_escouade`) :

- la config du serveur garde `mcp.escouade.enabled: false` pour tous les dossiers ;
- un agent à qui le serveur est donné (`Escouade::Granted`, son jeton à lui) reçoit, à son ouverture, `POST /mcp?directory=<son dossier>` avec `{"name": "escouade", "config": {"type": "remote", "url", "enabled": true, "headers": {"Authorization": "Bearer <son jeton>"}, "oauth": false}}`. Le jeton ne passe ni sur une ligne de commande ni dans un fichier : seulement dans cette requête à `127.0.0.1`, derrière le mot de passe du serveur ;
- un agent refusé (`Escouade::Denied`) ne reçoit rien ; si l'instance de son dossier avait gardé une entrée, elle est coupée (`disconnect`) ;
- un dossier n'a qu'un agent par serveur (`server::acquire`) : un second agent dans le même dossier (deux agents sans worktree) a son propre serveur, avec sa propre entrée. Un dossier en train d'être lâché (`dispose` sans réponse encore) compte comme occupé ;
- l'entrée part avec l'instance quand le dernier agent du dossier s'en va, comme le jeton à l'arrêt du process.

Ses outils s'appellent `escouade_<outil>` chez OpenCode, `mcp__escouade__<outil>` dans la conversation. Testé avec le faux (`opencode_tests::escouades_server_is_given_…` : un agent refusé et un agent permis de deux projets sur le même serveur, puis un second agent dans le même dossier, chacun pris pour lui-même par `whoami`) et pour de vrai (`real_opencode_writes_and_drives_escouade`, 2026-10-18 : `whoami` rend l'id de l'agent).

### Les textes rédigés (ESC-45)

« Modèle des textes rédigés » sur OpenCode : `opencode run` (`engine/opencode/run.rs`), essayé sur la 1.19.3 le 2026-10-18 :

```
opencode run --format json --model <fournisseur/modèle> --agent escouade-writer --title Escouade
```

- La question arrive sur son entrée (OpenCode l'ajoute au message), jamais sur la ligne de commande.
- `OPENCODE_CONFIG_CONTENT` : `model` et `small_model` (le modèle choisi), `mcp.escouade.enabled: false`, et un agent `escouade-writer` dont le `prompt` est la consigne (pas de prompt système d'OpenCode : 178 tokens en tout pour un nom, au lieu d'environ 10 700) et dont les outils sont coupés (`tools: {"*": false}`, `permission: {"*": "deny"}`) ; pour un texte écrit après lecture du dossier (`Weight::Reading`), seuls `read`, `glob`, `grep` et `list` sont permis. Un texte court se pose dans un dossier vide à lui (`escouade-opencode/writer` du dossier temporaire).
- La réponse est le texte du dernier message du flux `--format json` (`type: text`) ; un événement `error` (un modèle inconnu : `UnknownError`) refuse la réponse, avec son message.
- Chaque `opencode run` garde une session dans l'historique d'OpenCode : Escouade la supprime aussitôt (`opencode session delete <id>`, 1,2 s).
- **Le modèle** est toujours donné : celui de Réglages › Application › « Modèle » (`Settings.writer_model`, la liste des modèles des fournisseurs connectés) tant qu'il en fait partie, sinon le modèle par défaut (`Core::writer_model`, après `opencode models --verbose` si aucun n'est connu). Sans aucun modèle, aucun `opencode run` n'est lancé et le texte est refusé : OpenCode partirait sinon sur OpenCode Zen sans compte.

Essai réel (`real_opencode_writes_and_drives_escouade`, `qwen3-coder:30b-32k`) : « enregistrer-bouton-ne-fonctionne-pas » pour « Corrige le bouton Enregistrer qui ne sauve pas les réglages », l'historique d'OpenCode inchangé ensuite (`opencode session list`).

### Vue OpenCode (ESC-46)

`opencode attach <adresse du serveur> --session <session de l'agent> --dir <son dossier>`, dans un terminal intégré, avec l'environnement du compte et `OPENCODE_SERVER_PASSWORD` (jamais dans les arguments ni dans le journal). C'est un client de plus du serveur : Escouade garde le sien (`/global/event`), et le traducteur sait déjà ce que l'interface fait (un tour commencé ailleurs, une carte répondue ailleurs, ci-dessus). Le process de l'agent est démarré d'abord s'il ne tournait pas : l'interface a besoin de sa session. Une interface est arrêtée quand son agent n'a plus de process depuis 3 s, ou quand le process est sur un autre serveur (adresse ou mot de passe changés) ; jamais le serveur avec elle. Voir docs/ENGINES.md, « La vue OpenCode ».

### Les comptes

OpenCode n'a qu'un compte en 1.8, son Principal : sa config par défaut (`~/.config/opencode`, ou `$XDG_CONFIG_HOME/opencode`) et les fournisseurs qui y sont connectés. « Se connecter… » lance `opencode auth login` dans un terminal intégré ; OpenCode ne se connecte à aucun compte à lui. Le Principal n'est fait qu'au premier agent ou ticket OpenCode.

### Ce qui n'est pas pris en charge

OpenCode 2 (`@opencode/cli`, refusé avec sa raison), le mode « Auto » (OpenCode n'a pas de relecteur), un bac à sable (seules ses règles protègent), plusieurs comptes, les PDF joints, « Reprendre sur <compte> », les commandes `/` dans le composer, Remote Control, les tâches de fond et l'arrêt d'un sous-agent, et un message qui entre dans le tour en cours (il attend sa fin).

## Copilot SDK (ESC-39)

GitHub Copilot CLI est le quatrième harness (docs/ENGINES.md), piloté par un **client maison** du protocole de son SDK (choisi par l'utilisateur le 2026-10-18 sur la proposition d'ESC-23, ni la crate `github-copilot-sdk` ni ACP : docs/TODO-1.8.md, « Décisions »). Testé avec **Copilot CLI 1.0.98** (`tested()` : de la 1.0.98 à la 1.0.98, paquet npm `@github/copilot`), d'après les essais réels du 2026-10-18 sur un compte Copilot Free (ESC-23, docs/TODO-1.8.md, point 0, « Copilot CLI ») dont les flux sont dans `tests/fixtures/copilot/` et rejoués depuis `tests/fixtures/replays/copilot/`. Les schémas du protocole (SDK 1.0.22, protocole 3) sont dans `tests/fixtures/engines/copilot-1.0.98.api.schema.json` et `copilot-1.0.98.session-events.schema.json` ; `engine/copilot/schema_tests.rs` vérifie que les méthodes et les champs dont Escouade se sert y sont, et que celles qu'ils ne décrivent pas (`auth.getStatus`, `session.create`, `session.resume`, celles du SDK) ont été répondues aux essais réels.

### Lancement : un process par agent

```
copilot --server --stdio --no-auto-update --disable-builtin-mcps --disallow-temp-dir --secret-env-vars=GH_TOKEN,GITHUB_TOKEN,COPILOT_GITHUB_TOKEN
  [--additional-mcp-config @<fichier privé> | --disable-mcp-server escouade]
```

- Le programme est le binaire natif : sous Windows, le `copilot.exe` du paquet de la plateforme (`node_modules/@github/copilot/node_modules/@github/copilot-win32-x64/copilot.exe`, à côté du lanceur `copilot.cmd` ou `copilot.ps1`), sinon le `copilot` du PATH. Il est dans le Job de l'agent. Dans une build de debug, `ESCOUADE_COPILOT` (les e2e) donne le programme quand aucun chemin n'est réglé, ou `none` pour aucun.
- `--disable-builtin-mcps` : sans lui, Copilot branche son serveur MCP GitHub avec le compte. `--disallow-temp-dir` : sans lui, le dossier temporaire du système est ouvert sans demande. `--secret-env-vars` : ces variables sont retirées des commandes et des serveurs MCP de l'agent ; pas `ESCOUADE_MCP_TOKEN`, que Copilot ne mettrait plus dans l'en-tête de l'entrée d'Escouade (essayé, ESC-40 : voir « Le serveur MCP d'Escouade » plus bas).
- Pour un compte autre que Principal (une `COPILOT_HOME` à lui), les jetons de GitHub de l'environnement d'Escouade (`COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`) ne sont pas transmis : Copilot les préfère à sa connexion, et tous les comptes seraient alors le même.
- **Pas de bac à sable en mode serveur** dans la 1.0.98 (essayé : `sandboxApplied: false` à chaque commande, `--sandbox` et `settings.json` ou pas) : seules les règles d'Escouade protègent, et le menu des modes le dit.
- Le message est encadré par des en-têtes `Content-Length` (JSON-RPC 2.0). `connect` (`protocolVersion: 3`, sinon refusé avec la commande de mise à jour), puis `auth.getStatus` : **jamais un jeton dans un journal** (`account.getAllUsers` et `account.getCurrentAuth` le rendent en clair : Escouade n'appelle ni l'un ni l'autre, et ne journalise que la méthode d'un message). Non connecté, l'agent ne démarre pas : le process s'arrête et sa raison est dans la conversation (« connecte-le dans Réglages › Comptes », ESC-40). Connecté par le compte du GitHub CLI (`authType: gh-cli`, ce que Copilot fait seul faute de connexion à lui) : Principal démarre et la conversation le dit ; un autre compte est tenu pour non connecté (ce compte serait le même pour tous).
- L'arrêt doux envoie `runtime.shutdown`, puis ferme l'entrée.

### Les sessions

| Étape | Requête | Ce qu'Escouade y met |
|---|---|---|
| Conversation neuve | `session.create` | `workingDirectory` (le dossier de l'agent), `model` (toujours : sans lui, `auto` choisit seul), `reasoningEffort`, `streaming`, `requestPermission`, `requestUserInput`, `requestElicitation`, `requestExitPlanMode`, `systemMessage` (`append`, les consignes ajoutées) |
| Reprise | `session.resume` | les mêmes, `systemMessage` compris (Copilot l'oublie sinon, essayé) ; introuvable, une neuve est ouverte et la conversation dit « La session Copilot n'a pas pu être reprise » ; puis `session.model.switchTo` sur le modèle de l'agent |
| Copie | `sessions.readPersistedEvents`, `sessions.fork`, puis `session.resume` | Copilot copie les événements d'avant celui qu'il reçoit (`toEventId`, exclusif) : Escouade lui donne celui qui suit le dernier événement gardé de l'original à la fin de son dernier tour (`last_entry`), aucun quand c'est le dernier |
| Modes | `session.permissions.setMode`, `session.mode.set` | voir « Les modes » ; aussitôt, même pendant un tour |
| Serveur MCP | `session.mcp.disable` | `escouade` : une entrée de l'utilisateur de ce nom est coupée pour la session (le serveur d'Escouade vient avec ESC-40 ; `--disable-mcp-server` est sans effet en mode serveur, essayé) |
| Modèles | `models.list`, `session.model.list` | le menu du composer (`Ready.catalog`), voir plus bas |
| Un message | `session.send` | `prompt` (le texte, les fichiers texte joints en texte), `attachments` (les images, en `blob`), `mode` : `immediate` pendant un tour (le tour en cours le lit tout de suite : `caps.mid_turn` `immediate`), `enqueue` sinon ; refusé, le tour finit en erreur avec le message de Copilot |
| Interrompre | `session.abort` | Copilot tue la commande en cours (`abort`, `agent.interrupted`), puis `session.idle` avec `aborted` |
| Modèle, effort | `session.model.switchTo` | `modelId`, `reasoningEffort` : aussitôt |
| Permission | `session.permissions.handlePendingPermissionRequest` | `approve-once` ; `approve-for-session` avec ce que Copilot retient (`commands` et leurs `commandIdentifiers`, `read`, `write`, `mcp` et son outil, le `domain` d'une adresse) ; `reject` avec le message de refus. Jamais `approve-permanently` ni `approve-for-location` (une règle durable dans la config de Copilot : décidé le 2026-10-18) |
| Question | `session.ui.handlePendingUserInput` | `answer`, `wasFreeform` (une réponse qui n'est pas un des choix) ; la requête `userInput.request` de la même question reçoit la même réponse |
| Formulaire | `session.ui.handlePendingElicitation` | `action: accept`, `content` : chaque champ typé comme son schéma (`number`, `integer`, `boolean` par « Oui », une liste) |
| Fin d'un plan | `session.ui.handlePendingExitPlanMode` | « Approuver le plan » : `approved`, `selectedAction: interactive`, le mode passe à « Demander » ; « Approuver et accepter les édits » : `autoApproveEdits`, « Édits auto » ; « Continuer à planifier » : `approved: false` et le message ; la requête `exitPlanMode.request` reçoit la même réponse |
| Tâches | `session.plan.readSqlTodosWithDependencies` | lues à chaque `session.todos_changed` (une à la fois, relues si elles ont changé pendant) |
| Titre | `session.name.set` | `name` |

**La question et la fin d'un plan arrivent deux fois** : l'événement de la session (`user_input.requested`, `exit_plan_mode.requested`) et une requête de Copilot au client (`userInput.request`, `exitPlanMode.request`). Escouade en fait une seule carte, celle de l'événement, et répond aux deux : la première réponse gagne (l'autre reçoit `success: false`). Toute autre requête de Copilot au client est refusée (`-32601`).

**Les modèles** : `models.list` (ou `session.model.list`) donne chaque modèle avec ses efforts (`supportedReasoningEfforts`, `defaultReasoningEffort`), s'il lit les images (`capabilities.supports.vision`) et son **multiplicateur de facturation** (`billing.multiplier`), écrit à côté de son nom dans le menu (`×3`, `×0,33`) ; un modèle que sa politique désactive est écarté. Sur un compte Free, les deux listes sont vides (essayé) : le menu garde les modèles déclarés (`gpt-6-luna`, `gpt-5-mini`, ceux des essais), chacun avec sa catégorie de prix (`modelPriceCategories` : « coût bas »). Le premier est celui d'un nouvel agent ; `auto` n'est jamais proposé.

### Les modes

En `manual`, Copilot demande tout, lectures comprises : les règles d'Escouade (`cp_safe` d'`agent/copilot.rs`) répondent sans carte aux demandes sûres, comme le bac à sable de Codex.

| Escouade | Mode de l'agent | Permissions | Sans carte |
|---|---|---|---|
| Demander | `interactive` | `manual` | les lectures et écritures du dossier de l'agent |
| Accepter les modifications | `interactive` | `manual` | les mêmes, plus `git add` et `git commit` de son worktree |
| Plan | `plan` | `manual` | les lectures du dossier de l'agent |
| Auto | `autopilot` (il enchaîne jusqu'à `task_complete`) | `manual` | comme « Accepter les modifications » |
| Sans permissions | `interactive` | `allow-all` | tout (Copilot ne demande rien) |

`assisted` n'est pas proposé : expérimental (`--experimental`), et son juge a échoué à chaque demande sur un compte Free. Un changement de mode de Copilot (`session.mode_changed`) revient dans celui de l'agent : sorti du mode Plan, « Demander ».

| Copilot (`session.event`) | Dans la conversation |

| `assistant.message_delta`, `assistant.message` | un `text`, en direct puis entier ; le dernier, la réponse du tour |
| `assistant.reasoning_delta`, `assistant.reasoning` | un `thinking` (un raisonnement donné entier sans mots, le blob opaque du modèle, est écarté) |

| `*.completed` | une carte répondue autrement (par la requête au client, ou close par Copilot) dit la réponse et se ferme |
| `session.todos_changed` | les tâches lues (`escouade.todos`) dans le bandeau « Plan » (`pending`, `in_progress`, `done`) |

| `session.usage_info` | la fenêtre de contexte (`tokenLimit`, `currentTokens`) |
| `session.model_change` | le modèle de l'agent (jamais `auto`) |
| `session.compaction_complete` | « Contexte compacté » |
| `abort`, `session.error` | un tour interrompu ; une erreur, dite à la fin du tour ; `errorType: quota` (crédits épuisés, sauf `billing_not_configured`) ou une limite hebdomadaire (`rate_limit`, `user_weekly_rate_limited`) : le tour finit « limité », et reprend seul à la remise à zéro des crédits (ESC-40) |

Un flux enregistré (`{"dir", "msg"}` par ligne) se rejoue tel quel : les événements, la session qu'a ouverte la réponse à `session.create` ou `session.resume`, et les tâches lues.

### Les comptes (ESC-40)

Un compte est une `COPILOT_HOME` : Principal est `~/.copilot`, lancé sans la variable ; les autres sont sous `<données>/copilot/<nom>`. Un nouveau compte peut reprendre de Principal `mcp-config.json`, `copilot-instructions.md`, `agents` et `skills` (liés ou copiés), jamais `config.json` (les utilisateurs connectés, et le jeton lui-même sans trousseau), `settings.json` (ses dossiers de confiance) ni ses sessions. Il se connecte par `copilot login` (dans le dossier du compte, depuis un terminal intégré, comme un compte Claude Code) : Escouade ne prend ni ne recopie aucun jeton.

- **Qui est connecté** : `config.json` de la `COPILOT_HOME` (du JSON précédé de commentaires `//`) nomme les utilisateurs connectés (`loggedInUsers`, d'après la doc du dossier de config de Copilot CLI ; `lastLoggedInUser`, et les formes `logged_in_users` / `last_logged_in_user`, lus aussi) : leur `login` est ce que montre le panneau des comptes (`@login`) et l'empreinte de la connexion, jamais un jeton. Le jeton est dans le trousseau du système (sinon dans ce fichier) : un dossier connecté à un autre utilisateur GitHub est un autre compte.
- **Deux comptes ne se mélangent pas** : un compte à lui ne reçoit pas les jetons de l'environnement d'Escouade (voir « Lancement »), et un `gh-cli` y vaut « non connecté » (`process::signed_in`), au démarrage d'un agent comme à la lecture de ses crédits.
- **Pas essayé avec un vrai second compte GitHub** (il n'y en a pas ici) : la forme exacte de `loggedInUsers` après un vrai `copilot login` reste à voir (l'ajout s'essaie jusqu'à l'écran de connexion, qui donne un code à saisir sur github.com/login/device).

### Les crédits du mois (ESC-40)

`caps.quota` vaut `credits` : une barre « crédits » (`QuotaMeter` sans durée), ce qui est utilisé (`100 − remainingPercentage`) jusqu'à la remise à zéro.

| Source | Quand | Ce qu'Escouade en lit |
|---|---|---|
| `assistant.usage.quotaSnapshots` | à chaque appel au modèle | `chat` (les crédits d'IA, facturés par token), sinon `premium_interactions` ; `resetDate` (le 1ᵉʳ du mois suivant, 00:00 UTC) ; rien pour un plan sans limite (`isUnlimitedEntitlement`) |
| `session.quota.get` | `read_usage` d'un agent vivant | `snapshots`, avec `resetDateEpochMs` |
| `account.getQuota` | un compte sans agent, au plus toutes les 5 min, par un `copilot --server --stdio` du compte lancé puis arrêté (`connect`, `auth.getStatus`, `account.getQuota` : aucune session, aucun modèle) | `quotaSnapshots` ; son `resetDate` est l'heure du relevé (essayé) : le 1ᵉʳ du mois suivant à la place |

Au-delà de « Pause au-delà du quota », le pilote auto se met en pause (`PauseReason::Credits`) jusqu'à la remise à zéro. Les limites par session et par semaine des offres Pro et Pro+ n'ont pas de source lisible (le compte Free n'en a pas) : une limite hebdomadaire qui arrête un tour le finit « limité », sans heure de reprise connue.

### Le serveur MCP d'Escouade (ESC-40)

- **Donné** : `--additional-mcp-config @<données>/mcp/<agent>.json` (le fichier privé de `grant_file`, oublié à l'arrêt du process), dont l'entrée `escouade` (`type: http`, l'URL du serveur, `tools: ["*"]`) a l'en-tête `Authorization: Bearer ${ESCOUADE_MCP_TOKEN}` : le jeton n'est ni dans le fichier ni sur la ligne de commande, seulement dans l'environnement du process (`ESCOUADE_MCP_TOKEN`).
- Essayé sur la 1.0.98 sans dépenser de crédit (la connexion se fait à `session.create`) : le serveur reçoit le bon jeton à chaque requête (`server/discover`, `initialize`…) ; **avec `ESCOUADE_MCP_TOKEN` dans `--secret-env-vars`, l'en-tête arrive sans lui** (d'où sa sortie de la liste) ; une entrée `escouade` du `mcp-config.json` de l'utilisateur ne l'emporte pas sur celle d'`--additional-mcp-config` (« augments config from ~/.copilot/mcp-config.json »).
- **Refusé** : `--disable-mcp-server escouade`, sans effet en mode serveur (essayé, ESC-23), puis `session.mcp.disable` sur la session, qui coupe une entrée `escouade` de l'utilisateur. Donné, la session ne coupe rien.
- La déclaration pour l'utilisateur (son `mcp-config.json`) : « Serveur MCP d'Escouade » › « Déclaration dans les harness ».

### Les textes rédigés (ESC-40)

`copilot -p`, essayé le 2026-10-18 sur la 1.0.98 (compte Free) :

```
copilot --output-format json --stream off --no-auto-update --disable-builtin-mcps --no-custom-instructions --disallow-temp-dir
  --model gpt-5-mini --reasoning-effort low --available-tools=escouade-aucun-outil
  --session-id=<uuid> --log-dir <dossier temporaire>          (la question par l'entrée)
```

- **La question par l'entrée** (« piped stdin »), jamais sur la ligne de commande ; `-p` n'a pas de prompt système : les consignes la précèdent entre `<instructions>`. La réponse est le dernier `assistant.message` (sans `agentId`) du flux JSON (une ligne par événement, puis `result`) ; un `session.error` sans réponse refuse avec son message.
- **Sans outil** : `--available-tools=` (vide) les laisse tous (essayé : `powershell`, `view`, `edit`, `task`… au prompt) ; une liste qui ne nomme aucun outil de Copilot n'en laisse aucun, et un texte court coûte six fois moins (0,04 crédit au lieu de 0,23). Un texte qui lit son dossier a `view`, `glob` et `grep`, permis sans question (`--allow-tool`).
- **Le modèle est toujours donné** (`gpt-5-mini`, « Copilot (GPT-5 mini) ») : sans lui, `auto` choisit seul. Mais un compte Free n'accepte aucun `--model` nommé (« Model "…" from --model flag is not available », rien sur la sortie) : la question est alors reposée sur `auto` (qui y a choisi `mai-code-1.1-flash`).
- Chaque question est une session du compte : nommée (`--session-id`), elle est retirée de `session-state/` une fois répondue, et son journal (`--log-dir`) est gardé à part puis retiré. Sur le compte de l'agent ou du projet, comme Codex ; pour un compte à lui, les jetons de l'environnement ne sont pas transmis (vides).

### Vue Copilot CLI (ESC-48)

`copilot --resume <session>` (ou `--session-id <uuid>` pour une session neuve), avec les hooks d'un plugin propre à l'agent (`--plugin-dir`), les options du serveur, le mode, le modèle et l'effort de l'agent, dans un terminal intégré ; la conversation et le coût se remplissent depuis `events.jsonl`. Elle reçoit le même serveur MCP et les mêmes garde-fous des comptes que le serveur. Les choix et les essais : docs/ENGINES.md, « La vue Copilot ».

### Ce qui n'est pas pris en charge

Le mode `assisted` (expérimental), un bac à sable en mode serveur, « Toujours autoriser » (`approve-permanently`, `approve-for-location`), `auto` comme modèle, les PDF joints, « Reprendre sur <compte> », les commandes `/` dans le composer, Remote Control, les tâches de fond et l'arrêt d'un sous-agent. Les limites par session et par semaine des offres Pro et Pro+ n'ont pas de source lisible. En vue Copilot CLI, les consignes ajoutées et le bandeau « Plan » ne suivent pas.

## Serveur MCP d'Escouade

Escouade sert ses outils aux harness (un terminal, une app, ses propres agents) en MCP « Streamable HTTP », par le SDK officiel `rmcp` (3.5) derrière `hyper` (`src-tauri/src/mcp/`). Il tourne quand « Les agents peuvent piloter Escouade » est activé, et s'arrête avec l'app.

### Transport et garde-fous

- `http://127.0.0.1:<port>/mcp`, sur la boucle locale seulement. Port choisi au premier démarrage entre 47000 et 47999, puis gardé (`Settings.mcpPort`) ; s'il est pris, un autre est choisi et enregistré.
- Sans état (pas de `Mcp-Session-Id`), réponses en JSON (pas de flux SSE). Les deux poignées de main passent : `initialize` en `2025-11-25`, et le chemin `2026-07-28` (sonde `server/discover`, puis chaque requête porte sa version dans `_meta` et l'en-tête `MCP-Protocol-Version`, sans `initialize`), celui que prend Claude Code 2.1.296.
- Chaque requête, avant `rmcp` :
  - `Host` (ou l'autorité d'une URI absolue) autre que `127.0.0.1:<port>` ou `localhost:<port>`, ou absent → 403 ;
  - un en-tête `Origin` (une page web) → 403 ;
  - `Authorization: Bearer <jeton>` absent ou inconnu → 401 avec `WWW-Authenticate: Bearer` (comparaison à temps constant) ;
  - un autre chemin que `/mcp` → 404.
- Jetons : celui de Claude hors Escouade (32 octets aléatoires en base64url, dans le trousseau, entrée `mcp`, ou dans `mcp-token.json`, lisible par son seul propriétaire, quand le trousseau refuse) ; celui de chaque process d'un agent d'Escouade, en mémoire et dans le fichier de config que ce process reçoit (voir « Les agents d'Escouade »). Le jeton dit qui appelle : un outil le sait (`Caller`).
- Une connexion a 10 s pour envoyer les en-têtes d'une requête (et reste 10 s au plus sans requête) ; 64 connexions à la fois au plus, les suivantes attendent. Le corps d'une requête pèse 32 Mio au plus (le SDK en refuse 4 par défaut, avec un 413) : les 18 Mo d'images qu'un ticket prend, donnés en base64 à `create_ticket` ou `update_ticket`, y tiennent (et le total est tenu avant de lire ou de décoder une image de plus : voir « Les images d'un ticket aussi ») ; un autre fichier plus gros que ce qu'une requête porte se donne par son chemin (`path`, voir « Les autres fichiers d'un ticket aussi ») ; le jeton est vérifié avant que le corps soit lu. Une requête dont les arguments ne collent pas au schéma n'est jamais renvoyée au client, même à 32 Mio (voir « Réponses et erreurs »).
- Journal d'activité : chaque appel d'outil (refus et erreurs compris, y compris un outil inconnu ou des arguments qui ne collent pas au schéma) et chaque requête refusée, sans jamais les jetons ; les 200 derniers, en mémoire. Un appel dont les arguments ne collent pas au schéma est noté d'un message fixe, « Appel refusé par le serveur : les arguments ne correspondent pas au schéma de l’outil » (« Call refused by the server: the arguments do not match the tool’s schema » en anglais), qui ne cite aucune valeur : le message d'erreur de `serde` en contient (un chemin, le début d'un base64), et il n'entre jamais au journal. Pour chaque `set_board` réussi, le résumé garde ce qui a été demandé et le journal garde chaque champ changé avec sa valeur avant et après (« model: opus → sonnet · effort: (défaut) → medium »), ou « Aucun changement » quand rien ne change. Pour les images d'un ticket, le résumé dit combien, jamais lesquelles ni leur contenu, ni un chemin : `images: 2` (`create_ticket`), `addImages: 1 · removeImages: 2` (`update_ticket`), `images: 3` (`split_ticket` : le total des références données aux sous-tickets, rien quand l'argument est omis partout), le ticket et le `file` ou l'`index` demandés (`get_ticket_image`). De même pour les autres fichiers d'un ticket (ESC-108) : `files: 2` (`create_ticket`, et `split_ticket` pour le total des références), `addFiles: 1 · removeFiles: 2` (`update_ticket`), le ticket, le `file` ou l'`index`, l'`offset` et les `bytes` demandés (`get_ticket_file`), jamais un contenu ni un chemin. Pour les sous-agents et les tâches de fond (ESC-107), le résumé dit l'agent et l'`id` visé (`list_background_work` : l'agent seul), jamais le texte d'un message (`message_subagent`) ni une sortie (`get_background_output`) ; un `bytes` illisible (`"abc"`, `-1`) y entre sous le message fixe ci-dessus, sans sa valeur ; l'issue (« Fait », « Refusé », « Erreur ») s'y ajoute comme pour tout appel.

### Déclaration dans les harness (« Les agents peuvent piloter Escouade »)

Un seul interrupteur (Réglages › Harness › « Serveur MCP », réglage `mcpEnabled`, enregistré tout de suite par `mcp_set_enabled`, hors du brouillon des réglages ; ESC-119). Activé, le serveur tourne (jeton et port assurés), il est donné aux agents d'Escouade (« Les agents d'Escouade », ci-dessous), et Escouade le déclare, avec le jeton de « Claude (hors Escouade) », dans chaque harness installé, pour **chaque compte actif** (ou son Principal tant qu'aucun compte n'est enregistré), une exécution à la fois, sur sa propre tâche (`mcp/install.rs`, `Core::declare_now`). Un harness installé plus tard est déclaré au retour du focus sur la fenêtre (une fois par minute au plus) ; un compte ajouté, à la sauvegarde.

| Harness | Où | Comment |
|---|---|---|
| Claude Code | `.claude.json` du compte | `claude mcp add` et `remove` (ci-dessous) |
| Codex | `config.toml` du `CODEX_HOME` (`~/.codex/config.toml` pour Principal) | Escouade écrit `[mcp_servers.escouade]` (`url`, `http_headers`) |
| OpenCode | `opencode.json` (ou l'`opencode.jsonc` présent) sous `$XDG_CONFIG_HOME/opencode` | Escouade écrit `mcp.escouade` (`type: remote`, `url`, `headers`) |
| Copilot CLI | `mcp-config.json` du `COPILOT_HOME` (`~/.copilot` pour Principal) | Escouade écrit `mcpServers.escouade` (`url`, `headers`) |

Pour Codex, OpenCode et Copilot CLI, le fichier garde tout le reste (commentaires, ordre, indentation, fins de ligne) et redevient celui d'avant à l'octet près quand l'entrée est retirée ; un fichier qui n'est pas un TOML ou un JSON valide n'est pas touché, et l'onglet donne l'entrée à coller. Le détail de cette écriture (`UserConfig`, `engine::jsonc`, les liens des comptes partagés) est dans docs/ENGINES.md, « Les agents peuvent piloter Escouade », qui fait foi. Essayé pour de vrai, chacun lancé hors d'Escouade avec la seule entrée écrite par Escouade (ESC-50, ESC-119) : Codex 0.163.0 liste les outils, OpenCode 1.19.3 et Copilot CLI 1.0.98 appellent `list_projects`.

Pour Claude Code :

- Commande, lancée avec le `claude` du compte (le sien, sinon celui des réglages), l'environnement des réglages réseau et `accounts::launch_env` (le `CLAUDE_CONFIG_DIR` du compte ; **jamais** pour Principal), le dossier de données pour dossier courant, 30 s au plus (le process et ce qu'il a lancé sont tués au-delà) : `claude mcp add --scope user --transport http escouade http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <jeton>"`. `--header` prend tous les arguments qui suivent : il est donc **en dernier**.
- Comparaison : Escouade lit l'entrée `mcpServers.escouade` du `.claude.json` du compte (`{ "type": "http", "url", "headers": { "Authorization": "Bearer …" } }`), et n'utilise la CLI que pour écrire (`claude mcp get` se connecte au serveur : lent, et une connexion qui échoue ne dit rien de l'entrée). Ce fichier est `<dossier du compte>/.claude.json`, et pour Principal `$CLAUDE_CONFIG_DIR/.claude.json` si l'environnement de l'app définit la variable (ses processus l'héritent), sinon `~/.claude.json` (à côté de `~/.claude/`, pas dedans).
  - absente : `add` ;
  - identique (même URL, même jeton) : rien n'est lancé ;
  - différente (autre port, autre jeton, autre type, pas d'en-tête) : `claude mcp remove escouade --scope user`, puis `add` (un second `add` du même nom échoue : « already exists in user config », code 1) ; si le `remove` échoue, l'`add` ne part pas.
- Un compte ajouté (« Ajouter un compte… »), réactivé, ou dont le `claude` a changé reçoit la déclaration à l'enregistrement des réglages (`save_settings` appelle `sync_mcp`, qui la fait suivre) ; un compte désactivé n'est plus listé et son entrée reste telle quelle. Un changement de port (le port enregistré était pris au redémarrage du serveur : `sync_mcp` en choisit un autre) la refait partout. Au démarrage de l'app, elle est relue : des entrées à jour ne lancent rien.
- Désactiver : le jeton externe change **d'abord** (`McpServer::renew_external_token` : l'ancien n'ouvre plus rien tout de suite, quoi que fassent les commandes qui suivent, même lentes ou interrompues par un plantage), les jetons des agents sont oubliés avec le dossier `mcp/` (`McpServer::turned_off` ; `Core::mcp_turned_off` marque les process vivants comme sans serveur : rallumé, chacun a « Outils d'Escouade au prochain démarrage »), **puis** `claude mcp remove escouade --scope user` pour **chaque** compte (actif ou non ; un `.claude.json` absent ou sans l'entrée ne lance rien ; un `.claude.json` illisible, qui pourrait la contenir, lance la commande et son échec est une erreur ; un `remove` qui échoue alors que l'entrée a disparu n'en est pas une). Même si une entrée reste (un refus, un `claude` disparu), son jeton est mort. Désactivé puis réactivé avant que l'exécution n'ait lieu : le jeton est changé et les entrées sont remplacées par le nouveau.
- Supprimer un compte (« Comptes Claude ») : son dossier reste sur le disque, et son entrée du serveur avec lui, qui ouvrirait le serveur tant que l'interrupteur est activé. Escouade la retire donc de son `.claude.json` (`Core::withdraw_removed` : `claude mcp remove` avec le `claude` et le `CLAUDE_CONFIG_DIR` du compte retiré, sur sa propre tâche, après la déclaration en cours), que l'interrupteur soit activé ou non (une entrée laissée par une activation passée part aussi) ; un échec est seulement journalisé. Le jeton ne change pas : les autres comptes le gardent.
- Le résultat de chaque compte (`mcp_declare_status`, événement `mcpDeclared`) : `{ account, ok, error, command }`. `error` est ce que Claude Code a répondu (stderr, sinon stdout, une ligne de 300 caractères au plus, **le jeton qu'il citerait masqué** `••••••••`), « Claude Code introuvable… » ou « pas de réponse de claude en 30 s » ; `command` est la commande à lancer à la main **dont le jeton est masqué** (`Bearer ••••••••`) : le vrai jeton ne part jamais avec l'état, les événements ni les journaux (`Entry` n'imprime pas non plus son jeton). « Copier la commande » demande la vraie, au moment du clic, à `mcp_manual_command(account)` (refusée tant que l'interrupteur est éteint ou que le serveur ne tourne pas) : PowerShell sous Windows (`$old = $env:CLAUDE_CONFIG_DIR; $env:CLAUDE_CONFIG_DIR = '…'; claude mcp add …; $env:CLAUDE_CONFIG_DIR = $old`, pour que le terminal de l'utilisateur ne reste pas sur ce compte), shell POSIX ailleurs (`CLAUDE_CONFIG_DIR='…' claude mcp add …`), précédée d'un `claude mcp remove …` quand une entrée est déjà là ; la fenêtre dit pour quel shell elle est écrite.
- Le jeton est écrit **en clair** dans le `.claude.json` de chaque compte (c'est ce que dit l'onglet) ; `headersHelper` est écarté pour la 1.7.

### Les agents d'Escouade

L'interrupteur « Les agents peuvent piloter Escouade » (`mcpEnabled`) sert les agents de tous les projets, quel que soit leur harness : il n'y a pas de réglage par projet (« Les agents peuvent utiliser Escouade », `Project.agentsUseEscouade` jusqu'à la 1.7, a disparu avec ESC-91 ; un `state.json` qui l'a encore se charge sans lui). Ce que reçoit chaque lancement du process `claude` d'un agent (`Core::agent_access`, à la fin des arguments : `--disallowedTools` et `--mcp-config` prennent plusieurs valeurs). Depuis ESC-33, le cœur décide et le moteur de l'agent dit comment (`Engine::grant_file`, `refusal`, `escouade_launch` : docs/ENGINES.md, « Le serveur MCP d'Escouade ») ; pour Claude Code, rien n'a changé :

| Interrupteur | Serveur | Arguments |
|---|---|---|
| désactivé (défaut) | arrêté | `--settings <dossier de données>/mcp-refused.json --disallowedTools mcp__escouade` |
| activé | arrêté (son démarrage a échoué) | `--settings <dossier de données>/mcp-refused.json --disallowedTools mcp__escouade` (il n'y a rien à joindre) |
| activé | en marche | `--mcp-config <dossier de données>/mcp/<id de l'agent>.json` |

Les outils d'Escouade sont donc refusés à un agent à chaque fois qu'il n'a pas de jeton à lui, serveur arrêté compris : une entrée `escouade` peut rester déclarée dans la config de Claude Code de l'utilisateur (son retrait a échoué, ou l'utilisateur l'a écrite), que l'agent hérite, et il agirait alors sous l'identité « Claude (hors Escouade) ». Même cause pour un jeton d'agent qui n'a pas pu être écrit.

- **Le serveur tenu à l'écart** (`Engine::refusal` de Claude Code, `engine/claude/mcp.rs`). `--disallowedTools mcp__escouade` seul ne retire que les outils : Claude Code connecte quand même l'entrée et donne à l'agent les instructions du serveur, sans aucun de ses outils (ESC-91 : des agents qui lisaient « Escouade runs Claude Code agents… Its tools read and act on its projects » croyaient à une panne). Le refus passe donc aussi `--settings` avec `{"deniedMcpServers": [{"serverName": "escouade"}]}`, dans `<dossier de données>/mcp-refused.json` (le même pour tous, écrit quand il n'est pas comme il faut ; un chemin, pas du JSON en ligne, pour un lanceur `.cmd`). Claude Code ne lit que le **dernier** `--settings` : en vue Claude Code, le refus entre dans le fichier des hooks (`tui::tui_settings`, `<dossier de données>/tui/<id>.json`). Si le fichier ne s'écrit pas, l'agent part avec `--disallowedTools` seul (journalisé).

### Réponses et erreurs

- Un outil répond un seul bloc `text` : du JSON, clés en camelCase, dates en millisecondes depuis l'epoch. Seul `get_ticket_image` répond autrement : un bloc `image` (le contenu en base64 et son type MIME) suivi d'un bloc `text` de JSON.
- Un refus ou un échec est un résultat d'erreur que le modèle lit (`isError: true`, le texte dit pourquoi, dans la langue de l'interface). Des arguments qui ne collent pas au schéma donnent aussi un résultat d'erreur (texte de `rmcp`, « failed to deserialize parameters: … »), mais **coupé avant toute valeur que le client a donnée** (avant le premier guillemet droit ou le premier accent grave, dont `serde` entoure les valeurs, comme dans `invalid type: string "…"`), suivi d'une phrase fixe qui dit de relire le schéma de l'outil, et de 300 caractères au plus en tout, quelle que soit la taille de la requête : jamais un chemin ni du base64 renvoyés au client ; un outil inconnu, une erreur JSON-RPC.
- Résolution des noms : un projet par son id ou son nom (sans casse) ; un agent par son id (archivés compris) ou son nom (sans casse, parmi les agents non archivés, sinon parmi les archivés), dans le projet donné s'il y en a un ; un ticket par son id ou sa clé (sans casse). Un nom inconnu ou ambigu est une erreur qui le dit et liste 5 choix au plus (ceux dont le nom contient le texte demandé d'abord, « … » s'il y en a d'autres ; quand tous les agents en jeu sont archivés, l'erreur le dit et les propose), par exemple « Plusieurs projets s’appellent « demo » : demo (id 1a2b), demo (id 3c4d). Donne son id. ».

- **Projets privés** (ESC-139) : pour un agent d'Escouade, la résolution et les listes ne portent que sur les projets qu'il voit (`mcp::resolve::Sight`, relu à chaque appel) : ceux qui ne sont pas privés, pour un agent d'un projet qui ne l'est pas ; le sien seul, pour un agent d'un projet privé. Ce qu'il ne voit pas répond la même erreur, au mot près, qu'un nom que rien ne porte, et n'apparaît pas dans les choix qu'elle liste. `list_projects`, `list_agents` et `list_requests` sans argument ne donnent que ce qu'il voit. Le jeton de « Claude (hors Escouade) » voit tout. Les instructions du serveur le disent : « An agent of Escouade acts on its own project and on every project that is not private; a private project is known to its own agents alone, who know and act on no other project. »

### Outils qui agissent

Annotés `readOnlyHint: false`, `openWorldHint: false` (`stop_agent`, `stop_background_work`, `answer_permission`, `approve_ticket` et `delete_ticket` : `destructiveHint: true`, les autres `false` ; `approve_ticket` seul : `openWorldHint: true`, parce qu'il peut pousser une branche et ouvrir une pull request). Il est suivi de l'auteur : « <commentaire> (renvoyé par <auteur> via Escouade) » (« (sent back by <author> through Escouade) », dans la langue des textes pour Claude), le point final du commentaire retiré ; il n'est jamais pris pour les mots de l'utilisateur. Un commentaire vide est une erreur (« Dis ce qui ne va pas. »). |
| `resume_ticket` | `ticket` | le ticket comme `get_ticket`, plus `since` (le curseur de `wait_ticket` du ticket tel qu'il était avant l'action, comme pour `approve_ticket`). C'est « Reprendre » d'un ticket « En cours » bloqué : son agent poursuit, ou le ticket repart quand son agent a disparu. |
| `resolve_conflict` | `ticket` | le ticket comme `get_ticket`, plus `since` (le curseur de `wait_ticket` du ticket tel qu'il était avant l'action, comme pour `approve_ticket`). C'est « L'agent résout » d'un ticket « À tester » arrêté sur un conflit de merge : la cible est fusionnée dans sa branche et l'agent est invité à résoudre les conflits (avec la stratégie rebase : à rebaser), puis à finir par son rapport. Refusé sans conflit (« Ce ticket n’a pas de conflit à résoudre. »). |
| `dismiss_block` | `ticket` | le ticket comme `get_ticket`, plus `since` (le curseur de `wait_ticket` du ticket tel qu'il était avant l'action, comme pour `approve_ticket`). C'est « Annuler » sur un ticket « À tester » bloqué (un conflit, une étape en échec) : le blocage disparaît, le ticket reste « À tester », rien d'autre ne change. |
| `delete_ticket` | `ticket` | `{ key, deleted: true, agentArchived }`. C'est « Supprimer » de la fenêtre, quelle que soit la colonne : `agentArchived` est vrai quand le ticket avait un agent qui est archivé avec lui : celui d'un ticket « En cours » ou « À tester », et celui d'un ticket « Terminé » laissé dans son worktree quand le Kanban supprime les worktrees (« Supprimer le worktree d'un ticket terminé ou supprimé », allumé par défaut) ; avec ce réglage, les worktrees de ses agents sont supprimés, sauf ceux qui gardent des changements non commités ou des commits ni mergés ni poussés (voir SPEC, *Worktrees des tickets finis*) ; les tickets qui venaient après lui ne l'attendent plus. Irréversible. Refusé tant que la validation du ticket tourne (« La validation de ce ticket est en cours : attends sa fin pour le supprimer. »). |

Garde-fous, ceux de la fenêtre et du pilote auto ; un refus est un résultat d'erreur qui dit pourquoi, noté « refusé » dans le journal d'activité :

- **Pause du pilote auto, compte par compte** (un compte est retenu par une fenêtre de quota au-delà de « Pause au-delà du quota », par la pause après une limite d'usage, ou par un agent à lui qui attend son quota) : `start_ticket` et `create_agent` ne sont refusés que si aucun compte n'est utilisable pour le projet (son « Compte préféré », sinon tous les comptes actifs : un seul libre suffit, comme pour le pilote auto) ; `send_message` et `message_subagent` (qui coûte un tour de l'agent) sont refusés quand le compte de l'agent destinataire est retenu, pas quand un autre l'est ; `message_subagent` le vérifie en dernier, après ses autres refus et erreurs (un client ne doit pas attendre la fin de la retenue pour être refusé de toute façon). Le message dit jusqu'à quand (« Le pilote auto est en pause jusqu'à 14:30 : … », « 2026-10-12 14:30 » un autre jour), celui du premier compte qui sera libre, et, avec plusieurs comptes, de quel compte il s'agit pour `send_message`. Rien n'est modifié (le ticket n'est pas marqué lancé).
- **Maximum en parallèle du projet** (« En parallèle », 1 à 6, 2 par défaut) : `start_ticket` est refusé quand autant de tickets sont « En cours » sans être bloqués, `create_agent` quand autant d'agents non archivés du projet travaillent (en cours ou en attente d'une réponse). Deux `create_agent` simultanés ne trouvent pas la même place libre.
- **Un ticket qui attend d'autres tickets** (non « Terminé ») n'est pas lancé : la fenêtre demande d'abord à l'utilisateur de confirmer, ici le refus nomme ces tickets ; `update_ticket` avec `after` leur retire la dépendance. Un Kanban qui ne démarre rien (branche cible introuvable…) dit pourquoi.
- **Un ticket qui a démarré** : ni modifié (`update_ticket`, images et fichiers compris : il garde les siens, que `get_ticket`, `get_ticket_image` et `get_ticket_file` continuent de donner), ni déplacé ni placé avant (`move_ticket`), ni relancé (`start_ticket`, « Ce ticket est déjà parti. »). Un `after` qui ferait attendre deux tickets l'un l'autre est refusé avec le message du Kanban (« DEM-2 attend déjà DEM-1 (directement ou non). »).
- **Régler le Kanban** : le modèle et l'effort ont les contrôles de la fenêtre pour les deux outils, `set_board` et `start_ticket` (modèle connu, effort parmi `low`, `medium`, `high`, `xhigh` et `max`). Le reste ne concerne que `set_board`, `start_ticket` n'ayant pas de mode. Un agent d'Escouade règle le Kanban des projets qu'il voit comme la fenêtre, mode compris (`auto`, `default`, `plan`, `acceptEdits`). Refusés, avec la raison : `bypassPermissions` (lancer des agents sans aucune demande de permission reste la décision de l'utilisateur, dans la fenêtre, comme « Toujours autoriser » ; accepté seulement s'il est déjà le mode du Kanban, pour changer autre chose sans le défaire) et `testsFirst: true` sans commande de test, pour l'allumer seulement (la commande se règle dans la fenêtre : le serveur ne lance aucune commande et ne change pas celle du Kanban ; un `testsFirst` déjà allumé, redonné tel quel, passe). Une valeur qui n'existe pas (modèle inconnu, effort ou mode hors de la liste, branche cible qui n'est pas une branche locale du projet, `maxParallel` hors de 1 à 6), ou aucun champ donné, est une erreur. La cible du Kanban (même vide, sur une HEAD détachée par exemple) ou celle que `get_board` montre est laissée telle quelle, sans contrôle ; toute autre valeur doit être une branche locale du projet, et une cible vide qui diffère de celle du Kanban est une erreur.
- **Le remote control se lit, il ne se règle pas** (`list_projects`, `list_agents`, `get_agent_summary` ; décidé le 2026-10-15, ESC-103) : aucun outil n'allume, n'éteint ni ne règle le remote control, ni celui d'un agent, ni celui d'un projet, ni le global. L'allumer expose une session sur internet (joignable depuis claude.ai et l'app mobile) : cela reste la décision de l'utilisateur, dans la fenêtre (Réglages › Harness, Réglages › Projets, clic droit d'un agent), comme le mode `bypassPermissions` et la commande de test du Kanban, que les outils ne règlent pas non plus. Les descriptions des trois outils le disent.
- **Un agent ne s'écrit pas et ne s'arrête pas lui-même** (`send_message`, `stop_agent`) ; un agent archivé ne reçoit pas de message. De même, un agent n'arrête ni ses propres tâches de fond ni ses propres sous-agents (`stop_background_work`) et n'écrit pas à ses propres sous-agents (`message_subagent`).
- **Sous-agents et tâches de fond** (`list_background_work`, `get_background_output`, `stop_background_work`, `message_subagent` ; ESC-107) : chaque outil appelle la fonction du cœur que la fenêtre appelle (`stop_subagent`, `stop_bg_task`, `task_output`, `message_subagent`), et le cœur refuse ce que la fenêtre refuse, avec le même texte (voir les listes de refus de « Arrêter un sous-agent », « Lui écrire » et « Dans Escouade »). Dans l'ordre : l'agent est résolu ; pour `stop_background_work` et `message_subagent`, l'agent appelant lui-même est refusé (« Un agent ne peut pas arrêter ses propres tâches de fond. », « Un agent n'écrit pas à ses propres sous-agents. ») ; le projet est vérifié pour un agent d'Escouade (refus, comme les autres outils) ; un agent archivé est refusé (« L'agent X est archivé : on n'arrête plus ses sous-agents ni ses tâches de fond. », « … : ses sous-agents ne reçoivent plus de message. ») ; puis la ligne est résolue dans l'agent, par son `id` ou, pour un sous-agent, par son `taskId` (un `id` qui n'est ni un sous-agent ni une tâche de l'agent est une **erreur**, pas un refus : « L'agent X n'a ni sous-agent ni tâche de fond « Y » : list_background_work les liste. ») ; enfin les contrôles de l'outil, puis ceux du cœur. `message_subagent` donne aussi une erreur pour un texte vide (« Écris le message à envoyer. »), pour un texte de plus de 32 000 caractères (« Le message fait {n} caractères : 32000 au plus. », sans le texte) et pour un `subagent` qui est une tâche de fond (« … n'est pas un sous-agent mais une tâche de fond (command) : seuls les sous-agents reçoivent un message. »). Son ordre : d'abord tout ce qui ne dépend pas du quota (l'agent appelant lui-même, un agent archivé, un texte vide ou trop long, un `subagent` inconnu ou qui est une tâche de fond, puis les refus du cœur : un sous-agent qui ne tourne plus, au premier plan ou sans tâche donnée, un agent en vue Claude Code), et seulement ensuite le refus du compte retenu par le quota (« … jusqu'à 14:30 … »), pour qu'un client n'aille pas réessayer à 14 h, la retenue levée, pour être refusé de toute façon. `send_message` a la même borne de 32 000 caractères, côté MCP seulement, et la même erreur. Les refus du cœur sont ceux de la fenêtre, avec son texte ; un échec de Claude Code lui-même (la requête `stop_task` ou l'envoi à l'agent qui échoue) est une erreur, pas un refus. `list_background_work` et `get_background_output` sont ouverts, pour un agent d'Escouade, aux projets qu'il voit, comme l'image d'un ticket. Lire un rapport de sous-agent ne change rien, même en vue Claude Code (le transcript est lu sans terminer la ligne du plan). Aucun outil ne lance une commande ni n'écrit hors de l'agent : `stop_background_work` ne fait qu'arrêter ce que Claude Code a lancé, et `message_subagent` n'est qu'un message à l'agent, sous le nom de son auteur. Chaque appel, refusé ou non, est noté dans le journal d'activité, qui garde l'outil, l'agent et l'id, jamais le texte d'un message ni une sortie.
- **Répondre à une demande** (`answer_permission`, `answer_question`) : une fois l'interrupteur « Les agents peuvent piloter Escouade » allumé, tout client du serveur voit les demandes de tous les projets (`list_requests` est ouvert) et peut y répondre, Claude hors Escouade comme les agents de tous les projets, sans réglage de plus ni limite de ce qui peut être autorisé (décidé le 2026-10-15) ; un agent d'Escouade répond à celles des agents des projets qu'il voit. Refusés, avec la raison : `always` (voir plus haut) ; un agent qui répond à ses propres demandes (« Un agent ne répond pas à ses propres demandes. ») ; une demande qui n'attend plus de réponse (« Cette demande n'attend plus de réponse : l'utilisateur ou un autre client y a déjà répondu, ou l'agent ne tourne plus (ou ce n'est pas l'identifiant d'une de ses demandes). Demandes de l'agent X qui attendent : r1, r2. », « aucune » à la place de la liste quand rien n'attend) : il n'y a jamais deux réponses, la première prise gagne et la seconde, simultanée ou tardive, lit ce refus ; un agent en vue Claude Code (« L'agent X est en vue Claude Code : ses demandes sont dans son terminal, c'est là qu'on y répond. »). Une erreur plutôt qu'un refus : une demande de l'autre type (une question pour `answer_permission` et l'inverse : l'erreur nomme le bon outil), un `message` avec `allow`, une réponse qui ne convient pas à la question. Assumé, par décision de l'utilisateur : un agent poussé par un contenu piégé peut ainsi autoriser une commande demandée par un autre agent de son projet, une demande à la fois et jamais durablement.
- **Le flux du Kanban** (`approve_ticket`, `reject_ticket`, `resume_ticket`, `resolve_conflict`, `dismiss_block`, `delete_ticket`) : chaque outil appelle la fonction du cœur que la fenêtre appelle, et le cœur refuse ce que la fenêtre refuse, avec le même texte. Dans l'ordre : le ticket est résolu, le projet est vérifié pour un agent d'Escouade (ci-dessous), puis son ticket propre, puis les contrôles de l'outil. Refusés : `approve_ticket` et `reject_ticket` pour un ticket qui n'est pas « À tester », dont l'agent travaille ou dont la validation tourne déjà ; `resume_ticket` pour un ticket qui n'est pas « En cours », qui n'est pas bloqué ou dont l'agent attend la remise à zéro de son quota (le refus dit jusqu'à quand) ; `resolve_conflict` pour un ticket qui n'est pas « À tester » ou qui n'a pas de conflit ; `dismiss_block` pour un ticket qui n'est pas « À tester », dont la validation tourne ou qui n'est pas bloqué (« Ce ticket n’est pas bloqué. »). `delete_ticket` n'est refusé pour aucune colonne, mais tant que la validation du ticket tourne (« La validation de ce ticket est en cours : attends sa fin pour le supprimer. »). Un message que le flux envoie à un agent (`reject_ticket`, `resolve_conflict`, `resume_ticket`) n'est remis que tant que le compte Claude de cet agent n'est pas retenu, comme `send_message` ; `resume_ticket` d'un ticket dont l'agent a disparu, qui repart avec un nouvel agent, est refusé quand aucun compte n'est utilisable pour le projet, comme `start_ticket`. **Un agent d'Escouade ne valide ni ne renvoie son propre ticket** (« Un agent ne valide pas son propre ticket : il fusionnerait son travail sans relecture. », « Un agent ne renvoie pas son propre ticket. »), et n'agit pas non plus sur lui avec `resume_ticket`, `resolve_conflict`, `dismiss_block` et `delete_ticket` (« Un agent n’agit pas sur son propre ticket avec cet outil : c’est à l’utilisateur ou à un autre client de le faire. ») ; le sien est le ticket dont il est l'agent. La validation est ouverte à tout client du serveur, et `delete_ticket` supprime comme la fenêtre, sur n'importe quel ticket : un agent d'Escouade qui y est poussé par un contenu piégé peut ainsi valider ou supprimer le ticket d'un autre agent de son projet. Chaque appel, refusé ou non, est noté dans le journal d'activité.
- **Un agent d'Escouade agit là où il voit** (ESC-157, décidé le 2026-10-23 après un retour sur Discord : le back et le front d'un même produit sont deux projets d'Escouade) : l'agent d'un projet qui n'est pas privé agit sur le sien et sur tous les projets qui ne sont pas privés ; l'agent d'un projet privé n'agit que sur le sien. Un projet privé n'est donc touché que par ses propres agents. La garde (`act::may_act_on`) accepte ce que `resolve::Sight` voit : `create_ticket`, `update_ticket`, `move_ticket`, `start_ticket`, `set_board`, `create_agent`, `send_message`, `stop_agent`, `stop_background_work`, `message_subagent`, `answer_permission`, `answer_question`, les six outils du flux du Kanban, `split_ticket`, `get_ticket_image`, `get_ticket_file` et `get_background_output`. Ce qu'un agent ne voit pas est introuvable avant d'arriver à la garde, au mot près comme un nom que rien ne porte : aucun refus ne nomme un projet privé. Un agent que le cœur n'a plus n'agit nulle part (« L'agent X n'est plus dans Escouade : il n'agit plus. »). Les règles propres à chaque outil restent (un agent ne valide pas son propre ticket, n'arrête pas son propre tour…). Claude hors Escouade, lui, agit et lit sur n'importe quel projet, sans réduction.

**L'auteur d'un message est toujours dit.** Un texte qui vient du serveur n'est pas pris pour les mots de l'utilisateur : `send_message`, et le premier message de `create_agent`, sont remis à l'agent, et montrés dans sa conversation, précédés de « Message de <auteur> : » (« Message from <author>: » en anglais, dans la langue de l'interface), l'auteur étant le nom de l'agent qui appelle ou « Claude (hors Escouade) » (« Claude (outside Escouade) ») pour Claude hors Escouade, comme le journal d'activité le nomme. L'en-tête ne compte pas pour le nom que Haiku donne à un agent d'après son premier message, et un texte qui commence par `/` n'est plus une commande (il suit l'en-tête). `message_subagent` fait de même pour le texte que l'agent doit transmettre au sous-agent (`Core::message_subagent_from`) : la demande qu'Escouade envoie à l'agent (« Lui écrire », plus haut) le contient précédé de « Message de <auteur> : », et c'est ce texte que le sous-agent reçoit ; l'en-tête ne vient qu'après les refus (un texte vide reste vide).

**L'auteur d'une réponse aussi.** La carte d'une demande à laquelle `answer_permission` ou `answer_question` a répondu, dans la conversation de l'agent qui la posait, dit qui a répondu : « Autorisé par <auteur> via Escouade », « Refusé par <auteur> via Escouade » (permission, plan) ou « Répondu par <auteur> via Escouade » (question) — « Allowed by <author> through Escouade », « Denied by … », « Answered by … » en anglais —, l'auteur étant celui du journal d'activité. L'élément de la conversation reçoit pour cela un champ `by` (le nom de l'auteur) avec `decision` et `message`, ou `answers`, enregistré comme le reste de la conversation ; il est absent quand c'est l'utilisateur qui a répondu dans la fenêtre. Le reste suit la réponse de la fenêtre : la demande ne compte plus parmi celles qui attendent (`pending` et `requests` de la vue de l'agent), l'agent repasse « en cours » quand c'était la dernière, et la fenêtre en est avertie par l'événement de l'agent. Claude, lui, lit de qui vient la réponse, sauf pour une approbation : `allow` et un plan approuvé lui arrivent sans auteur (Claude Code écrit lui-même « User has approved… » et ne lit rien de ce que le serveur y mettrait), la carte de la conversation étant alors seule à dire qui a approuvé. Un refus commence par « Refusé par <auteur> via Escouade », chaque réponse à une question est suivie de « (réponse de <auteur> via Escouade) ».

**L'origine d'un ticket aussi.** La description d'un ticket créé par `create_ticket` ou `split_ticket` se termine, après une ligne vide, par « Créé par <auteur> via Escouade » (« Created by <author> through Escouade », dans la langue de l'interface), l'auteur étant celui du journal d'activité (le nom de l'agent qui appelle, ou « Claude (hors Escouade) »). La ligne fait partie de la description : la carte du ticket la montre, et le protocole que reçoit son agent la contient. La limite de 10 000 caractères porte sur ce que l'appelant écrit, pas sur cette ligne. `update_ticket` qui change le titre, la description ou les critères (pas `after` seul, ni des images seules) termine de même la description par « Modifié par <auteur> via Escouade » (« Modified by <author> through Escouade »), à la place de la ligne « Créé par… » ou « Modifié par… » qui la terminait (jamais deux lignes à la suite) ; la description donnée remplace l'ancienne, la ligne vient après, et la limite ne la compte pas non plus.

**Les images d'un ticket aussi.** `create_ticket` (`images`), `update_ticket` (`addImages`, `removeImages`) et `split_ticket` (`images` de chaque sous-ticket) passent par `Core::ticket_create` et `Core::ticket_update`, les fonctions de la fenêtre, donc par ses contrôles (`ticketimages::check`) : PNG, JPEG, GIF ou WebP, le type étant lu dans le contenu (un JPEG donné pour `image/png` est gardé JPEG), 5 Mo par image, 18 Mo en tout, 20 images au plus par ticket (celles que `update_ticket` garde comptent), un base64 valide. Une image refusée ne laisse rien : ni ticket, ni clé consommée, ni fichier, ni dossier. Le total de 18 Mo est tenu **avant de lire** : l'image qui le ferait dépasser est refusée, avec le message de la fenêtre, avant d'être lue quand elle est donnée par `path` (sa taille est celle du fichier ouvert), ou décodée quand elle l'est par `data` (sa taille se déduit de la longueur du base64) ; les images que `update_ticket` garde comptent dès le départ. `update_ticket` vérifie aussi d'abord que le ticket est « À faire » : sinon il refuse, avec le texte du Kanban (« Seul un ticket « À faire » se modifie. »), sans lire les fichiers donnés ni toucher aux images. Une image à joindre est `{ name?, mediaType?, data?, path? }`, avec exactement un de `data` (son contenu en base64) ou `path` (le chemin d'un fichier local), sinon une erreur ; `name` est obligatoire avec `data` et vaut par défaut le nom du fichier avec `path` ; `mediaType` n'est qu'indicatif. Le nom n'est qu'une étiquette (le fichier gardé a un nom généré), mais il s'affiche et part dans le premier message de l'agent : seul ce qui suit le dernier `/` ou `\` est gardé, sans caractère de commande ni caractère caché, sur une seule ligne (`../../etc/passwd.png` est gardé `passwd.png`) ; un nom vide, ou de plus de 100 caractères, est une erreur. Une image à désigner est `{ file?, index? }`, avec exactement un des deux : `file`, le nom que `get_ticket` donne (comparé tel quel), ou `index`, son rang dans la liste de `get_ticket`, à partir de 0. Aucun nom ni rang ne mène à un autre fichier que ceux du ticket : une référence qui ne correspond à aucune image (nom inconnu ou hostile comme `../state.json`, chemin absolu, rang hors de la liste) est une erreur qui dit de lire `get_ticket`, et rien n'est touché.

**Le chemin `path`, sûr aussi.** Claude hors Escouade peut donner n'importe quel chemin absolu vers un fichier local. Un agent d'Escouade seulement un fichier sous son dossier de travail (`AgentMeta.cwd`). C'est un garde-fou du serveur, pas une frontière de sécurité (un agent qui a la main sur sa machine a d'autres voies). Le fichier est ouvert d'abord, puis le chemin final de ce que la poignée a ouvert est comparé au dossier de travail canonique : il n'y a pas de fenêtre entre la vérification et la lecture, et un lien (symbolique, jonction Windows) qui sort du dossier est refusé. Un fichier hors du dossier de l'agent reçoit **un seul et même refus, qu'il existe ou non** (« Un agent d’Escouade ne joint que des fichiers de son dossier de travail : ce fichier n’en fait pas partie, ou il n’existe pas. »), pour ne rien révéler de son existence ; un chemin qui n'existe pas est jugé sur sa forme normalisée (les `..` résolus sans toucher au disque) et, s'il tombe sous le dossier, c'est « introuvable ». Le refus est noté « refusé » dans le journal. Sont des erreurs : un chemin relatif ; un chemin qui commence par `\\` ou `//` (un partage réseau UNC enverrait les identifiants Windows, `\\?\` et `\\.\` ouvrent des périphériques) ; un fichier introuvable ou illisible ; ce qui n'est pas un fichier ordinaire (dossier, périphérique, tube) ; un fichier de plus de 5 Mo, refusé sur sa taille avant d'être lu (la lecture elle-même est bornée à 5 Mo plus un octet) ; un fichier qui n'est pas une image, comme dans la fenêtre. Le chemin n'est jamais gardé : le ticket garde une copie du contenu.

**Les autres fichiers d'un ticket aussi (ESC-108).** `create_ticket` (`files`), `update_ticket` (`addFiles`, `removeFiles`) et `split_ticket` (`files` de chaque sous-ticket) joignent les fichiers de tout format comme la fenêtre : chaque nouveau fichier est d'abord **une copie des brouillons**, faite comme le formulaire la fait (`Core::attach_open`, ses morceaux, sa fin, propriétaire `draft` : `<données>/attachments/_drafts/<uniq>/<nom>`), puis `Core::ticket_create` ou `Core::ticket_update` la vérifient (`ticketfiles::check`) et la déplacent dans `<dossier du ticket>/files/<uniq>/<nom>`. Mêmes limites et mêmes refus que la fenêtre : 20 fichiers au plus par ticket (ceux que `update_ticket` garde comptent), chacun pas plus gros que « Taille maximale d'un fichier joint » des réglages (Réglages › Pièces jointes, `attachMaxMb`, 0 : sans limite ; refus « gros.iso dépasse 1 Mo »). Ces limites sont tenues **avant toute copie** : le nombre avant de regarder un fichier (une longue liste de chemins n'est pas lue pour être refusée), puis chaque fichier de la liste, entière, avant d'en copier un : un contenu `data` sur la longueur de son base64, un fichier `path` sur la taille du fichier ouvert, avant d'en lire un octet (la copie elle-même est bornée à cette taille, et le cœur refuse encore ce qui la dépasse). `update_ticket` vérifie d'abord que le ticket est « À faire », sans rien regarder d'autre. Un refus ou un échec ne laisse rien : ni ticket, ni clé consommée, ni fichier dans le dossier du ticket, **ni copie dans les brouillons** (celles que le cœur n'a pas déplacées sont retirées à la fin de l'appel, quoi qu'il arrive). Un fichier à joindre est `{ name?, data?, path? }`, avec exactement un de `data` (son contenu en base64, pour un petit fichier : une requête pèse 32 Mio au plus) ou `path` (le chemin d'un fichier local, copié ; mêmes règles que pour les images, voir le paragraphe précédent : un agent d'Escouade ne donne qu'un fichier de son dossier de travail, vérifié sur le fichier ouvert, même refus qu'il existe ou non ; chemin absolu, local, d'un fichier ordinaire) ; `name` est obligatoire avec `data` et vaut par défaut le nom du fichier avec `path`. Le nom est nettoyé comme la fenêtre nettoie celui d'un fichier qu'elle copie (`attachfiles::safe_name` sur ce qui suit le dernier `/` ou `\`, sur une ligne et sans caractère caché : les caractères que Windows refuse remplacés, un nom de périphérique préfixé, un nom trop long coupé en gardant son extension) ; seul un nom vide est une erreur. Un base64 invalide est une erreur qui ne le cite pas. Un fichier à désigner est `{ file?, index? }`, comme une image : `file`, le `<uniq>/<nom>` que `get_ticket` donne (comparé tel quel), ou `index`, son rang dans `files` ; une référence qui ne correspond à aucun fichier du ticket est une erreur qui dit de lire `get_ticket`, et rien n'est touché. Un fichier retiré est effacé du dossier du ticket, comme quand la fenêtre le retire. Un fichier joint par les outils est un fichier du ticket comme un autre : son agent en reçoit le chemin avec son premier message et le lit sans demander (`--add-dir`), et la purge de « Conserver les fichiers » le prend comme les autres. Le chemin donné n'est jamais gardé, ni écrit au journal.

Ce qui ne colle pas à ce qui est demandé (titre vide, nom inconnu ou ambigu, modèle inconnu, `before` sans `position: "before"`) est une erreur, pas un refus. Un `create_agent` dont le message n'a pas pu partir dit que l'agent existe (son id) mais pas son message.

### Outils réservés aux agents d'Escouade

`report_progress` et `split_ticket` sont listés pour tous les clients, mais un client qui n'est pas un agent d'Escouade (Claude hors Escouade) reçoit un refus qui le dit : « Cet outil est réservé aux agents d'Escouade : Claude hors Escouade ne peut pas l'appeler. » Il est noté « refusé » dans le journal.

| Outil | Arguments | Réponse |
|---|---|---|
| `report_progress` | `line` | `{ line }` telle que gardée. Une ligne d'état de 120 caractères au plus (plus long : erreur qui donne le compte, rien n'est gardé), sur une seule ligne (les caractères de commande, dont les sauts de ligne et les tabulations, les séparateurs de ligne et de paragraphe et les espaces multiples sont remplacés par une seule espace). Rien de caché n'est gardé : les caractères de format (marques de largeur nulle, marques et forçages de direction comme U+202E…) et ceux qui ne se dessinent pas (sélecteurs de variante, caractères d'étiquette…) sont retirés, comme la fenêtre les épelle dans une demande d'autorisation ; la ligne répondue est celle gardée (`null` si rien ne reste). Gardée dans `AgentMeta.progress_line` (enregistrée avec l'agent) et envoyée à la fenêtre : la carte de l'agent (barre latérale, vue d'ensemble) et celle de son ticket « En cours » la montrent jusqu'au prochain appel. Une ligne vide l'enlève (`{ line: null }`). |
| `split_ticket` | `tickets: [{ title, description?, criteria?, images?: [{ file?, index? }], files?: [{ file?, index? }] }]` (1 à 10), `chain?: bool` (vrai par défaut) | les clés des tickets créés, dans l'ordre : `["DEM-5", "DEM-6"]` ; quand au moins une image du ticket d'origine a été sautée (voir plus bas), `{ "tickets": ["DEM-5", "DEM-6"], "skipped": ["<une phrase par image sautée>"] }`. Ils sont créés en fin de « À faire », **après le ticket de l'agent** : le premier lui, chacun après le précédent avec `chain`, tous après lui seul sans (ils peuvent alors tourner en parallèle). `images` nomme des images **du ticket de l'agent** (par `file` ou `index`, comme `get_ticket` les liste) que le sous-ticket reprend : argument omis, **toutes** celles du ticket d'origine ; `[]`, aucune ; une liste, celles-là, sans doublon. Chaque sous-ticket reçoit **ses propres copies** (des fichiers distincts, avec les mêmes nom et type ; les octets du ticket d'origine sont lus une seule fois, puis passés à `Core::ticket_create` comme les images de la fenêtre, aux mêmes limites). Tout est vérifié avant de créer le premier : une référence inconnue, ou une image nommée dans `images` dont le fichier manque, est une erreur « Ticket n de la liste : … » et rien n'est créé (la demande ne peut pas être honorée). Par défaut (`images` omis), une image du ticket d'origine dont le fichier a disparu ou n'est pas lisible est **sautée** au lieu de bloquer le découpage : le sous-ticket est créé avec les autres, et `skipped` a une phrase par sous-ticket et par image sautée (sa clé, le nom de l'image, pourquoi) ; quand rien n'est sauté, la réponse reste le tableau des clés. Refusé à un agent sans ticket. Le ticket de l'agent n'est pas touché et garde ses images. `files` fait de même pour les autres fichiers du ticket de l'agent (ESC-108) : omis, tous ; `[]`, aucun ; une liste, ceux-là. Chaque sous-ticket en reçoit ses propres copies, faites dans les brouillons comme le formulaire les fait puis déplacées dans son dossier par `Core::ticket_create` (aux limites de la fenêtre). Tout est regardé avant de créer le premier : un fichier nommé qui a disparu, ou qui dépasse la taille que les réglages permettent désormais (il a pu être joint sous une taille plus grande), est une erreur « Ticket n de la liste : … » et rien n'est créé ; pris par défaut, il est sauté, et `skipped` le dit comme pour une image (« DEM-5 : le fichier « trace.log » n'a pas été copié, son fichier a disparu ou n'est pas lisible. »). Le ticket de l'agent garde ses fichiers. |
