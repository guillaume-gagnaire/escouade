# Le serveur MCP

Le serveur MCP d’Escouade laisse Claude Code, Codex, OpenCode, Copilot CLI et les agents d’Escouade lire tes projets, agents et tickets, créer, modifier, lancer, valider et supprimer des tickets, régler le Kanban et piloter des agents, y compris répondre à leurs demandes, sous les mêmes garde-fous que le pilote auto.

## À quoi il sert

MCP (Model Context Protocol) est le protocole par lequel un harness (Claude Code, Codex, OpenCode, Copilot CLI) appelle des outils. Escouade embarque un serveur MCP : une fois déclaré dans un harness, il lui donne les outils de la liste plus bas.

- **Claude dans un terminal** : tu lances `claude` où tu veux et tu lui parles d’Escouade (« liste les tickets à tester du projet api », « crée un ticket pour limiter les tentatives de connexion, puis lance-le »).
- **Un autre outil** qui parle MCP peut se connecter de la même façon (voir [Jeton et réseau](#jeton-et-reseau)).
- **Un agent d’Escouade**, de n’importe quel projet, avec un jeton à lui (voir [Les agents d’Escouade et le serveur](#les-agents-d-escouade-et-le-serveur)).

Le serveur tourne sur ta machine seule. Il ne sert qu’à lire et à commander ; il ne lance aucune commande de son choix et ne supprime ni projet ni agent. Pour un ticket, il fait ce que font les boutons du Kanban, valider (les tests, puis la fusion) et supprimer compris. Il peut répondre à la demande d’un agent à ta place, mais jamais par « Toujours autoriser » : une règle de permission qui dure reste ta décision, dans la fenêtre.

## Activer « Les agents peuvent piloter Escouade »

Un seul interrupteur donne le serveur aux agents d’Escouade de tous les projets, et le déclare dans chaque harness installé : Claude Code, Codex, OpenCode et Copilot CLI, lancés hors d’Escouade (un terminal, leur app).

1. Ouvre Réglages › Serveur MCP. L’onglet a l’interrupteur « Les agents peuvent piloter Escouade ».
2. Allume-le. Il s’enregistre tout de suite, sans « Enregistrer » : la déclaration écrit dans la config de chaque compte de chaque harness, ce qu’« Annuler » ne pourrait pas défaire.

Escouade démarre alors le serveur et le déclare dans chaque compte actif de chaque harness installé, seulement les comptes ajoutés (un harness sans compte n’a la déclaration nulle part) :

| Harness | Fichier (compte Principal) | Comment |
| --- | --- | --- |
| Claude Code | `~/.claude.json` | `claude mcp add --scope user --transport http escouade <adresse> --header "Authorization: Bearer <jeton>"`, lancée comme le compte lance Claude Code (son exécutable, son dossier de configuration) |
| Codex | `~/.codex/config.toml` | écrit par Escouade, `[mcp_servers.escouade]` |
| OpenCode | `~/.config/opencode/opencode.json` (sous `$XDG_CONFIG_HOME` quand il est défini ; l’`opencode.jsonc` qui est là, s’il y en a un) | écrit par Escouade, `mcp.escouade` |
| Copilot CLI | `~/.copilot/mcp-config.json` | écrit par Escouade, `mcpServers.escouade` |

Un autre compte a le même fichier dans son dossier. Pour Codex, OpenCode et Copilot CLI, dont la ligne de commande ne sait pas déclarer un serveur avec son en-tête, Escouade écrit l’entrée lui-même et garde tout le reste du fichier tel quel, commentaires, ordre et fins de ligne compris ; un fichier lié à celui de « Principal » reste un lien. Les entrées :

```toml
# Codex
[mcp_servers.escouade]
url = "http://127.0.0.1:<port>/mcp"
http_headers = { Authorization = "Bearer <jeton>" }
```

```jsonc
// OpenCode
"mcp": {
  "escouade": {
    "type": "remote",
    "url": "http://127.0.0.1:<port>/mcp",
    "headers": { "Authorization": "Bearer <jeton>" }
  }
}
// Copilot CLI
"mcpServers": {
  "escouade": {
    "type": "http",
    "url": "http://127.0.0.1:<port>/mcp",
    "headers": { "Authorization": "Bearer <jeton>" }
  }
}
```

Le jeton est écrit **en clair** dans chacun de ces fichiers, ce que la note du groupe dit.

Sous l’interrupteur, l’onglet liste chaque déclaration : le harness et le compte (« Codex · compte Principal »), le fichier, et son état, « Déclaré » ou « Pas déclaré ».

- Une entrée déjà à jour est laissée telle quelle. Une entrée différente (un autre port, un autre jeton) est remplacée. Un compte ajouté ou réactivé plus tard reçoit la déclaration, et un harness installé plus tard aussi : quand tu reviens dans la fenêtre d’Escouade, ou dès qu’elle montre cet onglet ou la liste des harness de Réglages › Harness.
- Si elle échoue pour un compte, l’onglet dit pourquoi (« Pas déclaré pour le compte Pro : … ») et ce qu’il faut faire à la main : pour Claude Code, la commande à lancer (« À lancer à la main dans PowerShell : »), écrite pour PowerShell sous Windows et pour `sh` ailleurs ; pour les autres, l’entrée à ajouter au fichier (« À ajouter à la main dans … : »). Le jeton y est masqué à l’écran ; « Copier la commande » ou « Copier l’entrée » copie la vraie. Un fichier qui n’est pas un TOML ou un JSON valide n’est pas touché.
- Éteindre l’interrupteur change le jeton tout de suite (l’ancien n’ouvre plus rien), puis retire l’entrée de chaque compte de chaque harness : chaque fichier redevient celui d’avant, à l’octet près ; un fichier qu’Escouade avait créé est supprimé. Les agents déjà lancés perdent les outils tout de suite eux aussi (leurs jetons sont oubliés) : rallumé, l’interrupteur les leur rend au prochain démarrage de leur processus (« Relancer »). Supprimer un compte retire la sienne.
- Si le serveur ne démarre pas, l’onglet le dit (« Le serveur n’a pas démarré : … »).

Claude Code connaît le serveur sous le nom `escouade` : ses outils s’appellent `mcp__escouade__<outil>` (par exemple `mcp__escouade__list_tickets`) ; dans OpenCode, `escouade_<outil>`.

Les agents d’Escouade, quel que soit leur harness, n’utilisent pas ces entrées : ils reçoivent le serveur par les options de leur processus, avec leur propre jeton, qui l’emporte (voir [Les agents d’Escouade et le serveur](#les-agents-d-escouade-et-le-serveur)).

> [!NOTE]
> Sous Windows avec Claude Code dans WSL, les outils MCP d’Escouade demandent le réseau miroir de WSL : `networkingMode=mirrored` sous `[wsl2]` dans `%UserProfile%\.wslconfig`, puis `wsl --shutdown`. Réglages › Harness le rappelle quand le réseau de WSL est en NAT.

## Les outils

Dans les arguments, un projet se nomme par son id ou son nom (casse libre), un agent par son id ou son nom, un ticket par sa clé (`ATL-12`, casse libre) ou son id. Les réponses sont en JSON.

### Lire

Ces douze outils ne changent rien.

| Outil | Arguments | Ce qu’il rend |
|---|---|---|
| `list_projects` | aucun | Les projets, dans l’ordre de l’app : id, nom, dossier, branche git courante, nombre d’agents (archivés exclus), nombre de tickets dans chaque colonne et réglages du remote control : `remoteControl` (« Remote control pour les agents de ce projet ») et `remoteControlAll` (« Remote control pour tous les agents », le même sur chaque ligne ; allumé, il couvre tous les agents de tous les projets et l’interrupteur du projet est grisé dans la fenêtre). |
| `list_agents` | `project` (facultatif) | Les agents non archivés, du plus ancien au plus récent, de tous les projets ou d’un seul : id, nom, projet, état (`idle`, `running`, `waiting`, `done` ou `error`), si une question ou une autorisation attend ta réponse et combien, clé de leur ticket, harness (`engine` : `claude` pour Claude Code, puis `codex`, `copilot`, `cursor` ou `opencode`), modèle, compte Claude, coût en dollars, `subagentsRunning` (combien de sous-agents tournent, au premier plan ou en arrière-plan), `backgroundTasksRunning` (combien de tâches de fond tournent : commandes, surveillances, agents distants, coéquipiers et workflows, jamais les sous-agents ; c’est le « N en fond » de la carte) et remote control. Ces deux comptes disent qu’un agent « Terminé » a encore du travail qui tourne : `list_background_work` le détaille. `remoteControl` dit s’il est en vigueur pour l’agent maintenant, donc si sa session est joignable depuis claude.ai. `remoteSource` dit ce qui l’a allumé : `hand` (toi, au clic droit de l’agent), `project` (le réglage du projet) ou `global` (le réglage de tous les agents, qui passe avant celui du projet quand les deux sont allumés) ; `off` quand tu as mis l’agent à part avec « Désactiver le remote control » (aucun réglage ne le lui redonne, redémarrage compris, tant que tu ne l’allumes pas à la main) ; `null` quand il n’est pas en vigueur et que l’agent n’est pas mis à part. `remoteControl` est donc `true` avec `hand`, `project` ou `global`, et `false` avec `off` ou `null`. `remoteState` est l’état du lien avec claude.ai que Claude Code rapporte : `ready` (en attente de connexion), `connected` ou `unavailable` (en vue Claude Code, l’interface tourne mais Claude Code n’a pas ouvert le remote control : compte sans abonnement claude.ai, réseau, proxy ou règle de l’organisation) ; `null` sans lien en cours. `interfaceRemote`, pour un agent en vue Claude Code : `true` quand son interface tourne, lancée avec le remote control (elle reste liée à claude.ai jusqu’à son prochain lancement, même si `remoteControl` est repassé à `false` après une désactivation), `false` quand elle tourne sans, `null` quand aucune ne tourne (agent hors vue Claude Code, ou interface pas lancée). |
| `list_tickets` | `project`, `column` (facultatif : `todo`, `doing`, `review` ou `done`) | Les tickets d’un projet dans l’ordre du Kanban : id, clé, titre, colonne, clés des tickets qu’ils attendent, nom de leur agent, motif du blocage, et le compte, le modèle et l’effort de leurs agents quand ils ne sont pas sur « Auto ». |
| `get_ticket` | `ticket` | Un ticket entier : titre, description, critères (atteints ou non, avec la note de l’agent), boucles (la courante et le maximum), colonne, tickets attendus, avancement, la liste de ses images (`index`, `file`, `name`, `mediaType` et `size` : collées ou glissées dans la fenêtre du ticket, ou jointes par le serveur ; son agent les reçoit avec son premier message), la liste de ses autres fichiers, de tout format (`files` : `index`, `file`, `name` et `size`, `null` pour un fichier que la purge des réglages a pris ; joints dans la fenêtre du ticket ou par le serveur ; son agent reçoit leurs chemins avec son premier message, et `get_ticket_file` en lit un), ticket externe d’origine (Jira, Trello, GitHub, Linear, ClickUp, GitLab ou Azure Boards), le compte (`account`, son nom, avec `accountId`), le modèle et l’effort de ses agents (`auto` quand ils suivent le compte courant, le Kanban ou le compte ; `accountLost` : pourquoi il est repassé en « Auto »), et de quoi suivre son flux : son agent (id, nom, état, demandes qui attendent), sa branche et son worktree (ceux de son agent : une fois le ticket terminé, le worktree peut avoir disparu), ce qui le bloque (`blocked`, `conflict`), l’étape de validation en cours (`step`) et, une fois terminé, son résultat (`outcome` : le texte, l’adresse de la pull request quand il y en a une, le commit que la fusion a fait dans la branche cible). Un agent d’Escouade peut omettre `ticket` pour lire le sien. |
| `get_ticket_image` | `ticket` (facultatif), `file` ou `index` | Une image d’un ticket, que Claude reçoit comme une image (le contenu), suivie de son `index`, son `file`, son `name`, son `mediaType` et sa `size` en octets. On la désigne par son `file` (le nom que `get_ticket` donne) ou par son `index` (son rang dans la liste de `get_ticket`, à partir de 0), l’un des deux seulement. Un agent d’Escouade peut omettre `ticket` pour lire celle de son ticket, et lit les images des tickets des projets qu’il voit, comme `get_ticket` ; Claude hors Escouade lit celles de tous les projets. Une image que le ticket n’a pas (un nom inconnu, un rang hors de la liste) est refusée, et jamais un nom ne mène à un autre fichier que ceux du ticket. |
| `get_ticket_file` | `ticket` (facultatif), `file` ou `index`, `offset` (facultatif), `bytes` (facultatif) | Un morceau d’un autre fichier d’un ticket, de tout format, désigné comme une image (`file` ou `index` dans `files` de `get_ticket`). Sans `offset`, sa fin ; avec, à partir de cet octet. `bytes` vaut 8 192 par défaut, 65 536 au plus : un plus gros fichier se lit en plusieurs fois, pour que la réponse tienne dans ce que Claude Code accepte d’un outil. Rend `size` (la taille du fichier entier), `offset` et `length` (où commence le morceau et combien d’octets il tient), `encoding` (`text` quand c’est du texte, coupé entre deux caractères, sinon `base64`) et `content`. Claude hors Escouade reçoit aussi `path`, le chemin du fichier sur ta machine, pour le lire en entier par ses propres moyens. Un agent d’Escouade peut omettre `ticket` pour lire un fichier du sien, lit les fichiers des tickets des projets qu’il voit et ne reçoit pas de chemin. Un fichier que la purge a pris est refusé. |
| `get_usage` | aucun | Le quota de chaque compte, de tout harness : son harness (`engine`), si les nouveaux agents de ce harness y partent maintenant, ses compteurs (`meters` : une fenêtre d’une durée en `minutes`, ou les crédits du mois ; `pct` de 0 à 100, `resetsAt`), les fenêtres de 5 h et hebdomadaire de Claude Code aussi en `fiveHour` et `sevenDay`, et pourquoi le pilote auto retient les tickets (`reason` : `window` avec ses `minutes`, `credits` ou `limit`), jusqu’à quand. |
| `index_search` | `project` (facultatif), `query`, `kind` (facultatif), `limit` (facultatif), `path_include` et `path_exclude` (facultatifs), `literal` (facultatif), `ids` (facultatif), `exact_total` et `timeout_ms` (facultatifs, littéral) | Les symboles de l’index du code du projet (fonctions, méthodes, classes, types, champs, titres Markdown) dont le nom, la doc ou la signature contiennent les mots du code, le meilleur d’abord, une ligne chacun : `fichier:ligne-fin: nom (sorte) — signature`, l’id avec `ids`. Avec `literal`, un texte exact du source, `fichier:ligne: texte`. Les chemins de `.escouade/queryignore` sont laissés de côté. Chaque réponse des six outils `index_…` finit par `index_metrics: before after result saved`, compté comme le compte tokensave (les fichiers touchés plafonnés à quatre fois la réponse, contre la réponse, la requête et, une fois par session, les schémas des outils). Un agent d’Escouade peut omettre `project` (le sien) et la réponse vaut pour le dossier où il travaille. Quand le projet n’a pas allumé « Index du code », l’outil le dit et dit où l’allumer. |
| `index_context` | `project` (facultatif), `task`, `keywords` (facultatif), `max_nodes` (facultatif), `include_code`, `max_code_blocks` et `max_code_lines` (facultatifs), `exclude_node_ids` (facultatif), `max_per_file` (facultatif), `path`, `path_include` et `path_exclude` (facultatifs) | Le contexte d’une tâche dite en mots, en un appel, en Markdown : les points d’entrée, les symboles qui leur sont liés, le code des points d’entrée (cinq blocs au plus, de 1 500 octets au plus ; un bloc coupé finit par l’appel `index_body` qui donne la suite), puis `### Retrieval` (les termes qui n’ont rien trouvé, à redemander avec `keywords`) et `seen_node_ids`, pour le `exclude_node_ids` de l’appel suivant. |
| `index_body` | `project` (facultatif), `symbol` ou `node_id`, `limit` (facultatif) | Le corps entier d’un symbole, par son nom (`Type::membre` ou ses derniers segments) ou son id ; un nom porté par plusieurs définitions donne leur liste, à redemander par id. |
| `index_callers` | `project` (facultatif), `id` ou `name`, `path` (facultatif), `limit` (facultatif), `max_matches` (facultatif) | Qui appelle une fonction ou une méthode : par son id (celui que donne `index_search` avec `ids`), ou par un nom (`forget`, `Runtime::forget`) répondu définition par définition. Les appels qui peuvent la viser parmi d’autres sont dits à part. |
| `index_callees` | `project` (facultatif), `id` ou `name`, `path` (facultatif), `limit` (facultatif), `max_matches` (facultatif) | Ce qu’elle appelle : les définitions du projet, les appels laissés à une égalité, et les noms restants (ceux du langage, des bibliothèques). |
| `index_impact` | `project` (facultatif), `id` ou `target`, `depth` (facultatif), `limit` (facultatif), `max_matches` (facultatif) | Ce qu’un changement toucherait : les appelants (sur `depth` niveaux), les types qui l’étendent, les fichiers qui l’importent et tous les fichiers touchés, définition par définition. |
| `get_board` | `project` | Les réglages du Kanban d’un projet, ceux de l’onglet « Kanban » de ses réglages : `project` et `projectId` (le nom du projet et son id), `action` (ce que fait « Valider » : `merge`, `pr`, `push` ou `keep`), `target` (la branche cible ; la branche courante du projet tant que le Kanban n’en a pas), `strategy` (`merge`, `squash` ou `rebase`), `draft`, `cleanup`, `conventional`, `conflict` (`ask`, `agent` ou `abort`), `maxParallel`, `autopilot`, `model`, `effort` et `mode` des agents de tickets (vides : ceux de l’app, que `defaults` donne), `testsFirst` (vrai seulement si le Kanban a une commande de test), `testCommand` et `prefix`. Ouvert à tous les projets. La réponse redonnée telle quelle à `set_board` est acceptée et ne change rien. |
| `get_workflow` | `project` | Les workflows d’un projet, comme l’onglet Workflow les montre (relus si un fichier lu a changé), avec les corrections de Réglages › Projets › Workflow : pour chacun ses portes d’entrée, ses étapes (commande, sous-agents, fichiers lus et écrits, et `agentsHere`, les agents qui y sont maintenant : id, nom, depuis quand, Nᵉ passage), ses retours (`back`, avec leur `condition` et leur `max`), ses fichiers d’état et sa sortie ; puis `alone` (les commandes qui ne sont d’aucun workflow) et `agentsElsewhere` (les agents qui suivent un workflow sans être sur une étape). `list_agents` et `get_agent_summary` donnent aussi le `workflow` de chaque agent, le second avec l’historique de ses étapes. Voir [les workflows](workflows). |
| `get_agent_summary` | `agent`, `project` (facultatif) | Un agent sans sa conversation : id, nom, état, harness (`engine`, comme dans `list_agents`), clé du ticket, dernier message (2 000 caractères au plus ; un message plus long donne son début et sa fin) et fichiers modifiés (les 100 derniers au plus), avec le nombre et le type des demandes qui attendent une réponse et, comme dans `list_agents`, ses sous-agents et ses tâches de fond en cours (`subagentsRunning` et `backgroundTasksRunning`) et son remote control (`remoteControl`, `remoteSource`, `remoteState` et `interfaceRemote`). |
| `list_background_work` | `agent`, `project` (facultatif) | Les sous-agents et les tâches de fond d’un agent, comme la barre latérale les montre : ce qui tourne d’abord, puis ce qui est fini, le dernier fini d’abord. Rend l’agent (`id`, `name`, `status`), ses deux comptes (comme dans `list_agents`), puis `subagents` et `tasks`. Un sous-agent donne son `id` (celui de l’appel qui l’a lancé), son `type` (`subagent`), sa `description`, son type de sous-agent (`subagentType`), son `model`, son `status` (`running`, `done`, `failed`, `stopped` ou `interrupted`), `background` (en arrière-plan, sinon au premier plan), `startedAt` et `endedAt` (en millisecondes), ses `tools` et ses `tokens`, ce qu’il fait (`doing`), sa tâche (`taskId`) et le sous-agent qui l’a lancé (`parent`). Une tâche de fond donne son `id` (celui de Claude Code), son `type` (`command`, `monitor`, `remote`, `teammate` ou `workflow`), sa `description`, sa `command`, son `status`, `startedAt` et `endedAt`, son `summary` (le dernier mot de Claude Code sur elle, avec le code de sortie d’une commande) et `parent` (la tâche du sous-agent qui l’a lancée) ; un workflow ajoute `name`, `now` (sa phase), `tools` et `tokens`. Un champ sans valeur est omis, et le chemin du fichier de sortie n’est jamais donné. Ouvert, comme `get_agent_summary`, à tous les projets que l’appelant voit : Claude hors d’Escouade voit tout, et un agent d’Escouade tout des projets qu’il voit. |
| `get_background_output` | `agent`, `project` (facultatif), `id`, `bytes` (facultatif) | La **fin** de la sortie d’une commande ou d’une surveillance, avec les bornes et les vérifications de la fenêtre : 8 Kio d’une tâche qui tourne (de son processus, sinon de son fichier de sortie), jusqu’à 256 Kio du fichier une fois finie, et seulement le fichier `<tâche>.output` d’un dossier `tasks`, jamais un chemin réseau. `bytes` (de 1 à 65 536, 8 192 par défaut, pour une tâche qui tourne comme pour une tâche finie) en demande moins : la fin est gardée, coupée à un caractère. La fenêtre garde ses bornes, mais un client MCP ne peut pas en demander autant : 256 Kio de journal, échappés en JSON, dépasseraient les quelque 25 000 jetons qu’une réponse d’outil peut faire pour Claude Code. Une valeur hors de la plage est ramenée dedans, pas refusée ; une valeur illisible (`"abc"`, `-1`) est refusée. Rend `agent`, `id`, `type`, `status`, `source` (`process`, `file`, `report` ou `none`), `output`, `totalBytes` et `truncated` (vrai quand le début manque). Un agent distant, un coéquipier et un workflow n’ont pas de sortie (`source` vaut `none`). Pour un sous-agent, l’outil rend son rapport (16 000 octets au plus, comme dans la fenêtre, rendu entier : `bytes` ne s’y applique pas ; `source` vaut `report`, ou `none` tant qu’il n’a rien rendu), et `id` peut être sa tâche (`taskId`). En vue Claude Code, le rapport est lu dans le transcript du sous-agent sans rien changer à sa ligne : lire un rapport ne change rien. Un agent d’Escouade lit dans les projets qu’il voit, ses propres tâches comprises. |
| `list_requests` | `agent` (facultatif), `project` (facultatif) | Les questions et les demandes d’autorisation qui attendent ta réponse, d’un agent, d’un projet ou de tous, dans l’ordre où elles sont venues : l’agent et la clé de son ticket, `request` (l’id que nomment les deux outils de réponse), `type` (`permission`, `question`, ou `plan` pour un plan à approuver), depuis quand, l’outil et ce sur quoi il agit (la commande, le fichier, le plan entier), tout ce que Claude Code a envoyé (le contenu d’un fichier à écrire, les chaînes d’un Edit, les options d’une commande), la raison, si Claude Code la refuserait par défaut, et pour une question ses questions avec leurs options et si plusieurs se choisissent. `cut` dit si un texte a été coupé : la demande entière est dans la conversation. Un agent en vue Claude Code n’a rien ici : ses demandes sont dans son terminal. |
| `wait_ticket` | `tickets` (1 à 20), `timeout` (facultatif), `since` (facultatif) | Attend que l’un de ces tickets change, puis dit quoi : sa colonne, son blocage (`blocked`, `conflict`), son agent qui se met à attendre une réponse ou cesse de l’attendre (`waiting` : `list_requests` donne les demandes), son agent qui se repose en « À tester » (`resting` : le ticket peut être validé) ou sa suppression (`gone`). Répond au premier changement, ou au bout de `timeout` secondes (120 par défaut, 240 au plus) avec `changed: false`. Chaque réponse donne un `since` : repasse-le à l’appel suivant (même après d’autres outils) et un ticket dont l’état diffère de celui qu’il garde est répondu aussitôt, un changement survenu entre les deux appels compris ; sans `since`, c’est l’état de chaque ticket à l’appel qui sert de comparaison. Si le client annule la requête ou coupe la connexion, l’attente s’arrête. |

### Agir

Ces outils font ce que tu ferais dans la fenêtre, par les mêmes fonctions : la fenêtre est prévenue, les tickets externes suivent et le Kanban se met à jour.

| Outil | Arguments | Ce qu’il fait |
|---|---|---|
| `create_ticket` | `project`, `title`, `description`, `criteria`, `after`, `images`, `files`, `account`, `model`, `effort` | Crée un ticket « À faire » au bas de la colonne. `criteria` est une liste (deux critères par défaut sans elle), `after` les tickets qu’il attend, par clé ou id. `images` joint des images au ticket, et `files` des fichiers de tout format, comme dans sa fenêtre. Avec le pilote auto allumé, il part dès qu’une place est libre et que ses prédécesseurs sont terminés. Sa description se termine par « Créé par `<auteur>` via Escouade ». `account` (le nom du compte ou son id), `model` et `effort` règlent ses agents comme « Compte », « Modèle » et « Effort » de sa fenêtre ; `auto`, par défaut, prend le compte courant, puis le modèle et l’effort du Kanban, sinon du compte. Un ticket fixé sur un compte y part toujours et y reste, en attendant sa remise à zéro à la limite. Un compte que le projet ne peut pas utiliser est refusé avec sa raison. |
| `update_ticket` | `ticket`, `title`, `description`, `criteria`, `after`, `addImages`, `removeImages`, `addFiles`, `removeFiles`, `account`, `model`, `effort` | Modifie un ticket « À faire », champ par champ : ce qui est omis reste. `criteria` et `after` remplacent la liste entière. `addImages` ajoute des images à la fin, `removeImages` en retire : celles qu’aucun des deux ne nomme sont gardées (il n’y a pas de remplacement de toute la liste, un oubli ne fait rien perdre), et les deux se combinent. `addFiles` et `removeFiles` font de même pour les autres fichiers, et un fichier retiré est effacé. Des images ou des fichiers seuls ne changent rien d’autre, la description non plus. Un ticket déjà parti ne se modifie pas, images et fichiers compris, et le refus vient avant la lecture de tout fichier donné ; une dépendance qui ferait attendre deux tickets l’un l’autre est refusée. Si titre, description ou critères changent, la dernière ligne de la description devient « Modifié par `<auteur>` via Escouade ». `account`, `model` et `effort` comme pour `create_ticket` : `auto` les remet par défaut. |
| `move_ticket` | `ticket`, `position` (`top`, `bottom` ou `before`), `before` | Place un ticket « À faire » en tête, en bas, ou juste avant un autre ticket « À faire » du projet (`before`). Rend les clés de la colonne dans leur nouvel ordre. |
| `set_board` | `project`, et au choix `action`, `target`, `strategy`, `draft`, `cleanup`, `conventional`, `conflict`, `maxParallel`, `autopilot`, `model`, `effort`, `mode`, `testsFirst` | Règle le Kanban d’un projet, comme sa fenêtre de réglages : seuls les champs donnés changent, et `""` pour `model`, `effort` ou `mode` remet celui de l’app. Les contrôles sont ceux de la fenêtre : un modèle connu, un effort parmi `low`, `medium`, `high`, `xhigh` ou `max`, un mode parmi `auto`, `default`, `plan` ou `acceptEdits`, une branche cible locale du projet, de 1 à 6 tickets en parallèle. La fenêtre se met à jour et le Kanban se replanifie : allumer le pilote auto peut démarrer des tickets. Le changement vaut pour les prochains agents de tickets, pas pour ceux déjà lancés. Rend le Kanban après le changement, au format de `get_board`. Un agent qui mène le Kanban peut ainsi passer les agents de tickets sur Sonnet pour ménager le quota. La réponse de `get_board` redonnée telle quelle est toujours acceptée et ne change rien : une `target` égale à celle du Kanban (même vide) ou à celle que `get_board` montre est laissée telle quelle, sans contrôle, et `testsFirst` n’est refusé sans commande de test que pour l’allumer. Un agent d’Escouade règle ainsi le Kanban des projets qu’il voit, mode compris. Avec Haiku, qui n’a ni effort ni mode Auto, les agents de tickets partent sans effort et, si le mode est `auto`, en mode « Demander ». |
| `start_ticket` | `ticket`, `account`, `model`, `effort` | Lance un ticket « À faire » comme le bouton « Lancer » : son agent démarre dès qu’une place est libre. Rend la main une fois le ticket en file ; suis-le avec `get_ticket`. `model` et `effort` ne valent que pour ce ticket et passent avant ceux du Kanban pour son agent (garder `opus` sur un ticket d’architecture quand le Kanban est sur `sonnet`) : `""` remet ceux du Kanban, omis ils ne changent pas, avec les mêmes contrôles que `set_board`. Rend `key`, `starting`, et le `model` et l’`effort` avec lesquels son agent partira (ceux du ticket, sinon du Kanban, sinon de l’app) ; l’`effort` manque quand ce modèle n’en prend pas (Haiku, dont l’agent part aussi en mode « Demander » si son mode serait `auto`). Le ticket garde les siens s’il est renvoyé puis relancé. Sa carte les montre, sans l’effort avec Haiku, à côté de sa clé (« Opus · Max »). `account` (nom ou id, `auto` pour le compte courant) fait de même pour le compte : il prime sur celui du ticket et devient le sien. |
| `create_agent` | `project`, `message`, `worktree`, `model` | Crée un agent dans un projet, avec son premier message, sans changer l’agent que tu regardes. `worktree` (vrai ou faux) dit s’il travaille dans un worktree à lui, sinon le projet décide ; `model` se nomme comme dans Claude Code (`sonnet`, `opus`, `haiku`…). Rend l’id et le nom de l’agent. |
| `send_message` | `agent`, `project`, `text` | Écrit à un agent. Un agent au travail lit le message après son tour en cours (la réponse dit `queued`). Le texte fait 32 000 caractères au plus (des caractères, pas des octets) : au-delà, une erreur dit combien il en fait, sans le renvoyer. La fenêtre ne change pas. |
| `stop_agent` | `agent`, `project` | Interrompt le tour en cours d’un agent, comme le bouton stop de sa conversation. L’agent reste, et peut recevoir un message ensuite. |
| `stop_background_work` | `agent`, `project` (facultatif), `id` | Arrête une tâche de fond, un workflow ou un sous-agent en arrière-plan, comme « Arrêter » de sa vue dans la fenêtre. `id` est celui d’une ligne de `list_background_work` (pour un sous-agent, son id d’appel ou sa tâche `taskId`). Rend `agent`, `id`, `type` et `stopped: true`. Les refus sont ceux du bouton : la ligne ne tourne plus, c’est un sous-agent au premier plan (l’agent l’attend, et « Arrêter » de l’agent l’arrête avec son tour), Claude Code n’a pas encore donné sa tâche, l’agent est en vue Claude Code (son interface le fait), n’a pas de processus ou est archivé. La réponse dit que l’arrêt est demandé : la fin de la ligne arrive ensuite, et `list_background_work` la montre. Claude Code fait faire un tour à l’agent pour le constater, ce qui lui coûte du quota. Un agent d’Escouade n’arrête rien de son propre agent, tâches de fond et sous-agents compris. |
| `message_subagent` | `agent`, `project` (facultatif), `subagent`, `text` | Écrit à un sous-agent en arrière-plan, comme « Lui écrire » de sa vue dans la fenêtre. Claude Code ne laisse écrire directement à aucun sous-agent : le message va à l’agent, qui est prié de le transmettre tel quel au sous-agent par son outil `SendMessage`. Il est précédé de « Message de `<auteur>` : » et jamais présenté comme le tien. Cela coûte un tour à l’agent, donc du quota. Refusés : un sous-agent qui ne tourne plus (« Ce sous-agent ne tourne plus. », même avec une tâche donnée : Claude Code le reprendrait avec le message, pour rien), un sous-agent au premier plan ou dont Claude Code n’a pas donné la tâche, un agent en vue Claude Code ou archivé, et un `subagent` qui est une tâche de fond et non un sous-agent. Un texte vide, ou de plus de 32 000 caractères (des caractères, pas des octets ; l’erreur dit combien le message en fait, sans le renvoyer), est une erreur, comme pour `send_message`. Quand le compte Claude de l’agent est retenu par le quota, le message est refusé aussi, comme `send_message`, mais seulement après tout le reste : un client ne va pas réessayer à 14 h pour être refusé de toute façon. Rend `agent`, `subagent` et `queued` (vrai quand l’agent est au travail : le message attend la fin de son tour). Un agent d’Escouade n’écrit pas à ses propres sous-agents. |
| `answer_permission` | `agent`, `project`, `request`, `decision` (`allow` ou `deny`), `message` | Répond à une demande d’autorisation d’un agent comme « Autoriser » et « Refuser » de sa carte, ou approuve (`allow`) ou renvoie (`deny`) son plan. `message`, avec `deny`, dit à l’agent pourquoi, ou quoi faire à la place. « Toujours autoriser » n’est pas offert (`always` est refusé) : une règle durable reste ta décision, dans la fenêtre. La carte de la demande, dans la conversation de l’agent, dit qui a répondu (« Autorisé par `<auteur>` via Escouade »), et l’agent lit qui a refusé. |
| `answer_question` | `agent`, `project`, `request`, `answers` | Répond à une question d’un agent comme sa carte de question : pour chaque question (`question`, son texte, qu’on peut omettre quand il n’y en a qu’une), les libellés des options choisies (`choices`, plusieurs seulement quand la question l’accepte) ou un texte libre (`text`). Chaque question veut une réponse. La carte dit « Répondu par `<auteur>` via Escouade », et l’agent lit chaque réponse suivie de son auteur. |
| `approve_ticket` | `ticket` | Valide un ticket « À tester » comme le bouton « Valider… » : les tests d’abord quand le Kanban les lance, le commit, puis ce que disent les réglages du Kanban du projet (fusion dans la branche cible, push et pull request, push de la branche, ou branche gardée). Un ticket dont la branche n’apporte rien de plus que sa cible, parce que tu l’as déjà fusionnée à la main, est clos sans fusionner de nouveau. Répond dès que la validation est partie, avec le ticket (son étape dit « Validation… ») et son `since` : suis-la avec `wait_ticket` ou `get_ticket`. Il peut pousser et ouvrir une pull request. |
| `reject_ticket` | `ticket`, `comment` | Renvoie un ticket « À tester » comme « Renvoyer » : il repart « En cours », avec le même agent et le même worktree, et l’agent reçoit le commentaire comme un retour de test, suivi de « (renvoyé par `<auteur>` via Escouade) ». Un commentaire vide est refusé. Rend le ticket et son `since`. |
| `resume_ticket` | `ticket` | Reprend un ticket « En cours » bloqué comme « Reprendre » : son agent poursuit, ou le ticket repart quand son agent a disparu. Refusé pour un ticket qui n’est pas bloqué, ou dont l’agent attend la remise à zéro de son quota (le refus dit jusqu’à quand). Rend le ticket et son `since`. |
| `resolve_conflict` | `ticket` | Confie à l’agent le conflit de fusion d’un ticket « À tester » comme « L’agent résout » : la branche cible est fusionnée dans la sienne, puis l’agent est invité à résoudre les conflits (à rebaser, avec la stratégie rebase) et à finir par son rapport. Refusé pour un ticket sans conflit. Rend le ticket et son `since`. |
| `dismiss_block` | `ticket` | Écarte le blocage d’un ticket « À tester » (un conflit, une étape en échec) comme « Annuler » : le blocage disparaît, le ticket reste « À tester » et rien d’autre ne change. Rend le ticket et son `since`. |
| `delete_ticket` | `ticket` | Supprime un ticket de n’importe quelle colonne comme « Supprimer ». Un ticket « En cours » ou « À tester » voit son agent archivé, son worktree gardé ; les tickets qui venaient après lui ne l’attendent plus. Irréversible. Refusé tant que la validation du ticket tourne. Rend `key`, `deleted` et `agentArchived`. |

Un titre fait 200 caractères au plus, une description 10 000, et un ticket 30 critères de 500 caractères au plus. Le texte de `send_message` et de `message_subagent` fait 32 000 caractères au plus. Un ticket créé par le serveur a le nombre de boucles par défaut, 5, et sa propre branche.

Les images d’un ticket se joignent avec `create_ticket` (`images`) et `update_ticket` (`addImages`). Une image à joindre est `{ name, mediaType, data, path }`, avec exactement un de `data` (son contenu en base64, et `name` est alors obligatoire) ou `path` (le chemin d’un fichier de ta machine, dont le nom sert de `name` s’il manque). `mediaType` est indicatif : comme dans la fenêtre, le type est lu dans le contenu. Pour en retirer avec `removeImages`, ou en lire une avec `get_ticket_image`, on désigne l’image par `{ file, index }` : son `file`, le nom que `get_ticket` donne, ou son `index`, son rang dans la liste de `get_ticket` à partir de 0.

Les autres fichiers d’un ticket, de tout format, se joignent avec `create_ticket` (`files`) et `update_ticket` (`addFiles`). Un fichier à joindre est `{ name, data, path }` : son contenu en base64 (`data`, avec `name`), pour un petit fichier, car une requête pèse 32 Mio au plus ; ou le chemin d’un fichier de ta machine (`path`), qui est alors copié. Les règles sont celles de la fenêtre du ticket, parce que le fichier suit le même chemin : 20 fichiers au plus par ticket, chacun dans la taille maximale de [Réglages › Harness](settings-claude-code#pieces-jointes). Elles sont vérifiées avant toute copie, et un refus ne laisse rien. Le nom est nettoyé comme celui d’un fichier que la fenêtre copie. Pour en retirer avec `removeFiles`, ou en lire un avec `get_ticket_file`, on le désigne par `{ file, index }`, comme une image.

### Orienter les agents vers l’index

Quand un projet allume « Index du code », Escouade oriente ses agents vers ces outils plutôt que vers grep, sans jamais bloquer une recherche. Dans les vues de Claude Code et de Codex, dont Escouade écoute les hooks, une recherche qui vise un symbole (`grep`, `rg`, l’outil Grep, pour un nom comme `parse_config` ou `parseConfig`, ou une déclaration comme `fn parse`) reçoit, avant de s’exécuter, une ligne qui dit que l’index y répond en un appel ; une recherche de texte (un message, une phrase, un mot ordinaire) passe sans un mot. Pour les autres harness et vues, et pour les agents pilotés sans vue terminal, le même conseil est une règle dans la consigne de l’agent. Ce que l’index a fait économiser est compté par agent et par projet, pour les statistiques.

### Mener tout le Kanban depuis Claude

Avec ces outils, Claude conduit un ticket de bout en bout sans que tu ouvres la fenêtre : `start_ticket` le lance, `wait_ticket` attend qu’il change (son agent pose une question, passe en « À tester », se bloque), `get_ticket` dit où il en est, puis `approve_ticket` le valide ou `reject_ticket` le renvoie avec ce qui ne va pas. `resume_ticket`, `resolve_conflict` et `dismiss_block` règlent un blocage, et `delete_ticket` supprime. `wait_ticket` rend la main au premier changement, ou au bout de 120 secondes par défaut (240 au plus) ; le `since` de sa réponse, repassé à l’appel suivant, fait répondre aussitôt un ticket dont l’état diffère de celui qu’il garde, un changement survenu entre deux appels compris. `approve_ticket`, `reject_ticket`, `resume_ticket`, `resolve_conflict` et `dismiss_block` rendent aussi un `since`, celui du ticket tel qu’il était avant l’action : passé à `wait_ticket`, il fait dire aussitôt ce qui suit, une validation rapide comprise.

Chacun suit les règles du bouton de la fenêtre et les garde-fous ci-dessous : un agent d’Escouade ne valide ni ne renvoie son propre ticket, et n’agit que dans les projets qu’il voit.

### Les sous-agents et les tâches de fond d’un agent

Un agent « Terminé » peut avoir encore du travail qui tourne : `list_agents` et `get_agent_summary` comptent ses sous-agents en cours (`subagentsRunning`) et ses tâches de fond en cours (`backgroundTasksRunning`, le « N en fond » de sa carte). Quand l’un des deux n’est pas nul, `list_background_work` dit lesquels, `get_background_output` lit la fin de la sortie d’une commande ou le rapport d’un sous-agent, puis `stop_background_work` arrête ce qui ne doit pas continuer, ou `message_subagent` donne une consigne à un sous-agent en arrière-plan. C’est ce que tu fais dans la fenêtre avec [les sous-agents](plan#les-sous-agents) et [les tâches de fond](plan#les-taches-de-fond) d’un agent, avec les mêmes bornes et les mêmes refus. La sortie d’une commande peut être longue : `bytes` (64 Kio au plus) en demande moins que la fenêtre, pour que la réponse tienne dans ce que Claude Code accepte d’un outil (environ 25 000 jetons). Lire n’est jamais agir : `get_background_output` ne change rien, même pour le rapport d’un sous-agent en vue Claude Code.

### La mémoire partagée

Quatre outils lisent et écrivent la [mémoire partagée](shared-memory) d’un projet, le carnet de travail de ses agents : `search_memory` (`query`, `limit` facultatif), `read_memory` (`name`), `write_memory` (`name`, `description`, `type` facultatif, `body`) et `forget_memory` (`name`). Chacun prend un `project`, qu’un agent d’Escouade peut omettre pour le sien. Ils ne touchent qu’au dossier `.escouade/memory/` du projet, jamais à travers un lien symbolique.

### Réservés aux agents d’Escouade

Ces deux outils sont refusés à Claude hors Escouade.

| Outil | Arguments | Ce qu’il fait |
|---|---|---|
| `report_progress` | `line` | Publie une ligne d’état de 120 caractères au plus, sur ce que l’agent fait. Elle s’affiche sous son nom dans la barre latérale et la vue d’ensemble, et sur la carte de son ticket « En cours », jusqu’à son prochain appel. Une ligne vide l’efface. |
| `split_ticket` | `tickets`, `chain` | Découpe ce qui reste du ticket de l’agent en dix tickets « À faire » au plus, après le sien. Avec `chain` vrai (par défaut), chacun vient après le précédent et le premier après le ticket de l’agent ; faux, tous viennent après le ticket de l’agent seul et peuvent tourner en parallèle. Chaque ticket peut avoir ses `images`, qui nomment des images du ticket de l’agent (par `file` ou `index`, comme pour `removeImages`) : sans cet argument, il les reprend toutes, avec `[]` aucune. Chacun reçoit ses propres copies, et le ticket de l’agent garde les siennes. Une référence inconnue, ou une image nommée dans `images` dont le fichier manque, refuse tout et ne crée rien ; sans `images`, une image du ticket de l’agent dont le fichier a disparu est sautée au lieu de bloquer le découpage. Ses autres fichiers suivent la même règle avec `files` : tous par défaut, ceux nommés, ou aucun avec `[]` ; un fichier pris par défaut qui a disparu, ou que les réglages ne permettent plus (trop gros), est sauté, et nommé il refuse tout. Refusé à un agent sans ticket. Rend les clés des tickets créés, ou, si des images ou des fichiers ont été sautés, `tickets` (les clés) et `skipped` (une phrase pour chacun). |

## Les garde-fous

Les outils qui agissent suivent les règles de la fenêtre et du pilote auto :

- **Quota.** Aucun ticket (`start_ticket`) ni agent (`create_agent`) ne démarre quand tous les comptes utilisables pour le projet sont à leur limite : fenêtre de quota épuisée, limite d’usage, agent qui attend sa remise à zéro. « Pause au-delà du quota » et le budget du jour ne retiennent que le pilote auto, jamais un outil. Un seul compte libre suffit. Le refus dit jusqu’à quand (« Le pilote auto est en pause jusqu’à 14:30 : la fenêtre de 5 h est utilisée à 100 %. Réessaie à ce moment-là. »). `send_message` est refusé quand le compte de l’agent est retenu ainsi (les agents d’un autre compte peuvent encore recevoir un message), et `message_subagent` aussi, mais après tous ses autres refus.
- **En parallèle.** Le maximum de tickets « En parallèle » du projet n’est pas dépassé par `start_ticket`, ni son maximum d’agents qui travaillent en même temps par `create_agent`.
- **Dépendances.** Un ticket qui vient après des tickets non terminés n’est pas lancé sans eux : le refus dit lesquels, et `update_ticket` retire les dépendances. Une dépendance circulaire est refusée.
- **Images d’un ticket.** Les limites et les refus de la fenêtre : PNG, JPEG, GIF et WebP (le type est lu dans le contenu), 5 Mo par image, 18 Mo en tout et 20 images au plus par ticket, celles qu’`update_ticket` garde comprises ; le total est tenu avant de lire, l’image qui le ferait dépasser est refusée avant d’être lue. Une image refusée ne laisse rien : ni ticket créé, ni modification, ni fichier. Le nom d’une image est nettoyé (ce qui suit le dernier `/` ou `\`, sur une ligne, 100 caractères au plus). Pour `path`, Claude hors Escouade donne n’importe quel chemin absolu vers un fichier de ta machine ; un agent d’Escouade seulement un fichier sous son dossier de travail (un lien, symbolique ou jonction, qui en sort est refusé), et un fichier hors de ce dossier reçoit le même refus qu’il existe ou non. C’est un garde-fou du serveur, pas une frontière de sécurité : un agent qui a la main sur ta machine a d’autres voies. Sont aussi refusés : un chemin relatif ou réseau (`\\serveur\partage`, `//hôte/partage`), ce qui n’est pas un fichier ordinaire, un fichier de plus de 5 Mo (refusé sans être lu) et un fichier qui n’est pas une image. Le chemin n’est pas gardé : le ticket garde une copie du contenu. Un ticket déjà parti garde ses images.
- **Autres fichiers d’un ticket.** Les limites et les refus de la fenêtre : 20 fichiers au plus par ticket, ceux qu’`update_ticket` garde compris, chacun dans la taille maximale des réglages ; vérifiées avant toute copie (le nombre avant de regarder un fichier, la taille d’un fichier avant d’en lire un octet). Un refus ne laisse rien, pas même une copie en attente. `path` suit les règles des images : un agent d’Escouade ne donne qu’un fichier de son dossier de travail. `get_ticket_file` ne rend pas plus de 64 Kio à la fois, et ne donne le chemin qu’à Claude hors Escouade.
- **Régler le Kanban.** Le modèle et l’effort ont les contrôles de la fenêtre dans les deux outils, `set_board` et `start_ticket` : un modèle inconnu, ou un effort hors de la liste, est une erreur. Le reste ne vaut que pour `set_board` (`start_ticket` n’a pas de mode). Il refuse `bypassPermissions` : lancer des agents sans aucune demande de permission reste ta décision, dans la fenêtre, comme « Toujours autoriser » (il est accepté seulement s’il est déjà le mode du Kanban, pour changer autre chose sans le défaire) ; les autres modes (`auto`, `default`, `plan`, `acceptEdits`) se règlent comme dans la fenêtre, y compris par un agent d’Escouade pour le Kanban des projets qu’il voit. Il refuse aussi `testsFirst` sans commande de test, pour l’allumer seulement : le serveur ne lance aucune commande et ne change pas celle du Kanban, qui se règle dans la fenêtre. Un mode hors de la liste, une branche cible qui n’est pas une branche locale du projet (sauf celle que le Kanban a déjà, même vide, ou celle que `get_board` montre : elle est laissée telle quelle), un « En parallèle » hors de 1 à 6, ou aucun champ à changer, est une erreur.
- **Le remote control.** `list_projects`, `list_agents` et `get_agent_summary` le lisent ; aucun outil ne l’allume, ne l’éteint ni ne le règle, pour un agent, un projet ou tous : l’allumer expose une session sur internet, joignable depuis claude.ai et l’app Claude. Cela reste ta décision, dans la fenêtre (Réglages › Harness, Réglages › Projets, clic droit d’un agent), comme `bypassPermissions` et la commande de test du Kanban, que les outils ne règlent pas non plus.
- **Le Kanban.** `start_ticket` est refusé quand le Kanban du projet ne démarre rien pour l’instant (la branche cible n’a aucun commit ou est introuvable, aucun compte actif ne sert le projet) ; le refus dit pourquoi.
- **Les tickets partagés.** Un ticket partagé par un coéquipier ([Partager le Kanban](shared-board)) ne se lance qu’à la main : `start_ticket` le refuse, et `delete_ticket` aussi. Les outils de tickets disent le partage (`shared`), et `create_ticket` et `update_ticket` prennent `shared` pour partager un ticket ou arrêter.
- **Les agents d’Escouade** agissent là où ils voient, Kanban compris : l’agent d’un projet qui n’est pas privé, sur le sien et sur tous les projets qui ne sont pas privés ; l’agent d’un projet privé, sur le sien seul. Un projet privé n’est donc touché que par ses propres agents, et un refus ne le nomme jamais. Ils ne s’écrivent pas à eux-mêmes, ne s’arrêtent pas eux-mêmes, n’arrêtent ni leurs propres tâches de fond ni leurs propres sous-agents, n’écrivent pas à ces derniers et ne répondent pas à leurs propres demandes. On n’écrit pas à un agent archivé.
- **Les sous-agents et les tâches de fond.** Chaque outil est refusé là où la fenêtre refuse, avec le même texte. `stop_background_work` l’est pour une ligne qui ne tourne plus, un sous-agent au premier plan, une tâche que Claude Code n’a pas encore donnée, un agent en vue Claude Code, sans processus ou archivé. `message_subagent` l’est pour un sous-agent qui ne tourne plus, qui est au premier plan ou qui n’a pas de tâche donnée, un agent en vue Claude Code ou archivé, un `subagent` qui est une tâche de fond, et, en dernier seulement, quand le compte Claude de l’agent est retenu (un client ne va pas réessayer à 14 h pour être refusé de toute façon) ; un texte vide ou de plus de 32 000 caractères, comme celui de `send_message`, est une erreur. `get_background_output` ne lit que le fichier `<tâche>.output` de la tâche, jamais un autre fichier ni un chemin réseau. Un agent d’Escouade n’arrête ni ses propres tâches de fond ni ses propres sous-agents et n’écrit pas à ces derniers ; il agit et lit sorties et rapports dans les projets qu’il voit. Chaque appel est noté dans l’activité MCP, sans le texte du message ni la sortie.
- **Le flux du Kanban.** Chaque outil est refusé là où la fenêtre refuse : `approve_ticket` et `reject_ticket` pour un ticket qui n’est pas « À tester », dont l’agent travaille ou dont la validation tourne déjà ; `resume_ticket` pour un ticket qui n’est pas « En cours », qui n’est pas bloqué ou dont l’agent attend la remise à zéro de son quota ; `resolve_conflict` pour un ticket sans conflit ; `dismiss_block` pour un ticket qui n’est pas bloqué ; `delete_ticket` pour un ticket dont la validation tourne (« La validation de ce ticket est en cours : attends sa fin pour le supprimer. »). Un message que le flux envoie à un agent (`reject_ticket`, `resolve_conflict`, `resume_ticket`) n’est remis que tant que le compte Claude de cet agent n’est pas retenu. Un agent d’Escouade ne valide ni ne renvoie son propre ticket (valider, ce serait fusionner son travail sans relecture), et n’agit pas non plus sur lui avec `resume_ticket`, `resolve_conflict`, `dismiss_block` et `delete_ticket` : c’est à toi ou à un autre client de le faire. Tout client du serveur peut valider un ticket, et `delete_ticket` supprime comme la fenêtre, un ticket de n’importe quelle colonne. Chaque appel est noté dans l’activité MCP.
- **Répondre à une demande.** Une fois « Les agents peuvent piloter Escouade » allumé, tout client du serveur voit les demandes de tous les projets et peut y répondre, Claude hors Escouade comme les agents, sans réglage de plus ; un agent répond à celles des agents des projets qu’il voit, jamais aux siennes. `answer_permission` n’offre que `allow` et `deny` : « Toujours autoriser » reste ta décision, dans la fenêtre. Une demande qui n’attend plus de réponse (tu y as répondu dans la fenêtre, un autre client aussi, ou l’agent ne tourne plus) est refusée, et si deux réponses arrivent en même temps, une seule passe. Un agent en vue Claude Code n’a rien à répondre ici : ses demandes sont dans son terminal.
- **Aucun outil** ne lance une commande de son choix ni ne supprime un projet ou un agent : un agent poussé par un contenu piégé ne peut donc pas s’en servir pour monter en droits. Les exceptions sont la réponse aux demandes des agents et le flux du Kanban. Avec l’interrupteur allumé, un agent peut autoriser, une demande à la fois et jamais pour de bon, ce qu’un autre agent de son projet demande ; il peut aussi valider (les tests, puis la fusion) ou supprimer le ticket d’un autre agent de son projet, comme tu le ferais dans la fenêtre.
- **Ce qui vient du serveur n’est jamais pris pour toi.** Un message envoyé à un agent (`send_message`, premier message de `create_agent`, ou texte que `message_subagent` fait transmettre à un sous-agent) est lu par l’agent et montré dans sa conversation sous « Message de `<auteur>` : », l’auteur étant le nom de l’agent qui l’envoie ou « Claude (hors Escouade) ». Un ticket créé ou découpé par le serveur se termine par « Créé par `<auteur>` via Escouade », un ticket modifié par « Modifié par `<auteur>` via Escouade », sur sa carte comme dans le protocole de son agent. La carte d’une demande à laquelle le serveur a répondu dit qui l’a fait (« Autorisé par `<auteur>` via Escouade », « Refusé par `<auteur>` via Escouade », « Répondu par `<auteur>` via Escouade »), et un refus, comme chaque réponse à une question, dit à Claude de qui il vient, pas que c’est toi (« Refusé par `<auteur>` via Escouade », « SQLite (réponse de `<auteur>` via Escouade) »).

Une demande d’autorisation d’un outil d’Escouade le nomme en clair (« Escouade · Créer un ticket », « Escouade · Lancer un agent »…) et montre ce que Claude lui donne, un argument par ligne. Une valeur de plus de 2 000 caractères est coupée : la carte dit combien ne sont pas montrés et renvoie à la conversation.

## Les agents d’Escouade et le serveur

L’interrupteur « Les agents peuvent piloter Escouade » sert aussi les agents d’Escouade, ceux de tous les projets : il n’y a rien à permettre dans les réglages d’un projet.

- **Allumé**, chaque agent reçoit le serveur au démarrage de son processus, avec un jeton à lui : il agit en son nom, jamais comme Claude hors Escouade. Il lit les tickets et les agents, et peut créer des tickets ou lancer d’autres agents, ce qui dépense du quota, et mener les tickets à leur validation, sauf le sien. Il voit aussi les questions et les demandes d’autorisation des agents, et peut y répondre. Tout cela dans son projet et dans tous ceux qui ne sont pas privés.
- **Éteint**, les agents déjà lancés perdent les outils tout de suite, et Escouade tient son serveur à l’écart de chaque agent qui démarre, même si une entrée `escouade` reste dans ta config de Claude Code : ses outils sont refusés, et le serveur lui-même n’est pas chargé (Escouade démarre l’agent avec le réglage `deniedMcpServers` de Claude Code). L’agent ne reçoit donc ni les outils, ni les instructions du serveur.
- **Un agent déjà lancé** quand tu allumes l’interrupteur garde un processus sans les outils. Sa conversation affiche « Outils d’Escouade au prochain démarrage » avec « Relancer » : son processus s’arrête et le suivant reprend la même session : la conversation reste. Le bouton est grisé tant que l’agent est occupé (son tour, une question ou une autorisation qui attend ta réponse, la préparation de son worktree, un sous-agent, un workflow, une commande ou une surveillance en arrière-plan) et revient quand c’est fini. Une commande, un serveur de dev ou une surveillance ne finit pas seul : la carte dit alors d’arrêter d’abord ses tâches de fond, depuis leur vue (« Arrêter » ; voir [les tâches de fond](plan#les-taches-de-fond)). En vue Claude Code, « Relancer » redémarre son interface. Réglages › Harness dit combien d’agents sont dans ce cas.
- Entre projets qui ne sont pas privés, ce n’est pas un cloisonnement : un agent lit et agit dans son projet comme dans les autres. Ainsi l’agent du back d’un produit crée, modifie et lance les tickets de son front, et écrit à ses agents. Pour cloisonner un projet, rends-le privé (ci-dessous).

Le serveur tourne tant que l’interrupteur est allumé, et s’arrête avec l’app.

### Les projets privés

Le réglage « Projet privé » d’un projet (Réglages › Projets, groupe « Confidentialité », éteint par défaut) le cloisonne dans le serveur, dans les deux sens, pour les agents d’Escouade :

- **Les agents des autres projets ne le connaissent pas.** Il n’apparaît ni dans `list_projects`, ni dans `list_agents` ou `list_requests`, et un outil qui le nomme, par son id, son nom, un de ses tickets ou un de ses agents, répond qu’il ne le trouve pas, avec le même message que pour un nom qui n’existe pas : rien ne laisse deviner qu’il existe.
- **Ses propres agents ne voient que lui.** `list_projects` ne donne que leur projet, et tout autre projet, privé ou non, leur est introuvable de la même façon. Ils lisent et agissent dans leur projet comme avant.
- **Toi, tu vois tout** : Claude hors Escouade (le jeton déclaré dans tes harness) voit tous les projets, et la fenêtre aussi (onglets, vue d’ensemble, statistiques).

Les projets qui ne sont pas privés se voient et agissent les uns chez les autres. Un cadenas marque un projet privé, sur sa tuile, à côté de son nom dans la barre de titre et dans les réglages. Le changement vaut dès l’appel suivant, sans relancer les agents. Pour que chaque nouveau projet le soit, allume « Nouveaux projets privés » dans le même onglet. Ses fichiers sont cloisonnés aussi, par les règles de chaque harness : voir [ses fichiers](settings-projects#ses-fichiers). Pour que sessions, mémoire et historique du harness ne soient pas partagés non plus, donne-lui [un compte réservé](accounts#un-compte-pour-un-projet-prive).

Hors du serveur non plus, Escouade ne fait rien passer d’un projet privé à un autre :

- **Copier la configuration** : l’assistant « Nouveau projet » ne propose jamais un projet privé comme source, et le dit sous ses choix (« Un projet privé n’est pas proposé : rien d’un projet privé ne passe à un autre. »). Copier un projet qui ne l’est pas dans un projet privé reste possible.
- **Dupliquer la conversation** : la copie reste dans le projet de l’agent copié. Rien ne déplace un agent, une conversation ou un ticket vers un autre projet.
- **Dépendances** : « Après » ne propose que les tickets du même projet, et par le serveur un ticket d’un projet privé est introuvable dans `after` comme ailleurs. `split_ticket` découpe dans le projet de l’agent.
- **Ce qu’Escouade écrit aux agents** (consignes d’un ticket, messages, relances, passation à un autre harness, noms, branches, messages de commit) vient seulement du ticket, du projet et de la conversation de l’agent : jamais le nom ni le contenu d’un autre projet. Les textes rédigés sont demandés sans session gardée.

> [!NOTE]
> Jusqu’à la 1.7, chaque projet avait son interrupteur « Les agents peuvent utiliser Escouade » (Réglages › Projets › Serveur MCP). Il n’existe plus : un projet qui l’avait allumé alors que « Claude peut piloter Escouade » était éteint ne donne plus le serveur à ses agents tant que tu n’allumes pas « Claude et les agents peuvent piloter Escouade ».

Dans une conversation, un appel à un outil d’Escouade porte l’étiquette « Escouade · » suivie de son nom (« Escouade · Lire un ticket », « Escouade · Régler le Kanban », « Escouade · Donner son avancement »).

## L’activité MCP

Réglages › Harness › « Activité MCP » garde les 200 derniers appels et refus, les plus récents en tête, mis à jour en direct. Chaque ligne donne :

- l’heure (au survol, la date) ;
- l’appelant : le nom de l’agent, « Claude (hors Escouade) », ou « Client inconnu » pour une requête refusée avant que son jeton dise d’où elle vient ;
- l’outil, et en bref ce qui lui a été demandé (jamais un jeton ; pour des images ou des fichiers, combien, jamais leur contenu ni un chemin ; pour la sortie d’une tâche de fond ou un message à un sous-agent, l’agent et l’id, jamais la sortie ni le texte) ;
- le résultat : « Fait », « Refusé » ou « Erreur », avec la raison pour les deux derniers (colorés en alerte).

Pour un `set_board` réussi, la ligne garde ce qui a été demandé et dit aussi ce qui a changé : chaque champ changé avec sa valeur avant et après (« model: opus → sonnet · effort: (défaut) → medium »), ou « Aucun changement ».

« Effacer » vide la liste. Le journal n’est pas enregistré : il repart à zéro au prochain démarrage d’Escouade.

Sont aussi refusées, et notées : une requête sans jeton (« Requête refusée : pas de jeton »), avec un jeton inconnu, avec un en-tête `Host` inattendu, avec un en-tête `Origin` (une page web), ou vers un autre chemin que celui du serveur.

## Jeton et réseau

- Le serveur n’écoute que sur `127.0.0.1`, sur un port libre entre 47000 et 47999, choisi au premier démarrage puis gardé (il en change seulement quand le sien est pris, et la déclaration est alors refaite dans chaque compte).
- Chaque requête porte un jeton, dans l’en-tête `Authorization: Bearer`. Celui de Claude hors Escouade est gardé dans le trousseau du système ; quand il le refuse, et sous Linux, dans `~/.escouade/mcp-token.json`, lisible par toi seul. Il est aussi écrit en clair dans la config de chaque harness installé où l’interrupteur le déclare (`~/.claude.json`, `~/.codex/config.toml`, `~/.config/opencode/opencode.json`, `~/.copilot/mcp-config.json` pour « Principal »). Celui d’un agent est propre à cet agent, vit en mémoire et dans un fichier de configuration sous `~/.escouade/mcp/` que l’app retire quand son processus s’arrête. Un agent sans les outils démarre avec `~/.escouade/mcp-refused.json`, qui écarte le serveur.
- Une requête envoyée par une page web (en-tête `Origin`) ou adressée à un autre nom que `127.0.0.1` ou `localhost` est refusée, même avec un jeton : un site que tu visites ne peut pas appeler le serveur.
- Un autre client MCP se connecte à `http://127.0.0.1:<port>/mcp` avec le même en-tête. L’adresse et le jeton se lisent dans l’entrée `escouade` du `.claude.json` du compte, ou dans la commande que l’onglet propose quand la déclaration échoue.
