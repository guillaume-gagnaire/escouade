# The MCP server

Escouade’s MCP server lets Claude Code, Codex, OpenCode, Copilot CLI and Escouade’s agents read your projects, agents, and tickets, create, edit, start, approve, and delete tickets, set a project’s Kanban, and drive agents, including answering their requests, under the same guardrails as the autopilot.

## What it is for

MCP (Model Context Protocol) is the protocol through which a harness (Claude Code, Codex, OpenCode, Copilot CLI) calls tools. Escouade embeds an MCP server: once declared in a harness, it gives it the tools listed below.

- **Claude in a terminal**: you run `claude` wherever you like and talk to it about Escouade (“list the tickets to review in the api project”, “create a ticket to limit login attempts, then start it”).
- **Another tool** that speaks MCP can connect the same way (see [Token and network](#token-and-network)).
- **An Escouade agent**, of any project, with a token of its own (see [Escouade’s agents and the server](#escouade-s-agents-and-the-server)).

The server runs on your machine alone. It only serves to read and to give orders; it runs no command of its own choosing and deletes no project or agent. For a ticket, it does what the Kanban’s buttons do, approving (the tests, then the merge) and deleting included. It can answer an agent’s request on your behalf, but never with “Always allow”: a lasting permission rule stays your decision, in the window.

## Turning on “Agents can drive Escouade”

One switch gives the server to Escouade’s agents in every project, and declares it in every harness installed: Claude Code, Codex, OpenCode and Copilot CLI, started outside Escouade (a terminal, their app).

1. Open Settings › MCP server. The tab has the “Agents can drive Escouade” switch.
2. Turn it on. It saves right away, without “Save”: the declaration writes into the config of each account of each harness, which “Cancel” could not undo.

Escouade then starts the server and declares it in each active account of each harness installed, only the accounts added (a harness without one has it declared nowhere):

| Harness | File (Main account) | How |
| --- | --- | --- |
| Claude Code | `~/.claude.json` | `claude mcp add --scope user --transport http escouade <address> --header "Authorization: Bearer <token>"`, run as the account runs Claude Code (its program, its configuration folder) |
| Codex | `~/.codex/config.toml` | written by Escouade, `[mcp_servers.escouade]` |
| OpenCode | `~/.config/opencode/opencode.json` (under `$XDG_CONFIG_HOME` when it is set; the `opencode.jsonc` there, if there is one) | written by Escouade, `mcp.escouade` |
| Copilot CLI | `~/.copilot/mcp-config.json` | written by Escouade, `mcpServers.escouade` |

Another account has the same file in its folder. For Codex, OpenCode and Copilot CLI, whose command line cannot declare a server with its header, Escouade writes the entry itself and keeps all the rest of the file as it was, comments, order and line endings included; a file linked to the Main account’s stays a link. The entries:

```toml
# Codex
[mcp_servers.escouade]
url = "http://127.0.0.1:<port>/mcp"
http_headers = { Authorization = "Bearer <token>" }
```

```jsonc
// OpenCode
"mcp": {
  "escouade": {
    "type": "remote",
    "url": "http://127.0.0.1:<port>/mcp",
    "headers": { "Authorization": "Bearer <token>" }
  }
}
// Copilot CLI
"mcpServers": {
  "escouade": {
    "type": "http",
    "url": "http://127.0.0.1:<port>/mcp",
    "headers": { "Authorization": "Bearer <token>" }
  }
}
```

The token is written **in plain text** in each of these files, which the group’s note says.

Under the switch, the tab lists each declaration: the harness and the account (“Codex · Main account”), the file, and its state, “Declared” or “Not declared”.

- An entry already up to date is left as it is. A different entry (another port, another token) is replaced. An account added or switched back on later gets the declaration, and so does a harness installed later: when you come back to Escouade’s window, or as soon as it shows this tab or the list of harnesses in Settings › Harness.
- If it fails for an account, the tab says why (“Not declared for the Pro account: …”) and what to do by hand: for Claude Code, the command to run (“Run it by hand in PowerShell:”), written for PowerShell on Windows and for `sh` elsewhere; for the others, the entry to add to the file (“Add it by hand to …:”). The token is masked on screen; “Copy the command” or “Copy the entry” copies the real one. A file that is not valid TOML or JSON is left alone.
- Turning the switch off changes the token at once (the old one opens nothing any more), then takes the entry out of each account of each harness: each file is back to what it was, byte for byte; a file Escouade had made is deleted. Agents already running lose the tools at once too (their tokens are forgotten): turned back on, the switch gives them back at their process’s next start (“Restart”). Removing an account takes its entry out.
- If the server does not start, the tab says so (“The server did not start: …”).

Claude Code knows the server as `escouade`: its tools are called `mcp__escouade__<tool>` (for example `mcp__escouade__list_tickets`); in OpenCode, `escouade_<tool>`.

Escouade’s agents, whatever their harness, do not use these entries: they get the server through their process’s options, with their own token, which wins (see [Escouade’s agents and the server](#escouade-s-agents-and-the-server)).

> [!NOTE]
> On Windows with Claude Code in WSL, Escouade’s MCP tools need WSL’s mirrored networking: `networkingMode=mirrored` under `[wsl2]` in `%UserProfile%\.wslconfig`, then `wsl --shutdown`. Settings › Harness reminds you when WSL’s network is in NAT mode.

## The tools

In the arguments, a project is named by its id or its name (any case), an agent by its id or its name, a ticket by its key (`ATL-12`, any case) or its id. Answers are JSON.

### Reading

These twelve tools change nothing.

| Tool | Arguments | What it returns |
|---|---|---|
| `list_projects` | none | The projects, in the app’s order: id, name, folder, current git branch, number of agents (archived ones left out), number of tickets in each column, and the remote control settings: `remoteControl` (“Remote control for this project’s agents”) and `remoteControlAll` (“Remote control for all agents”, the same on every line; when on, it covers every agent of every project and the project’s switch is grayed out in the window). |
| `list_agents` | `project` (optional) | The agents that are not archived, oldest first, of every project or of one: id, name, project, status (`idle`, `running`, `waiting`, `done`, or `error`), whether a question or a permission is waiting for your answer and how many, the key of their ticket, harness (`engine`: `claude` for Claude Code, then `codex`, `copilot`, `cursor` or `opencode`), model, Claude account, cost in dollars, `subagentsRunning` (how many subagents are running, in the foreground or the background), `backgroundTasksRunning` (how many background tasks are running: commands, monitors, remote agents, teammates, and workflows, never the subagents; it is the “N in background” of the card), and remote control. These two counts say that an agent that shows “Done” still has work running: `list_background_work` details it. `remoteControl` says whether it is in effect for the agent right now, so whether its session is reachable from claude.ai. `remoteSource` says what turned it on: `hand` (you, with the right-click on the agent), `project` (the project’s setting) or `global` (the setting for all agents, which comes before the project’s when both are on); `off` when you set the agent apart with “Turn off remote control” (no setting gives it back, a restart included, until you turn it on by hand); `null` when it is not in effect and the agent is not set apart. So `remoteControl` is `true` with `hand`, `project` or `global`, and `false` with `off` or `null`. `remoteState` is the state of the link with claude.ai that Claude Code reports: `ready` (waiting for a connection), `connected` or `unavailable` (in the Claude Code view, the interface is running but Claude Code did not open remote control: no claude.ai subscription, network, proxy or organization policy); `null` with no link in progress. `interfaceRemote`, for an agent in the Claude Code view: `true` when its interface is running, started with remote control (it stays linked to claude.ai until its next launch, even if `remoteControl` went back to `false` after a turn-off), `false` when it runs without, `null` when none is running (an agent outside the Claude Code view, or an interface not started). |
| `list_tickets` | `project`, `column` (optional: `todo`, `doing`, `review`, or `done`) | A project’s tickets in the Kanban’s order: id, key, title, column, the keys of the tickets they wait for, their agent’s name, why they are blocked, and the account, model and effort of their agents when they are not on “Auto”. |
| `get_ticket` | `ticket` | A whole ticket: title, description, criteria (met or not, with the agent’s note), loops (the current one and the maximum), column, tickets it waits for, progress, its images (`index`, `file`, `name`, `mediaType`, and `size`: pasted or dropped in the ticket’s window, or attached through the server; its agent gets them with its first message), its other files, of any format (`files`: `index`, `file`, `name`, and `size`, `null` for a file the purge of the settings took; joined in the ticket’s window or attached through the server; its agent gets their paths with its first message, and `get_ticket_file` reads one), the external ticket it comes from (Jira, Trello, GitHub, Linear, ClickUp, GitLab, or Azure Boards), the account (`account`, its name, with `accountId`), model and effort of its agents (`auto` when they follow the current account, the Kanban or the account; `accountLost`: why it went back to “Auto”), and what it takes to follow its flow: its agent (id, name, status, requests waiting), its branch and worktree (its agent’s: once the ticket is done, the worktree may be gone), what blocks it (`blocked`, `conflict`), the validation step running (`step`) and, once it is done, its result (`outcome`: the text, the pull request’s address when there is one, the commit the merge made on the target branch). An Escouade agent may leave out `ticket` to read its own. |
| `get_ticket_image` | `ticket` (optional), `file` or `index` | One image of a ticket, which Claude receives as an image (the content), followed by its `index`, `file`, `name`, `mediaType`, and `size` in bytes. It is named by its `file` (the name `get_ticket` gives) or by its `index` (its rank in the list of `get_ticket`, from 0), one of the two only. An Escouade agent may leave out `ticket` to read an image of its own ticket, and reads the images of the tickets of the projects it sees, as `get_ticket` does; Claude outside Escouade reads those of every project. An image the ticket doesn’t have (an unknown name, a rank outside the list) is refused, and no name ever leads to a file other than the ticket’s. |
| `get_ticket_file` | `ticket` (optional), `file` or `index`, `offset` (optional), `bytes` (optional) | A part of another file of a ticket, of any format, named as an image is (`file` or `index` in `files` of `get_ticket`). Without `offset`, its end; with it, from that byte on. `bytes` is 8,192 by default, 65,536 at most: a bigger file is read in several calls, so that the answer fits what Claude Code takes from a tool. Returns `size` (the whole file’s), `offset` and `length` (where the part starts and how many bytes of the file it holds), `encoding` (`text` when it is text, cut between two characters, else `base64`), and `content`. Claude outside Escouade also gets `path`, where the file is on your machine, to read it whole by its own means. An Escouade agent may leave out `ticket` to read a file of its own, reads the files of the tickets of the projects it sees, and gets no path. A file the purge took is refused. |
| `get_usage` | none | Each account’s quota, of every harness: its harness (`engine`), whether new agents of that harness start on it now, its meters (`meters`: a window of a length in `minutes`, or the month’s credits; `pct` from 0 to 100, `resetsAt`), Claude Code’s 5-hour and weekly windows also as `fiveHour` and `sevenDay`, and why the autopilot holds the tickets back (`reason`: `window` with its `minutes`, `credits`, or `limit`), until when. |
| `index_search` | `project` (optional), `query`, `kind` (optional), `limit` (optional), `path_include` and `path_exclude` (optional), `literal` (optional), `ids` (optional), `exact_total` and `timeout_ms` (optional, literal) | The symbols of the project’s code index (functions, methods, classes, types, fields, Markdown headings) whose name, doc or signature hold the words of the code, the best first, one line each: `file:line-end: name (kind) — signature`, the id with `ids`. With `literal`, an exact text of the source, `file:line: text`. The paths of `.escouade/queryignore` are left out. The answers of the six `index_…` tools carry no line about a saving; Escouade keeps a count for the statistics. An agent of Escouade may leave `project` out (its own) and is answered for the folder it works in. When the project has not turned “Code index” on, the tool says so and where to turn it on. |
| `index_context` | `project` (optional), `task`, `keywords` (optional), `max_nodes` (optional), `include_code`, `max_code_blocks` and `max_code_lines` (optional), `exclude_node_ids` (optional), `max_per_file` (optional), `path`, `path_include` and `path_exclude` (optional) | The context of a task told in words, in one call, in Markdown: the entry points, the symbols they are linked to, the code of the entry points (five blocks at most, of 1,500 bytes at most; a cut one ends with the `index_body` call that gives the rest), then `### Retrieval` (the terms that found nothing, to ask again with `keywords`) and `seen_node_ids`, for the next call’s `exclude_node_ids`. |
| `index_body` | `project` (optional), `symbol` or `node_id`, `limit` (optional) | The whole body of a symbol, by its name (`Type::member` or its last segments) or its id; a name several definitions bear gives their list, to ask again by id. |
| `index_callers` | `project` (optional), `id` or `name`, `path` (optional), `limit` (optional), `max_matches` (optional) | Who calls a function or a method: by its id (the one `index_search` gives with `ids`), or by a name (`forget`, `Runtime::forget`) answered definition by definition. The calls that may mean it among others are told apart. |
| `index_callees` | `project` (optional), `id` or `name`, `path` (optional), `limit` (optional), `max_matches` (optional) | What it calls: the definitions in the project, the calls left to a tie, and the names left (the language’s, libraries’). |
| `index_impact` | `project` (optional), `id` or `target`, `depth` (optional), `limit` (optional), `max_matches` (optional) | What a change would touch: the callers (up to `depth` levels), the types that extend it, the files that import it, and every file touched, definition by definition. |
| `get_board` | `project` | A project’s Kanban settings, those of the “Kanban” tab of its settings: `project` and `projectId` (the project’s name and its id), `action` (what “Approve” does: `merge`, `pr`, `push`, or `keep`), `target` (the target branch; the project’s current branch while the Kanban has none), `strategy` (`merge`, `squash`, or `rebase`), `draft`, `cleanup`, `conventional`, `conflict` (`ask`, `agent`, or `abort`), `maxParallel`, `autopilot`, the ticket agents’ `model`, `effort`, and `mode` (empty: those of the app, which `defaults` gives), `testsFirst` (true only if the Kanban has a test command), `testCommand`, and `prefix`. Open to every project. Its answer given back as is to `set_board` is accepted and changes nothing. |
| `get_workflow` | `project` | A project’s workflows, as the Workflow tab shows them (read again if a file they read changed), with the corrections of Settings › Projects › Workflow: for each one its doors, its steps (command, sub-agents, files read and written, and `agentsHere`, the agents on it now: id, name, since when, nth stay), its returns (`back`, with their `condition` and `max`), its state files and its exit; then `alone` (commands that belong to no workflow) and `agentsElsewhere` (agents that follow a workflow without being on a step). `list_agents` and `get_agent_summary` give each agent’s `workflow` too, the second with the history of its steps. See [workflows](workflows). |
| `get_agent_summary` | `agent`, `project` (optional) | An agent without its conversation: id, name, status, harness (`engine`, as in `list_agents`), the ticket’s key, last message (2,000 characters at most; a longer message gives its start and its end), and the files it edited (the latest 100 at most), with the number and the type of the requests waiting for an answer and, as in `list_agents`, its subagents and background tasks that are running (`subagentsRunning` and `backgroundTasksRunning`) and its remote control (`remoteControl`, `remoteSource`, `remoteState` and `interfaceRemote`). |
| `list_background_work` | `agent`, `project` (optional) | An agent’s subagents and background tasks, as the sidebar shows them: what is running first, then what is finished, the latest finished first. Returns the agent (`id`, `name`, `status`), its two counts (as in `list_agents`), then `subagents` and `tasks`. A subagent gives its `id` (the id of the call that started it), its `type` (`subagent`), its `description`, its kind of subagent (`subagentType`), its `model`, its `status` (`running`, `done`, `failed`, `stopped`, or `interrupted`), `background` (in the background, otherwise in the foreground), `startedAt` and `endedAt` (in milliseconds), its `tools` and its `tokens`, what it is doing (`doing`), its task (`taskId`), and the subagent that started it (`parent`). A background task gives its `id` (Claude Code’s), its `type` (`command`, `monitor`, `remote`, `teammate`, or `workflow`), its `description`, its `command`, its `status`, `startedAt` and `endedAt`, its `summary` (Claude Code’s last word on it, with a command’s exit code), and `parent` (the task of the subagent that started it); a workflow adds `name`, `now` (its phase), `tools`, and `tokens`. A field with no value is left out, and the path of the output file is never given. Open, like `get_agent_summary`, to every project the caller sees: Claude outside Escouade sees everything, and an Escouade agent sees everything of the projects it sees. |
| `get_background_output` | `agent`, `project` (optional), `id`, `bytes` (optional) | The **end** of the output of a command or a monitor, with the window’s limits and checks: 8 KiB of a task that is running (from its process, otherwise from its output file), up to 256 KiB of the file once it has finished, and only the `<task>.output` file of a `tasks` folder, never a network path. `bytes` (from 1 to 65,536, 8,192 by default, for a task that is running as for one that has finished) asks for less: the end is kept, cut at a character. The window keeps its limits, but an MCP client cannot ask for as much: 256 KiB of log, escaped in JSON, would exceed the roughly 25,000 tokens a tool answer can have for Claude Code. A value outside the range is brought back inside it, not refused; an unreadable value (`"abc"`, `-1`) is refused. Returns `agent`, `id`, `type`, `status`, `source` (`process`, `file`, `report`, or `none`), `output`, `totalBytes`, and `truncated` (true when the start is missing). A remote agent, a teammate, and a workflow have no output (`source` is `none`). For a subagent, the tool returns its report (16,000 bytes at most, as in the window, given whole: `bytes` does not apply to it; `source` is `report`, or `none` while it has handed nothing back), and `id` can be its task (`taskId`). In the Claude Code view, the report is read in the subagent’s transcript without changing its line: reading a report changes nothing. An Escouade agent reads in the projects it sees, its own tasks included. |
| `list_requests` | `agent` (optional), `project` (optional) | The questions and the permission requests waiting for your answer, of one agent, of one project, or of all, in the order they came: the agent and the key of its ticket, `request` (the id the two answering tools name), `type` (`permission`, `question`, or `plan` for a plan to approve), since when, the tool and what it acts on (the command, the file, the whole plan), everything Claude Code sent (the content of a file to write, the strings of an edit, the flags of a command), the reason, whether Claude Code would refuse it by default, and for a question its questions with their options and whether several may be picked. `cut` says whether a text was cut: the whole request is in the conversation. An agent in the Claude Code view has none here: its requests are in its terminal. |
| `wait_ticket` | `tickets` (1 to 20), `timeout` (optional), `since` (optional) | Waits until one of these tickets changes, then says what: its column, its block (`blocked`, `conflict`), its agent starting or ceasing to wait for an answer (`waiting`: `list_requests` gives the requests), its agent coming to rest in “To review” (`resting`: the ticket can be approved), or the ticket deleted (`gone`). Answers at the first change, or after `timeout` seconds (120 by default, 240 at most) with `changed: false`. Each answer gives a `since`: pass it to the next call (even after other tools) and a ticket whose state differs from the one it holds is answered at once, a change made between the two calls included; without `since`, each ticket’s state at the call is the one compared. If the client cancels the request or drops the connection, the wait stops. |

### Acting

These tools do what you would do in the window, through the same functions: the window is told, external tickets follow, and the Kanban updates.

| Tool | Arguments | What it does |
|---|---|---|
| `create_ticket` | `project`, `title`, `description`, `criteria`, `after`, `images`, `files`, `account`, `model`, `effort` | Creates a “To do” ticket at the bottom of the column. `criteria` is a list (two default criteria without it), `after` the tickets it waits for, by key or id. `images` attaches images to the ticket, and `files` files of any format, as its window does. With the autopilot on, it starts as soon as a slot is free and its predecessors are done. Its description ends with “Created by `<author>` through Escouade”. `account` (the account’s name or id), `model` and `effort` set its agents as “Account”, “Model” and “Effort” in its window do; `auto`, the default, takes the current account, then the Kanban’s model and effort, else the account’s. A ticket set on an account always starts there and stays there, waiting for its reset at the limit. An account the project may not use is refused, with why. |
| `update_ticket` | `ticket`, `title`, `description`, `criteria`, `after`, `addImages`, `removeImages`, `addFiles`, `removeFiles`, `account`, `model`, `effort` | Edits a “To do” ticket, field by field: what is left out stays. `criteria` and `after` replace the whole list. `addImages` adds images at the end, `removeImages` takes some off: the ones neither names are kept (the whole list is never replaced, so a forgotten image is not lost), and the two combine. `addFiles` and `removeFiles` do the same for the other files, and a file taken away is deleted. Images or files alone change nothing else, the description included. A ticket that has already started cannot be edited, images and files included, and the refusal comes before any file you gave is read; a dependency that would make two tickets wait for each other is refused. If the title, description, or criteria change, the last line of the description becomes “Modified by `<author>` through Escouade”. `account`, `model` and `effort` as for `create_ticket`: `auto` sets them back to the default. |
| `move_ticket` | `ticket`, `position` (`top`, `bottom`, or `before`), `before` | Puts a “To do” ticket at the top, at the bottom, or just before another “To do” ticket of the project (`before`). Returns the column’s keys in their new order. |
| `set_board` | `project`, and any of `action`, `target`, `strategy`, `draft`, `cleanup`, `conventional`, `conflict`, `maxParallel`, `autopilot`, `model`, `effort`, `mode`, `testsFirst` | Sets a project’s Kanban, as its settings window does: only the fields given change, and `""` for `model`, `effort`, or `mode` puts the app’s back. The checks are the window’s: a known model, an effort among `low`, `medium`, `high`, `xhigh`, or `max`, a mode among `auto`, `default`, `plan`, or `acceptEdits`, a target branch that is a local branch of the project, 1 to 6 tickets in parallel. The window updates and the Kanban replans: turning the autopilot on can start tickets. The change applies to the next ticket agents, not to those already started. Returns the Kanban after the change, in the format of `get_board`. An agent that runs the Kanban can thus move the ticket agents to Sonnet to spare the quota. The answer of `get_board` given back as is is always accepted and changes nothing: a `target` equal to the Kanban’s (even empty) or to the one `get_board` shows is left as is, unchecked, and `testsFirst` is refused without a test command only to turn it on. An Escouade agent sets the Kanban of the projects it sees this way, mode included. With Haiku, which has no effort and no Auto mode, the ticket agents start without an effort and, if the mode is `auto`, in “Ask” mode. |
| `start_ticket` | `ticket`, `account`, `model`, `effort` | Starts a “To do” ticket as the “Start” button does: its agent starts as soon as a slot is free. Answers once the ticket is queued; follow it with `get_ticket`. `model` and `effort` apply to this ticket only and come before the Kanban’s for its agent (keep `opus` on an architecture ticket while the Kanban is on `sonnet`): `""` puts the Kanban’s back, left out they do not change, with the same checks as `set_board`. Returns `key`, `starting`, and the `model` and `effort` its agent will start with (the ticket’s, else the Kanban’s, else the app’s); `effort` is missing when that model takes none (Haiku, whose agent also starts in “Ask” mode if its mode would be `auto`). The ticket keeps its own if it is sent back and started again. Its card shows them, without the effort for Haiku, next to its key (“Opus · Max”). `account` (name or id, `auto` for the current account) does the same for the account: it takes precedence over the ticket’s and becomes its own. |
| `create_agent` | `project`, `message`, `worktree`, `model` | Creates an agent in a project, with its first message, without changing the agent you are looking at. `worktree` (true or false) says whether it works in a worktree of its own, otherwise the project decides; `model` is named as in Claude Code (`sonnet`, `opus`, `haiku`…). Returns the agent’s id and name. |
| `send_message` | `agent`, `project`, `text` | Writes to an agent. An agent at work reads the message after its current turn (the answer says `queued`). The text is 32,000 characters at most (characters, not bytes): beyond that, an error says how long it is, without sending it back. The window does not change. |
| `stop_agent` | `agent`, `project` | Interrupts an agent’s current turn, as the stop button of its conversation does. The agent stays, and can be sent a message afterward. |
| `stop_background_work` | `agent`, `project` (optional), `id` | Stops a background task, a workflow, or a subagent in the background, as the “Stop” of its view in the window does. `id` is that of a line of `list_background_work` (for a subagent, its call id or its task `taskId`). Returns `agent`, `id`, `type`, and `stopped: true`. The refusals are the button’s: the line is no longer running, it is a subagent in the foreground (the agent waits for it, and the agent’s own “Stop” stops it along with its turn), Claude Code has not given its task yet, the agent is in the Claude Code view (its interface does it), has no process, or is archived. The answer says the stop is requested: the end of the line comes afterward, and `list_background_work` shows it. Claude Code gives the agent a turn to notice, which costs it quota. An Escouade agent stops nothing of its own agent, background tasks and subagents included. |
| `message_subagent` | `agent`, `project` (optional), `subagent`, `text` | Writes to a subagent in the background, as the “Write to it” of its view in the window does. Claude Code lets no one write to a subagent directly: the message goes to the agent, which is asked to pass it on as is to the subagent through its `SendMessage` tool. It is headed by “Message from `<author>`:” and never presented as yours. This costs the agent a turn, so quota. Refused: a subagent that is no longer running (“This subagent is no longer running.”, even with a task given: Claude Code would resume it with the message, for nothing), a subagent in the foreground or whose task Claude Code has not given, an agent in the Claude Code view or archived, and a `subagent` that is a background task and not a subagent. An empty text, or one of more than 32,000 characters (characters, not bytes; the error says how long the message is, without sending it back), is an error, as for `send_message`. When the agent’s Claude account is held back by the quota, the message is refused too, like `send_message`, but only after everything else, so a client does not retry at 2 pm only to be refused anyway. Returns `agent`, `subagent`, and `queued` (true when the agent is at work: the message waits for the end of its turn). An Escouade agent does not write to its own subagents. |
| `answer_permission` | `agent`, `project`, `request`, `decision` (`allow` or `deny`), `message` | Answers an agent’s permission request as the “Allow” and “Deny” buttons of its card do, or approves (`allow`) or sends back (`deny`) its plan. `message`, with `deny`, tells the agent why, or what to do instead. “Always allow” is not offered (`always` is refused): a lasting rule stays your decision, in the window. The request’s card, in the agent’s conversation, says who answered (“Allowed by `<author>` through Escouade”), and the agent reads who refused. |
| `answer_question` | `agent`, `project`, `request`, `answers` | Answers an agent’s question as its question card does: for each question (`question`, its text, which can be left out when there is only one), the labels of the options picked (`choices`, several only when the question allows it) or a free text (`text`). Every question needs an answer. The card says “Answered by `<author>` through Escouade”, and the agent reads each answer followed by who gave it. |
| `approve_ticket` | `ticket` | Approves a “To review” ticket as the “Approve…” button does: the tests first when the Kanban runs them, the commit, then what the project’s Kanban settings say (merge into the target branch, push and open a pull request, push the branch, or keep it). A ticket whose branch brings nothing more than its target, because you already merged it by hand, is closed without merging again. Answers as soon as the approval has started, with the ticket (its step reads “Validation…” or “Approving…”, in the interface’s language) and its `since`: follow it with `wait_ticket` or `get_ticket`. It may push and open a pull request. |
| `reject_ticket` | `ticket`, `comment` | Sends a “To review” ticket back as “Send back” does: it goes back “In progress”, with the same agent and the same worktree, and the agent receives the comment as test feedback, followed by “(sent back by `<author>` through Escouade)”. An empty comment is refused. Returns the ticket and its `since`. |
| `resume_ticket` | `ticket` | Resumes a blocked “In progress” ticket as “Resume” does: its agent goes on, or the ticket starts again when its agent is gone. Refused for a ticket that is not blocked, or whose agent is waiting for its quota to reset (the refusal says until when). Returns the ticket and its `since`. |
| `resolve_conflict` | `ticket` | Hands the merge conflict of a “To review” ticket to its agent as “Let the agent resolve” does: the target branch is merged into its own, then the agent is asked to resolve the conflicts (to rebase, with the rebase strategy) and to end with its report. Refused for a ticket with no conflict. Returns the ticket and its `since`. |
| `dismiss_block` | `ticket` | Dismisses the block of a “To review” ticket (a conflict, a failed step) as “Cancel” does: the block goes, the ticket stays in “To review”, and nothing else changes. Returns the ticket and its `since`. |
| `delete_ticket` | `ticket` | Deletes a ticket of any column as “Delete” does. A ticket “In progress” or “To review” has its agent archived, its worktree kept; the tickets that came after it no longer wait for it. Cannot be undone. Refused while the ticket’s approval is running. Returns `key`, `deleted`, and `agentArchived`. |

A title is 200 characters at most, a description 10,000, and a ticket has 30 criteria of 500 characters at most. The text of `send_message` and of `message_subagent` is 32,000 characters at most. A ticket created by the server has the default number of loops, 5, and its own branch.

A ticket’s images are attached with `create_ticket` (`images`) and `update_ticket` (`addImages`). An image to attach is `{ name, mediaType, data, path }`, with exactly one of `data` (its content in base64, in which case `name` is required) or `path` (the path of a file on your machine, whose name stands in for `name` when it is missing). `mediaType` is only a hint: as in the window, the type is read from the content. To take images off with `removeImages`, or to read one with `get_ticket_image`, an image is named with `{ file, index }`: its `file`, the name `get_ticket` gives, or its `index`, its rank in the list of `get_ticket`, counting from 0.

A ticket’s other files, of any format, are attached with `create_ticket` (`files`) and `update_ticket` (`addFiles`). A file to attach is `{ name, data, path }`: its content in base64 (`data`, with `name`), for a small file, since a request weighs 32 MiB at most; or the path of a file on your machine (`path`), which is then copied. The rules are those of the ticket’s window, because the file takes the same way: 20 files at most per ticket, each within the largest size of [Settings › Harness](settings-claude-code#attachments). They are checked before anything is copied, and a refusal leaves nothing behind. The name is cleaned as the window cleans the name of a file it copies. To take one away with `removeFiles`, or read one with `get_ticket_file`, it is named by `{ file, index }`, as an image is.

### Steering agents to the index

When a project turns “Code index” on, Escouade steers its agents to these tools rather than grep, without ever blocking a search. In the views of Claude Code and Codex, whose hooks Escouade listens to, a search that aims at a symbol (`grep`, `rg`, the Grep tool, for a name like `parse_config` or `parseConfig`, or a declaration like `fn parse`) gets, before it runs, a line saying what the index finds in one call (a symbol, its callers, the impact of a change); a search for a text (a message, a phrase, a plain word) goes by with no word. For the other harnesses and views, and for agents driven without a terminal view, the same advice is a rule in the agent’s instructions. The answers of the index are counted by agent and by project, for the statistics.

### Leading the whole Kanban from Claude

With these tools, Claude takes a ticket from start to finish without you opening the window: `start_ticket` starts it, `wait_ticket` waits until it changes (its agent asks a question, moves to “To review”, gets blocked), `get_ticket` says where it stands, then `approve_ticket` approves it or `reject_ticket` sends it back with what is wrong. `resume_ticket`, `resolve_conflict`, and `dismiss_block` deal with a block, and `delete_ticket` deletes. `wait_ticket` hands back at the first change, or after 120 seconds by default (240 at most); the `since` of its answer, passed to the next call, has a ticket whose state differs from the one it holds answered at once, a change made between two calls included. `approve_ticket`, `reject_ticket`, `resume_ticket`, `resolve_conflict`, and `dismiss_block` also return a `since`, the ticket’s as it was before the action: passed to `wait_ticket`, it has what follows told at once, a quick approval included.

Each follows the rules of the window’s button and the guardrails below: an Escouade agent neither approves nor sends back its own ticket, and only acts in the projects it sees.

### An agent’s subagents and background tasks

An agent that shows “Done” may still have work running: `list_agents` and `get_agent_summary` count its subagents that are running (`subagentsRunning`) and its background tasks that are running (`backgroundTasksRunning`, the “N in background” of its card). When either is not zero, `list_background_work` says which ones, `get_background_output` reads the end of a command’s output or a subagent’s report, then `stop_background_work` stops what should not go on, or `message_subagent` gives an instruction to a subagent in the background. It is what you do in the window with an agent’s [subagents](plan#subagents) and [background tasks](plan#background-tasks), with the same limits and the same refusals. A command’s output can be long: `bytes` (64 KiB at most) asks for less than the window, so the answer fits what Claude Code accepts from a tool (about 25,000 tokens). Reading is never acting: `get_background_output` changes nothing, even for the report of a subagent in the Claude Code view.

### The shared memory

Four tools read and write a project’s [shared memory](shared-memory), its agents’ work notebook: `search_memory` (`query`, optional `limit`), `read_memory` (`name`), `write_memory` (`name`, `description`, optional `type`, `body`) and `forget_memory` (`name`). Each takes a `project`, which an Escouade agent may leave out for its own. They only touch the project’s `.escouade/memory/` folder, never through a symbolic link.

### Reserved to Escouade’s agents

These two tools are refused to Claude outside Escouade.

| Tool | Arguments | What it does |
|---|---|---|
| `report_progress` | `line` | Publishes a status line of 120 characters at most, about what the agent is doing. It shows under its name in the sidebar and the overview, and on the card of its “In progress” ticket, until its next call. An empty line clears it. |
| `split_ticket` | `tickets`, `chain` | Splits what remains of the agent’s ticket into ten “To do” tickets at most, after its own. With `chain` true (the default), each comes after the one before and the first after the agent’s ticket; false, all come after the agent’s ticket alone and may run in parallel. Each ticket can have its `images`, which name images of the agent’s ticket (by `file` or `index`, as for `removeImages`): without that argument it takes them all, with `[]` none. Each gets its own copies, and the agent’s ticket keeps its own. An unknown reference, or an image named in `images` whose file is missing, refuses everything and creates nothing; without `images`, an image of the agent’s ticket whose file is gone is skipped instead of blocking the split. Its other files follow the same rule with `files`: all of them by default, the ones named, or none with `[]`; a file taken by default that is gone, or that the settings no longer allow (too big), is skipped, and a named one refuses everything. Refused to an agent without a ticket. Returns the keys of the tickets made or, if some images or files were skipped, `tickets` (the keys) and `skipped` (one sentence for each). |

## The guardrails

The tools that act follow the rules of the window and of the autopilot:

- **Quota.** No ticket (`start_ticket`) or agent (`create_agent`) starts when every account usable for the project is at its limit: quota window used up, usage limit, an agent waiting for its reset. “Pause above quota” and the day’s budget hold back the autopilot alone, never a tool. A single free account is enough. The refusal says until when (“The autopilot is paused until 14:30: the 5-hour window is 100% used. Try again then.”). `send_message` is refused when the agent’s account is held back that way (agents on another account can still take a message), and so is `message_subagent`, but after all its other refusals.
- **In parallel.** The project’s “In parallel” maximum of tickets is not exceeded by `start_ticket`, nor its maximum of agents working at once by `create_agent`.
- **Dependencies.** A ticket that comes after tickets that are not done is not started without them: the refusal says which ones, and `update_ticket` takes the dependencies off. A circular dependency is refused.
- **A ticket’s images.** The window’s limits and refusals: PNG, JPEG, GIF, and WebP (the type is read from the content), 5 MB per image, 18 MB in all, and 20 images at most per ticket, the ones `update_ticket` keeps included; the total is held before reading, and the image that would go over it is refused before it is read. A refused image leaves nothing behind: no ticket made, no change, no file. An image’s name is cleaned (what follows the last `/` or `\`, on one line, 100 characters at most). For `path`, Claude outside Escouade gives any absolute path to a file on your machine; an Escouade agent only a file under its working folder (a link, symbolic or junction, that leaves it is refused), and a file outside that folder gets the same refusal whether it exists or not. This is a safeguard of the server, not a security boundary: an agent that has control of your machine has other ways. Also refused: a relative or network path (`\\server\share`, `//host/share`), anything that is not an ordinary file, a file of more than 5 MB (refused without being read), and a file that is not an image. The path is not kept: the ticket keeps a copy of the content. A ticket that has already started keeps its images.
- **A ticket’s other files.** The window’s limits and refusals: 20 files at most per ticket, the ones `update_ticket` keeps included, each within the largest size of the settings; checked before anything is copied (the count before a file is looked at, a file’s size before a byte of it is read). A refusal leaves nothing behind, not even a copy waiting. `path` follows the rules of images: an Escouade agent only gives a file of its working folder. `get_ticket_file` returns 64 KiB at most at a time, and gives the path to Claude outside Escouade only.
- **Setting the Kanban.** The model and the effort have the window’s checks in both tools, `set_board` and `start_ticket`: an unknown model, or an effort outside the list, is an error. The rest only applies to `set_board` (`start_ticket` has no mode). It refuses `bypassPermissions`: starting agents with no permission request at all stays your decision, in the window, like “Always allow” (it is accepted only if it is already the Kanban’s mode, to change something else without undoing it); the other modes (`auto`, `default`, `plan`, `acceptEdits`) are set as in the window, including by an Escouade agent for the Kanban of the projects it sees. It also refuses `testsFirst` without a test command, only to turn it on: the server runs no command and does not change the Kanban’s, which is set in the window. A mode outside the list, a target branch that is not a local branch of the project (except the one the Kanban already has, even empty, or the one `get_board` shows: it is left as is), an “In parallel” outside 1 to 6, or no field to change, is an error.
- **Remote control.** `list_projects`, `list_agents` and `get_agent_summary` read it; no tool turns it on, turns it off or sets it, for an agent, a project or all of them: turning it on exposes a session on the internet, reachable from claude.ai and the Claude app. That stays your decision, in the window (Settings › Harness, Settings › Projects, right-click on an agent), like `bypassPermissions` and the Kanban’s test command, which the tools do not set either.
- **The Kanban.** `start_ticket` is refused when the project’s Kanban starts nothing for now (the target branch has no commit or is not found, no active account serves the project); the refusal says why.
- **Shared tickets.** A ticket a teammate shared ([Sharing the Kanban](shared-board)) is started by hand alone: `start_ticket` refuses it, and so does `delete_ticket`. The ticket tools say the sharing (`shared`), and `create_ticket` and `update_ticket` take `shared` to share a ticket or stop.
- **Escouade’s agents** act where they see, Kanban included: the agent of a project that is not private, on its own and on every project that is not private; the agent of a private project, on its own alone. A private project is therefore only touched by its own agents, and a refusal never names it. They do not write to themselves, do not stop themselves, stop neither their own background tasks nor their own subagents, do not write to the latter, and do not answer their own requests. You do not write to an archived agent.
- **Subagents and background tasks.** Each tool is refused where the window refuses, with the same text. `stop_background_work` is for a line that is no longer running, a subagent in the foreground, a task Claude Code has not given yet, an agent in the Claude Code view, with no process, or archived. `message_subagent` is for a subagent that is no longer running, is in the foreground, or has no task given, an agent in the Claude Code view or archived, a `subagent` that is a background task, and, last of all, when the agent’s Claude account is held back (so a client does not retry at 2 pm only to be refused anyway); an empty text, or one of more than 32,000 characters, like the text of `send_message`, is an error. `get_background_output` only reads the `<task>.output` file of the task, never another file or a network path. An Escouade agent stops neither its own background tasks nor its own subagents and does not write to the latter; it acts, and reads outputs and reports, in the projects it sees. Every call is logged in the MCP activity, without the message’s text or the output.
- **The Kanban’s flow.** Each tool is refused where the window refuses: `approve_ticket` and `reject_ticket` for a ticket that is not in “To review”, whose agent is working, or whose approval is already running; `resume_ticket` for a ticket that is not “In progress”, is not blocked, or whose agent is waiting for its quota to reset; `resolve_conflict` for a ticket with no conflict; `dismiss_block` for a ticket that is not blocked; `delete_ticket` for a ticket whose approval is running. A message the flow sends to an agent (`reject_ticket`, `resolve_conflict`, `resume_ticket`) only goes while that agent’s Claude account is not held back. An Escouade agent neither approves nor sends back its own ticket (approving would merge its work without a review), and does not act on it either with `resume_ticket`, `resolve_conflict`, `dismiss_block`, and `delete_ticket`: it is up to you or another client. Any client of the server can approve a ticket, and `delete_ticket` deletes as the window does, a ticket of any column. Every call is logged in the MCP activity.
- **Answering a request.** Once “Agents can drive Escouade” is on, any client of the server sees the requests of every project and can answer them, Claude outside Escouade as well as the agents, with no extra setting; an agent answers those of the agents of the projects it sees, never its own. `answer_permission` only offers `allow` and `deny`: “Always allow” stays your decision, in the window. A request that no longer waits for an answer (you answered it in the window, another client did, or the agent no longer runs) is refused, and if two answers arrive at the same time, only one goes through. An agent in the Claude Code view has nothing to answer here: its requests are in its terminal.
- **No tool** runs a command of its own choosing or deletes a project or an agent: an agent pushed by booby-trapped content cannot use them to escalate its rights. The exceptions are answering the agents’ requests and the Kanban’s flow. With the switch on, an agent can allow, one request at a time and never for good, what another agent of its project asks; it can also approve (the tests, then the merge) or delete the ticket of another agent of its project, as you would in the window.
- **What comes from the server is never taken for you.** A message sent to an agent (`send_message`, the first message of `create_agent`, or the text `message_subagent` has passed on to a subagent) is read by the agent and shown in its conversation under “Message from `<author>`:”, the author being the name of the agent sending it or “Claude (outside Escouade)”. A ticket created or split by the server ends with “Created by `<author>` through Escouade”, a ticket it modified with “Modified by `<author>` through Escouade”, on its card as in its agent’s protocol. The card of a request the server answered says who did (“Allowed by `<author>` through Escouade”, “Denied by `<author>` through Escouade”, “Answered by `<author>` through Escouade”), and a refusal, like each answer to a question, tells Claude who it comes from, not that it is you (“Refused by `<author>` through Escouade”, “SQLite (answer from `<author>` through Escouade)”).

A permission request for an Escouade tool names it in plain words (“Escouade · Create a ticket”, “Escouade · Start an agent”…) and shows what Claude gives it, one argument per line. A value of more than 2,000 characters is cut: the card says how many are not shown and points you to the conversation.

## Escouade’s agents and the server

The “Agents can drive Escouade” switch also serves Escouade’s agents, those of every project: there is nothing to allow in a project’s settings.

- **On**, each agent receives the server when its process starts, with a token of its own: it acts in its own name, never as Claude outside Escouade. It reads the tickets and the agents, and can create tickets or start other agents, which uses quota, and take the tickets through to their approval, except its own. It also sees the questions and permission requests of the agents, and can answer them. All of this in its own project and in every project that is not private.
- **Off**, the agents already running lose the tools at once, and Escouade keeps its server away from every agent that starts, even when an `escouade` entry is left in your Claude Code config: its tools are refused, and the server itself is not loaded (Escouade starts the agent with Claude Code’s `deniedMcpServers` setting). The agent therefore gets neither the tools nor the server’s instructions.
- **An agent already running** when you turn the switch on keeps a process without the tools. Its conversation shows “Escouade’s tools at the next start” with “Restart”: its process stops and the next one resumes the same session: the conversation stays. The button is disabled while the agent is busy (its turn, a question or permission waiting for your answer, the setup of its worktree, a subagent, a workflow, a command or a monitor in the background) and comes back when that is over. A command, a dev server or a monitor doesn’t end by itself: the card then says to stop its background tasks first, from their view (“Stop”; see [background tasks](plan#background-tasks)). In the Claude Code view, “Restart” starts its interface again. Settings › Harness says how many agents are in that case.
- Between projects that are not private, it is not a partition: an agent reads and acts in the others as in its own. So the agent of a product’s back end creates, edits, and starts the tickets of its front end, and writes to its agents. To partition a project, make it private (below).

The server runs while the switch is on, and stops with the app.

### Private projects

A project’s “Private project” setting (Settings › Projects, “Privacy” group, off by default) partitions it in the server, both ways, for Escouade’s agents:

- **The agents of the other projects don’t know it.** It is not in `list_projects`, `list_agents` or `list_requests`, and a tool that names it, by its id, its name, one of its tickets or one of its agents, answers that it can’t find it, with the same message as for a name that doesn’t exist: nothing gives away that it exists.
- **Its own agents see it alone.** `list_projects` gives only their project, and every other project, private or not, can’t be found by them in the same way. They read and act in their project as before.
- **You see everything**: Claude outside Escouade (the token declared in your harnesses) sees every project, and so does the window (tabs, overview, statistics).

Projects that are not private see each other and act on each other. A lock marks a private project, on its tile, beside its name in the title bar and in the settings. The change applies from the next call, without restarting the agents. To make every new project private, turn on “New projects are private” in the same tab. Its files are walled off too, by each harness’s rules: see [its files](settings-projects#its-files). So that the harness’s sessions, memory and history are not shared either, give it [an account reserved to it](accounts#an-account-for-a-private-project).

Outside the server too, Escouade passes nothing from a private project to another:

- **Copying the setup**: the “New project” assistant never offers a private project as the source, and says so under its choices (“A private project isn’t offered: nothing of a private project goes to another.”). Copying a project that isn’t private into a private one still works.
- **Duplicating the conversation**: the copy stays in the project of the agent copied. Nothing moves an agent, a conversation or a ticket to another project.
- **Dependencies**: “After” only offers the tickets of the same project, and through the server a private project’s ticket can’t be found in `after` as anywhere else. `split_ticket` splits within the agent’s project.
- **What Escouade writes to the agents** (a ticket’s instructions, messages, reminders, handover to another harness, names, branches, commit messages) only comes from the agent’s ticket, project and conversation: never the name nor the content of another project. Written texts are asked for without any session kept.

> [!NOTE]
> Up to 1.7, each project had its own “Agents can use Escouade” switch (Settings › Projects › MCP server). It is gone: a project that had it on while “Claude can drive Escouade” was off no longer gives the server to its agents until you turn “Claude and the agents can drive Escouade” on.

In a conversation, a call to an Escouade tool carries the label “Escouade · ” followed by its name (“Escouade · Read a ticket”, “Escouade · Set the Kanban”, “Escouade · Report progress”).

## MCP activity

Settings › Harness › “MCP activity” keeps the last 200 calls and refusals, the most recent first, updated live. Each line gives:

- the time (on hover, the date);
- the caller: the agent’s name, “Claude (outside Escouade)”, or “Unknown client” for a request refused before its token says where it comes from;
- the tool, and in short what it was asked (never a token; for images or files, how many, never their content or a path; for a background task’s output or a message to a subagent, the agent and the id, never the output or the text);
- the result: “Done”, “Refused”, or “Error”, with the reason for the last two (shown in the alert color).

For a `set_board` that succeeded, the line keeps what was asked and also says what changed: each changed field with its value before and after (“model: opus → sonnet · effort: (default) → medium”), or “No change”.

“Clear” empties the list. The log is not saved: it starts from zero the next time Escouade starts.

Also refused, and logged: a request without a token (“Request refused: no token”), with an unknown token, with an unexpected `Host` header, with an `Origin` header (a web page), or to a path other than the server’s.

## Token and network

- The server only listens on `127.0.0.1`, on a free port between 47000 and 47999, chosen at the first start and then kept (it only changes when its own is taken, and the declaration is then redone in every account).
- Every request carries a token, in the `Authorization: Bearer` header. Claude outside Escouade’s token is kept in the system keychain; when it refuses it, and on Linux, in `~/.escouade/mcp-token.json`, readable by you alone. It is also written in plain text in the config of each harness installed the switch declares it in (`~/.claude.json`, `~/.codex/config.toml`, `~/.config/opencode/opencode.json`, `~/.copilot/mcp-config.json` for “Main”). An agent’s token is its own, lives in memory and in a configuration file under `~/.escouade/mcp/` that the app removes when its process stops. An agent without the tools starts with `~/.escouade/mcp-refused.json`, which keeps the server out.
- A request sent by a web page (`Origin` header) or addressed to a name other than `127.0.0.1` or `localhost` is refused, even with a token: a site you visit cannot call the server.
- Another MCP client connects to `http://127.0.0.1:<port>/mcp` with the same header. The address and the token can be read in the account’s `.claude.json`, in the `escouade` entry, or in the command the tab offers when the declaration fails.
